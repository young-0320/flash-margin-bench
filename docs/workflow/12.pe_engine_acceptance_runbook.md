# 12. P/E 엔진 실칩 인수 — 돌리는 법과 읽는 법

- **작성일**: 2026-09-21
- **직전 상태**: 엔진(`ps/src/flash_wear.c`)·호스트 시뮬레이션·어댑터·실행기가 전부 서 있고
  TB 114개가 초록이다. **실칩에 P/E 를 낸 적은 없다** — [로그 45](../log/young/45.pe_engine_build_to_sim.md)
- **언제 쓰나 (2026-09-22 개정)**: **엔진(`ps/src/flash_wear.c`)을 고친 뒤 첫 실칩 실행**. 매번 거치는
  관문이 아니다 — 본 마모의 **첫 체크포인트가 100사이클이고 같은 판정 9줄을 돌린다**(`run_wear.py` 의
  `CHECKPOINTS` 첫 점, 유인 1회가 기본). 사이클 수도 판정도 같으므로 엔진이 그대로면 이 런북을
  다시 밟을 이유가 없다. TB 영역의 존재 이유는 「관문」이 아니라
  「파일럿 칩을 실험대로 쓰지 않고 엔진을 시험하는 자리」다 (S-4 §9). H 행의 `git_rev` 가 마지막
  통과와 다르면 그때 여기로 돌아온다
- **목표**: S-1 §13 A(100사이클)·B(전원 차단 복구)를 실칩에서 닫고, 결과를 「칩·엔진·전송 중
  무엇이 틀렸나」까지 읽을 수 있게 한다. C(측정 경로 연결)는 근접·원격 스윕이 막혀 있어(로그 44
  `[U44-8]`) 이 런북 밖이다
- **근거 문서**: S-1 §6~§10·§13 · S-4 §2·§4·§5.2·§9 · `docs/interface/pe_engine.md` §2 · 로그 45
- **명령 정본**: `docs/commands.md` §3 — 이 런북의 명령 블록은 그날의 순서이고, 옵션·자물쇠·산출물은 거기가 정본
- **절대 규칙**: P/E 는 비가역이다. `accept` 는 `--i-approve-real-pe` 없이 START 를 보내지 않는다.
  **이 런북(인수 시험)의 마모 영역은 TB 전용 1,000~1,006 이다** — `--base-sector` 의 기본값이라
  아무것도 안 주면 여기가 닳는다. 파일럿 마모 그룹 0~6 은 `--base-sector 0` 으로 **본 실험에서만**
  건드린다 (2026-09-22, 인수 시험 통과 뒤 열렸다)
- **파일럿 착수 전 — 그 칩의 신품 25MHz 스윕(x=0)이 집계표에 있어야 한다.** `CHECKPOINTS` 는 100 부터라
  0 점은 S-2 신품 측정이 맡는다. 없으면 `run_sweep_chip.py --mode newchip --mhz 25` 를 먼저 돈다
  (2026-09-22 chip01 에서 빠뜨릴 뻔했다 — 집계표 §1 · 워크플로 10 W10-A)

## 0. 준비 — 한 번만

```bash
source ~/Xilinx/2025.2/Vitis/settings64.sh
vitis -s ps/scripts/build_flash_wear.py        # build/vitis_wear/flash_wear/build/flash_wear.elf (프리스케일러 64)
uv run pytest host/tests/ -q                    # 114 passed — mock·sim·실행기. 여기가 빨간불이면 보드를 만지지 않는다
```

확인할 것 — `docs/chip_registry.md` 에 chip01 의 UID(`D1654CB09B352233`)가 있다. chip01 은 prep
이 0~127 만 썼으므로 tally(512·1,536)와 TB 영역(1,000~1,006)이 `0xFF` 다. 다른 칩이면
`--chip chipNN` 으로 바꾸되 그 칩의 tally 가 비어 있어야 한다 — 비어 있지 않으면 엔진이 `E_DIRTY`
로 거부한다(§4 「재시험」).

## 1. A 시험 — 100사이클

보드 USB · JP5=JTAG · chip01 장착 · 포트 `/dev/ttyUSB1`.

```bash
uv run python host/run/run_wear.py uid --port /dev/ttyUSB1     # 읽기 전용 — 소켓의 칩이 chip01 인지
uv run python host/run/run_wear.py accept --port /dev/ttyUSB1 --chip chip01 \
    --base-sector 1000 --cycle 0 --to 100
```

`accept` 가 하는 일, 순서대로:

1. `program_g2.tcl` — `rst -system` → g2 비트스트림 → `flash_wear.elf`. 엔진은 SPI → JEDEC(EF 40 17)
   → UID 3회 일치로 부팅해 `idle` 로 앉는다. 배너는 없다. 실패하면 `error` 로 앉고 `accept` 는
   START 를 보내지 않는다
2. UID 를 등록부와 대조. 다르면 아무것도 하지 않는다
3. `WEAR START base=1000 n_sectors=7 pattern=0x00 cycle=0 delta=100 session=<epoch>`. 엔진은 tally
   두 벌을 읽어 `E_DIRTY`·`E_CYCLE` 을 본 뒤에야 `OK` 와 `#WEAR H` 를 낸다
4. 100사이클 — 사이클마다 섹터 1,000~1,006 의 112페이지에 `0x00` 프로그램(섹터당 16페이지 WIP 합 =
   `t_program_us`), 7섹터 소거(각 WIP = `t_erase_us`), 카운터 +1, `#WEAR A` 7행 즉시 출력.
   100번째만 다르다: 프로그램 직후 읽기(`program_fail_bits`) → 소거 → 소거 직후 읽기
   (`erase_residual_bits`) → UID 재확인 → tally 두 벌에 `0x00` 1바이트 → A 7행 → `#WEAR B` 1행 →
   `checkpoint_due`. 이후 명령 없이는 P/E 도 출력도 없다
5. STATUS·TALLY·DUMP 를 읽어 판정하고 `docs/chip_pe.md` 에 `1000~1006 +100` 행을 붙인다

사이클당 약 0.5초(프리스케일러 64)라 1분 안쪽이다. 터미널에는 START 문자열과 마지막 9줄의
PASS/FAIL 이 보인다. 종료 코드 0 = 전부 PASS, 1 = FAIL 있음, 3 = 중단(거부·UID 불일치·타임아웃).

## 3. 읽는 법

판단은 두 층이다. **시험 자체가 유효한가**를 먼저, **기준을 통과했나**를 그 다음.

### 3.1 유효성 — 이것이 서야 숫자를 읽는다

- `commands.txt` 에 `REJECT` 가 없고 START 의 `OK` 가 여섯 인자를 그대로 되돌렸다
- `verdict.txt` A2 줄의 「깨진 행 0」. 깨진 행 = 체크섬 실패 = UART 손상이고 세지 않았다
- H 행 `chip_id` 가 등록부와 같고 B 행 `uid_ok=1`. 도중에 칩이 바뀌거나 접촉이 튀지 않았다
- `R.txt` 가 없다. 사건이 있었으면 완주가 아니다
- state 가 `checkpoint_due`. `error`·`halted` 는 완주가 아니다

### 3.2 A5 가 원인을 가른다

A5 는 네 경로(카운터 · A행수÷7 · B 의 cycle · tally×100)가 전부 100 인지 본다. 어긋나는
조합이 「누가 틀렸나」를 말한다.

| 어긋남 | 뜻 | 다음 |
| ------ | -- | ---- |
| 카운터 100 · tally 100 · A 행 < 700 | 칩·엔진은 정상, UART 가 행을 잃었다 | 호스트 쪽. `raw.txt` 의 결측 구간 확인, 재시험(§4) |
| 카운터 100 · tally 0 · A 700 | 엔진은 돌았는데 tally 가 안 써졌다 | `dump` 로 확인. 쓰기 보호(BP)·tally 섹터 |
| 카운터 < 100 · `R.txt` 있음 | 정지 사유대로 | `wip_timeout` = 2초 안에 WIP 미해제 → 칩·배선·전원. `*_fail` = 결함 비트 > 4,588 |
| tally 두 벌 불일치 | 한 벌만 써졌다 | 완주한 시험에서 나오면 안 된다. `dump` 로 어느 벌인지 |
| 전부 100, B 의 `cycle` 만 다름 | 검사 사이클 계산 오류 | 엔진 버그 — 칩 탓이 아니다 |

### 3.3 칩의 물리 — A6 와 B 행

- `t_erase_us`: typ 45,000 부근, 400,000 이상이면 A6 FAIL. 2026-09-15 chip02 신품 소거가 26.4ms 였으니
  그 근처면 정상. **값이 정확히 4배 작으면** `COUNTS_PER_SECOND` 괄호 함정, **전부 0 이면** 글로벌
  타이머 미enable — 둘 다 엔진 문제다 (`ps/src/wear_plat_zynq.c`)
- `t_program_us`: 16페이지 WIP 합. tPP 0.7ms 기준 11,000 안팎. SPI 클럭과 무관해야 한다
- B 행 `erase_residual_bits`·`program_fail_bits`: 신품 100사이클의 정답은 둘 다 0. 0 이 아니면
  `e_addrs`/`p_addrs` 에 `페이지:바이트:비트`. 문턱 46·459·4,588 은 각각 θ=10⁻⁴·10⁻³·10⁻² 무효
  (S-1 §10). 100사이클에서 0 이 아니면 마모가 아니라 배선·전원·접촉을 먼저 본다
- `dump`: tally 에 `0x00`·`0xFF` 외의 값이 있으면 부분 프로그램(S-1 §8.5 파일럿 확인 항목)

**B 행의 0 은 정보가 없다.** 「제대로 재고 0」과 「세는 경로가 죽어서 0」이 같아 보인다. 그것을
가르는 것이 verdict 의 마지막 줄 `probe` 다 — `accept` 가 멈춘 직후 `BLANK` 를 불러(읽기 전용) 마지막
동작인 소거 뒤의 `0xFF` 를 패턴 `0x00` 과 대조하면 **`program_fail_bits=229,376`**(7섹터 전 비트)이
나와야 한다. 화재경보기의 시험 버튼이다 — 일부러 울려서 경보기가 살아 있는지 본다. `probe` 가 FAIL
이면 B 행의 0 은 읽지 않는다(2026-09-21 추가, 이전엔 mock·sim 채점에만 있었다).

> **본 마모로 넘어가기 전에 `tally-erase` 를 한 번 한다** (S-1 §8.1 실험 개시 소거). 이 시험이 tally 에
> 남긴 마크는 TB 영역의 마모인데, tally 는 영역을 구분하지 않으므로 그대로 두면 마모 그룹의 x축이
> 그만큼 밀린다. 실행기가 그 상태를 감지하면 START 전에 멈추고 이 절차를 가리킨다.

## 4. 재시험

A 시험이 완주하면 tally 에 `0x00` 이 한 바이트 남는다. 같은 칩에 `--cycle 0` 으로 다시 돌리면
엔진이 `E_DIRTY` 로 거부한다 — 재개를 신규로 착각해 X축을 지우는 것을 막는 자물쇠다.

- **이어 돌리기**: `accept --base-sector 1000 --cycle 100 --to 200` 은 받는다 (`--cycle` 을 빼면 칩의 tally 에서 잇는다). 판정은 **구간 기준**이라 9줄이
  그대로 선다 — A2·A3·A5 의 행 수는 이 세션이 본 것만 세고(기준도 이 구간), A1·A4 는 칩이 들고 있는
  누적(카운터·tally)을 본다. 구간 끝이 100의 배수가 아니면 A5 의 tally 경로는 그 아래 100 단위로
  본다(tally 는 100마다 1바이트). 결함이 보인 뒤에는 검사 주기가 10 으로 조밀해지므로 A3 는
  「기대치 이상」으로 받는다 (2026-09-22)
- **처음부터**: tally 두 벌을 지운다 — `tally-erase` (2026-09-21 추가, S-1 §8.1 의 「실험 개시 소거」).
  열쇠가 무겁다: 실행기가 지울 값과 `chip_pe.md` 이력을 보여 준 뒤 **그 칩의 UID 를 직접 타이핑**해야
  하고(y/n 이 아니다), 지우기 전 값을 장부에 512·1,536 `+1` 두 행으로 먼저 적은 뒤에야 엔진에
  `TALLY_ERASE uid=…` 를 보낸다. 엔진은 `idle`(리셋 직후)에서만, UID 가 소켓의 칩과 같을 때만 받는다

```bash
uv run python host/run/run_wear.py tally-erase --port /dev/ttyUSB1 --chip chip01 --i-approve-tally-erase
#   UID> D1654CB09B352233        ← 사람이 친다. 출력 마지막 줄 clean=1 이어야 한다
```

  `clean=0` 이면 소거 뒤에도 `0xFF` 가 아닌 것이고 엔진은 `error` 로 앉는다 — 쓰기 보호(BP)·배선을
  본다. 그 뒤 `accept --cycle 0` 이 다시 열린다

## 5. B 시험 — 전원 차단 복구

TB 영역만 닳린다 (S-4 §9 — 50회를 돌려도 목표의 1.7%).

```bash
uv run python host/run/run_wear.py accept --port /dev/ttyUSB1 --base-sector 1000 --cycle 100 --to 300
#   … 사이클이 도는 중에 보드 전원을 뽑는다 (소거 중을 노리려면 여러 번)
uv run python host/run/run_wear.py resume --port /dev/ttyUSB1 --from-session build/logs/wear/<위 세션>
```

`resume` 이 밟는 것 (S-1 §8.3): UID 대조 → RESUME(tally 두 벌 원본·다음 바이트·`write_ok`) →
`decide_resume` → BLANK → 잔류가 있으면 REERASE → BLANK 재확인 → **채택값 출력. START 는 보내지
않는다.**

| 출력 | 뜻 |
| ---- | -- |
| `판정 normal / tally_late / uncertain` | 정상 차단. 채택값이 뒤에 온다 |
| `판정 host_died` | 호스트가 먼저 죽었다 — tally×100 채택, 결손 구간 기록 |
| `판정 halt_call_human` | 두 벌 차이 > 100 · `write_ok=0` · tally 소진 — 사람이 본다. 종료 코드 2 |
| `blank_check 잔류 N` (N>0) | 소거 중 차단의 부분 소거. `reerase ok=1 … 재확인 잔류 0` 이 따라와야 한다 |
| `재소거 뒤에도 잔류` | 사람이 본다 — 자동 재시도는 없다 |

통과 = 채택값이 실제 진행과 100 이내이고(칩은 모르지만 A 로그 최대 cycle 과 tally 로 가늠),
잔류가 있었으면 재소거 뒤 0, 그리고 아래로 이어 완주:

```bash
uv run python host/run/run_wear.py accept --port /dev/ttyUSB1 --base-sector 1000 --cycle <채택값> --to <목표>
```

`chip_pe.md` 에는 재소거한 섹터 하나가 증분 `±1`, 비고 「reerase · ±1」로 남는다.

## 6. 프리스케일러 실측 (로그 44 `[U44-7]`)

§1 의 A 시험(64)에서 `t_erase_us` 분포와 A 행 `ts` 간격(사이클 시간)을 얻는다. 그 뒤:

```bash
WEAR_SPI_PRESCALE=16 vitis -s ps/scripts/build_flash_wear.py
uv run python host/run/run_wear.py accept --port /dev/ttyUSB1 --base-sector 1000 --cycle <현재> --to <현재+100>
```

`t_program_us`·`t_erase_us` 는 WIP 만 재므로 **같아야** 하고 `ts` 간격만 줄어야 한다. 어긋나면
EMIO·점퍼선 경로 문제이니 64 로 남긴다. 8 은 16 이 깨끗할 때만 같은 방식으로. 값은 사람이 고른다.

## 7. 그 밖의 명령

```bash
run_wear.py status   # cycle · state · defect_seen · last_reject
run_wear.py halt     # 다음 사이클 경계에서 halted — 이어 가려면 accept --cycle <표시된 값>
run_wear.py tally    # 두 벌의 0x00 바이트 수
run_wear.py dump     # 두 벌 4,096B 를 hex 파일로, 0x00/0xFF 외 값 목록
run_wear.py uid
run_wear.py tally-erase --i-approve-tally-erase   # §4 「처음부터」 — UID 를 타이핑해야 지운다
```

`running` 중에 보내도 되는 것은 `HALT`·`STATUS` 뿐이다 — RX FIFO 가 64B 라 START(약 110B)는
넘친다. 호스트는 응답을 받은 뒤에만 다음 명령을 보낸다.

## 8. 이 런북이 닫지 못하는 것

- C 의 실칩 절반 — 근접(7)·원격(2,041) 스윕은 RTL 에 `BASE_SECTOR` 가 없다 (`[U44-8]`)
