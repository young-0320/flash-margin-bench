## N. 예상 노화 이동량 Δ — G5 ②의 분자가 없다

**G5 ②는 *"노이즈 플로어가 예상 노화 이동량 대비 충분히 작음을 수치로 확인"* 이다**
(`project_context.md` §260). 2026-09-20 에 분모는 확보됐다 — σ_repeat = **13.86ps**
(chip10 재장착 3회, 집계표 §6). **그런데 분자가 문서 어디에도 수치로 없다.**

분자가 없으면 "충분히 작다"를 판정할 수 없고, 게이트가 통과도 실패도 못 한 채 열려 있다.

정할 것: **300k 사이클에서 width 가 몇 ps 움직일 것으로 보는가.** 후보 세 가지.

| 후보 | 방법 | 한계 |
| ---- | ---- | ---- |
| 선행 연구·데이터시트 | NAND/NOR 마모 문헌의 t_R 열화율에서 환산 | W25Q64JV 의 SPI 읽기 경로 타이밍으로 곧장 옮겨지지 않는다 |
| **파일럿 chip01 의 초기 체크포인트** | 0 · 300 · 645 사이클을 먼저 태우고 실측 기울기로 외삽 | **마모를 시작해야 알 수 있다** — 게이트가 요구하는 값을 게이트 통과 후에야 얻는 순환 |
| 하한만 정한다 | "σ_repeat 의 10배(≈140ps)보다 크면 실험이 성립한다"로 **판정 기준을 뒤집어 등록** | 실제 Δ 를 모르는 것은 그대로다. 다만 **사전 등록**이라 사후 해석은 막는다 |

**세 번째가 현실적이다.** 순환을 인정하고, "얼마나 움직일지는 모르지만 이만큼보다 작으면
실험이 성립하지 않는다"를 미리 적어 두는 쪽이다. 어느 쪽을 택하든 **마모 착수 전에 문서에
수치가 있어야 한다** — 데이터를 본 뒤 정하면 S-2 §6 이 금지한 사후 해석이 된다.

## C. 교차 시험 — 칩인가 배선인가

칩마다 배선이 따로이므로(S-2 §3.3) 지금까지의 「개체 산포」는 전부 **칩 + 그 배선**의 산포다.
배선이 핀헤더로 분리되므로 서로 바꿔 꽂아 가를 수 있다. 절차와 판정표는 **S-2 §8 말미**.

- **후보 쌍: chip07(벽 204.3ps) × chip10(벽 1,289.9ps).** 6.3 배 차이라 어느 쪽을 따라가는지
  분간이 쉽다. 차이가 작은 쌍을 고르면 결론이 안 난다
- 스윕만 하므로 **P/E 불변**, 2런 약 10분
- **전수조사를 닫는 데는 불필요하다** — 인수 기준 어디에도 이 구분이 없고, 집계표에 단서로
  달아 두었다. 필요해지는 시점은 **개체차를 주장할 때**(최종보고서·블라인드 추정 근거)다
- 결과에 따라 S-2 §9 산출물 2「개체 산포 σ」의 정의를 다시 써야 할 수 있다 (로그 43 `[U43-7]`)

### B. `reproduce.py` 후속 — 무엇이 남았나

**① 닫혔다 (2026-09-16).** g0·g3 의 Vivado 전체 경로를 맨바닥에서 2회 돌렸다 — 8단계
**8/8 PASS · FAIL 0 · WARN 0**, 수치는 `build_reproduction.md` §3.5 기준값과 일치. 전체 약 9분
(문서의 "20분"은 2024.2 시절 값이라 정정했다). 로그 33 §3.

**② 검사 전용 모드(`--check-only`)는 출처 기록이 선행이다.** "빌드 없이 지금 `build/` 가
쓸 만한가"를 5초에 답하는 모드인데, **mtime 으로는 제대로 못 판정한다**:

- `git checkout`·`pull` 이 내용과 무관하게 mtime 을 갱신한다 → 멀쩡한 빌드가 stale 로 뜨고
  사람이 경고를 무시하기 시작한다
- 입력 목록(RTL·xdc·tcl·C·빌드 스크립트)을 하나라도 빠뜨리면 **조용히 통과**한다
- **툴 버전은 파일이 아니다** — 2024.2 ↔ 2025.2 세대 혼합(chip01↔chip02 106ps 의 원인 후보)을
  mtime 은 영원히 못 잡는다

그래서 순서가 **출처 기록 → 검사 모드**다. 단계 성공 시 산출물 옆에 남긴다:

```
build/vitis_g3_45/.provenance
    built_utc · git_rev · git_dirty · tool(Vivado/Vitis 판번) · params · inputs_sha
```

이것은 새 발명이 아니라 **이 리포가 측정 데이터에 이미 쓰는 방식**이다 — CSV 의 `git_rev` 열,
`_prev/manifest.txt` 의 `git_rev_at_backup`. 빌드 산출물에만 없었다. 기록하는 주체는
`reproduce.py` 로 두면 `ps/scripts`·`fpga/scripts`(소유자가 다른 폴더)를 건드리지 않는다.
**③ 설계 논의는 2026-09-16 에 한 단계 진전됐고, 구현은 보류다.** 0단계(요약 머리말에 신원
한 줄)와 입력 내용 해시를 시제품까지 만들어 동작을 확인한 뒤 되돌렸다 — Windows 경로(세은 확인)가
먼저이고, **보존처가 안 정해졌기 때문**이다. `build/` 는 gitignore 라 요약이 증발한다(실제로
겪었다). 재개 시 정할 것: 0·1·2 중 어디까지인가, 어디에 남기는가. 근거와 실험 결과는 로그 33 §4 —
특히 **rev 만으로는 문서 커밋에도 값이 바뀌어 거짓 불일치가 난다**는 것과, **입력 해시 × 결과
수치의 2×2 로 원인(소스 차이 / 환경 차이)이 갈린다**는 것.

손으로 빌드하면 기록이 없을 텐데, 그때는 **"기록 없음"으로 판정**한다 — 모르는 것을 모른다고
말하는 편이 틀린 확신보다 낫다(`chip_pe.md` 의 `미상(≥1)` 과 같은 자).

### L. 로그 서식 규약 — 확정 (2026-09-17)

**닫혔다.** 규약은 `docs/log/FORMAT.md` 다(2026-09-17 분리, 로그 39). 근거 — 전 로그 계측,

정한 것만 옮겨 적으면:

- **로그는 다른 문서가 가질 수 없는 것만 담는다** — git · `results/` · `workflow/` 가 답할 수
  있으면 쓰지 않는다. 절차·측정 수치·파일 목록·작업 실적이 이 선에서 나간다
- **골격 다섯** — 머리말 → `## 결정` → `## 근거` → `## 산출물` → `## 미결`
- **머리말** `작성일 · 발단 · 목적 · 관련` (+ 측정일이 작성일과 다르면 `측정일`). `목적` 은
  질문이고 `## 결정` 이 답이다. `작성`·`성격` 은 뺀다 — 폴더와 `발단`·`목적` 이 이미 답한다
- **뒤집힌 결정은 그 자리에 인용구.** 목차형 정오표를 두지 않는다 (로그 36 §5 가 실물)
- **적용은 새 로그부터.** 기존 34편은 소급하지 않는다. 본인 로그에는 강제, `jimin/`·`seeun/`
  에는 제안이다 — 그래서 자리가 `CONTRIBUTING.md` 가 아니라 로그 폴더의 README 다

폐기한 처방 둘: 볼드 `100줄당 5개` 상한(세는 법이 분류기마다 달라 기준선이 안 선다 — 문단당
하나라는 습관 규칙으로 대체), 헤더 항목 "한쪽으로 통일"(로그 28~36 이 이미 수렴해 있어 고를
문제가 아니었다).
