  하루를 더 쓸 가치가 없다. 대신 7월 게재 수치의 유래 md에 "Vivado 2024.2 빌드" 한 줄을
  달고, 9/15 이후 수치는 2025.2 빌드로 표기한다 — 두 세대를 한 표에 놓을 때 각주로 구분.
- **성격**: 7/7 운영 결정("공유 편집이 필요해지면 그때 2025.2로 통일")의 **실행**.
  워크플로 5의 M 트랙(신품 전수 측정, 실행 장세은)은 **이 문서가 닫힌 뒤에** 시작한다.
- **왜 지금인가**: 조원이 각자 PC에서 루프백·실칩 측정을 돌리려면 빌드 산출물이
  필요한데 `build/`는 커밋하지 않는다(CONTRIBUTING §1). 산출물 복사보다 **각자 빌드**가
  재현성이 높다 — 소스는 tcl·RTL·XDC·벤더링 보드파일(`fpga/boards/`)로 완결돼 있고,
  막는 것은 2024.2 버전 가드(tcl 3곳)뿐이다. 조원은 2025.2를 쓴다.
- **핵심 제약**: **비트스트림이 곧 계측기다.** Vivado 버전이 바뀌면 배치·배선이 바뀌고
  MMCM 위상 기준점·왕복 지연(PAY_LEAD)이 움직일 수 있다. 게재된 7월 수치(README
  §결과)는 전부 2024.2 비트스트림이다. 빌드 세대가 바뀌는 사실은 유래 md와
  각주로 남긴다(위 결정).
- **가드는 지우는 것이 아니라 옮기는 것**: 가드의 역할은 "돌게 하기"가 아니라 "팀이
  한 버전만 쓰게 강제하기"다. 지우면 영웅 2024.2 / 조원 2025.2로 계측기가 둘이 된다.
  `2024.2*` → `2025.2*` 로 바꿔 다시 잠근다.

## W8-I. 병렬 설치 (한영웅)

**병렬 설치는 서로를 건드리지 않는다.** Xilinx 툴은 버전별 폴더에 독립으로(2024.2는 `~/Xilinx/<툴>/2024.2/`, 2025.2부터는 `~/Xilinx/2025.2/<툴>/` — 설치기 구조가 바뀌었다)
들어가고 전역 환경변수를 만들지 않는다. PATH에 오르는 것은 그 셸에서 `settings64.sh`를
source한 버전뿐이다. 공유되는 것은 케이블 드라이버와 `~/.Xilinx/` 설정 폴더인데 둘 다
버전 간 호환된다.

```
I1. 설치: Vivado 2025.2 + Vitis 2025.2 (Zynq-7000 디바이스 패밀리만 체크 — 용량 절감)
    설치 루트 ~/Xilinx → ~/Xilinx/2025.2/Vivado, ~/Xilinx/2025.2/Vitis (2024.2와 다른 배치)
    2024.2 툴은 2025.2 첫 빌드(B2 g0)가 통과한 뒤 삭제해도 된다 (R 생략 결정, 53GB 회수)
I2. 검증: 새 셸에서
    source ~/Xilinx/2025.2/Vitis/settings64.sh
    vivado -version | head -1      # "Vivado v2025.2"
    xsct -eval 'puts [version]'    # 2025.2
    vitis -s /dev/null 2>&1 | head -3   # 파이썬 CLI가 뜨는지 (B의 최대 위험 지점 사전 확인)
I3. 셸 규율: 프로젝트 작업 셸은 **하나의 버전만** source한다. 두 버전을 한 셸에서 연달아
    source하지 않는다 (PATH 앞뒤가 섞인다). 확인은 항상 `which vivado`.
```

동시 사용: 셸 A(2024.2)·셸 B(2025.2)는 동시에 돌 수 있다. 단 저장소의 `build/`는
하나라서 **두 버전이 같은 `build/`에 쓰면 섞인다** — B에서 처리한다.

## W8-B. 가드 이전 + 전 산출물 재빌드 (한영웅)

```
B0. 2024.2 산출물 제거 (보존하지 않기로 결정 — 위 헤더):
    rm -rf build
B1. 가드 이전 — 세 tcl의 "2024.2*" → "2025.2*", 에러 문구도 같이:
    fpga/scripts/build_g0_loopback.tcl · build_g2_jedec.tcl · build_g3_chip.tcl
    호스트 쪽 안내 문구 1곳: host/run/run_sweep_chip.py:172 "Vitis 2024.2" → "2025.2"
    로그 8·9의 "2024.2" 언급은 당시 기록이므로 손대지 않는다
B2. 빌드 (2025.2 셸, 순서대로 — 각 단계는 다음 단계의 XSA를 만든다):
    vivado -mode batch -source fpga/scripts/build_g0_loopback.tcl            # g0 (bit+XSA+ELF)
    vivado -mode batch -source fpga/scripts/build_g2_jedec.tcl               # g2 (+ flash_jedec ELF)
    vitis -s ps/scripts/build_flash_prep.py                                  # prep ELF (g2 XSA 소비)
    vivado -mode batch -source fpga/scripts/build_g3_chip.tcl -tclargs all 25
    vivado -mode batch -source fpga/scripts/build_g3_chip.tcl -tclargs all 45
    vivado -mode batch -source fpga/scripts/build_g3_chip.tcl -tclargs all 75
    보험 비트(pl4·pl6)는 R에서 PAY_LEAD가 어긋났을 때만 굽는다 (-tclargs bit 25 <k>)
B3. 검증: 산출물 존재 + 타이밍
    ls build/vivado/g0_loopback.runs/impl_1/g0_wrapper.bit build/vitis/g0_sweep/build/g0_sweep.elf
    ls build/vivado_g3_{25,45,75}/g3_chip_*.runs/impl_1/g3_wrapper.bit
    ls build/vitis_prep/flash_prep/build/flash_prep.elf
    grep -l "All user specified timing constraints are met" build/vivado*/*.runs/impl_1/*_timing_summary_routed.rpt
    → 6개 전부 met. 하나라도 위반이면 9/15 측정 금지 (2024.2에서는 전부 met였다)
```

**위험 지점**: `vitis -s`(unified Vitis 파이썬 API, `vitis.create_client` · `create_platform_component`
등)가 2025.2에서 시그니처가 바뀌었을 수 있다. 깨지면 그 자리에서 고치고 로그 28에
차이를 적는다. 로그 9의 SDT 플로우 주의(`LookupConfig`가 DEVICE_ID가 아니라 BASEADDR)는
2025.2도 동일하다.

## W8-R. 재기준선 A/B — **생략 (2026-09-14 결정)**

원래 설계: 칩·점퍼를 두고 2024.2 비트(A)와 2025.2 비트(B)를 교대로 6회 재서 빌드 차이만
분리한다(재장착 편차와 섞이지 않게). 예상 차이가 수 ps라 하루를 더 쓰지 않기로 했다.
남는 의무는 기록뿐이다:

- `docs/results/data/`의 7월 유래 md 3개(`sweep_loopback_20260708…`, `sweep_chip01_20260708…`,
  반복 5회)에 "빌드: Vivado 2024.2" 한 줄 추가. 9/15 이후 유래 md에는 "빌드: Vivado 2025.2".
- 9/15 값이 7월 값과 재장착 편차 이상으로 다르면, 그 차이에는 빌드 세대 변경이 섞여 있을 수
  있다는 것을 로그에 적는다. 분리가 필요해지면 그때 2024.2 산출물을 다시 빌드해 A/B한다
  (소스·tcl은 그대로 있으므로 재현 가능. 단 2024.2 툴 재설치 필요).

`program_g0/g3.tcl`의 `BUILD_DIR` 환경변수는 그대로 둔다 — 기본값이 `build`라 무해하고,
나중에 A/B를 하게 되면 그대로 쓴다.

## W8-T. 조원 PC 전개 (장세은 · 박지민)

B 완료 후. **조원이 따라 할 문서는 `docs/build_and_run_guide.md`** (목차·단계별 명령·기대 출력). 아래는 요약.

각자 PC에 필요한 것은 네 가지다.

| 준비물 | 내용 | 확인 명령 |
| ------ | ---- | --------- |
| Vivado + Vitis **2025.2** | 빌드(vivado, vitis -s)와 프로그래밍(xsct). Lab Edition만으로는 빌드 불가 | `vivado -version`, `which xsct` |
| uv 환경 | CONTRIBUTING §1.5. 리포 루트에서 `uv sync` 1회 | `uv run python host/analysis/bathtub_analysis.py --selftest` |
| 저장소 클론 | `build/`는 없다 — **직접 빌드한다** | HEAD 가 가드 2025.2 커밋 이후 |
| 보드 + UART 포트 | Zybo Z7, USB 1개(JTAG+UART), JP5=JTAG. 리눅스: `dialout` 그룹 + `/dev/ttyUSB1`. Windows: 장치 관리자에서 부모가 "USB Serial Converter **B**"인 COM → `--port COM<N>` (로그 13) | 캡처 후 프로그래밍하면 BEGIN이 수 초 내 뜬다 |

```
T1. 빌드 (각자, ~수십 분):
    source <설치루트>/2025.2/Vitis/settings64.sh   # 2025.2 배치: <루트>/2025.2/<툴>
    vivado -mode batch -source fpga/scripts/build_g0_loopback.tcl
T2. 루프백 1회 (점퍼 JE1↔JE2):
    [터미널 1] uv run python host/capture/sweep_uart_capture.py --loopback [--port COM<N>]
    [터미널 2] xsct ps/scripts/program_g0.tcl
    uv run python host/analysis/bathtub_analysis.py build/data/sweep_loopback_<stamp>.csv
T3. 판정: valid=1 + 체크리스트 통과 + width@1e-2 가 영웅 PC의 R-L B값과 같은 자릿수(±수백 ps —
    점퍼·접촉 차이가 이 정도라는 것이 로그 22의 교훈). 이 값은 "PC가 다르다"가 아니라
    "점퍼가 다르다"를 재는 것이므로 정밀 비교는 하지 않는다
T4. 실칩(M 트랙)용 추가 빌드는 실행자(장세은)만:
    build_g2_jedec.tcl → build_flash_prep.py → build_g3_chip.tcl -tclargs all 25
    이후 명령은 워크플로 5 D1 (run_sweep_chip.py)
```

**빌드 재현성 확인 (선택)**: `.bit`는 헤더 시각 때문에 md5 비교 불가. 가이드 §3의 WNS·자원 수치 비교로 대신한다.
