# 시료 등록부 (W25Q64JV — 1차 ×10 + 추가 구매분, 라벨 chip01~chip20)

Updated: 2026-10-06

칩 개체의 **정본 식별자는 하드웨어 Unique ID**다. 사람이 부르는 라벨(chip01 등)은 편의를
위한 별칭이며, 라벨과 데이터가 어긋나면 **UID가 진실**이다.

- **UID**: `4Bh` Read Unique ID Number — 공장에서 새긴 개체별 읽기 전용 64비트
  ("a factory-set read-only 64-bit number that is unique to each W25Q64JV device")
- **JEDEC ID**(`9Fh` → `EF 40 17`)는 모델 식별자라 10개가 전부 동일하다. **개체 식별 불가.**

  **판정 (2026-10-06, chip10 판독 — 한영웅)**: chip10 은 `25Q64JVSIQ` `1850` — 「1430 이후」 는 맞았지만 **FV 가 아니라 JV** 였다.
  「chip10 · 14 같은 로트」 는 확인 후 작성 예정.
  위 「날짜 코드와 무리가 갈린다」 는 FV 칩들의 이야기라 chip10 에는 쓰지 않는다
- 날짜 코드 `1309` 는 2013년 생산으로 읽힌다. 모듈이 오래된 재고 칩을 얹었다는 뜻이고, **「신품」 은 「우리가 받기 전 사용 이력을 모른다」 는 뜻**이다 —
  재생 칩일 가능성까지 배제하지는 못한다. 신품 측정에서 마모 섹터(0-6)와 기준 섹터(32-127)의 소거 시간이 같은지가 그 점검이다
- **점검 결과 (2026-10-05)**: 칩마다 첫 신품 newchip prep 의 소거 중앙값 비 0-6 ÷ 32-127 이 **0.96-1.04**, 7-31 ÷ 32-127 이 0.98-1.05 (15칩).

  없고, 느린 무리는 수백 사이클 이하를 가려낼 힘이 없다. 칩 전체가 고르게 쓰였다면 이 비로는 보이지 않는다(기준 섹터도 같이 닳으므로)

**2026-10-05 — chip07 만 점퍼선이 20cm 였다 (다른 칩은 10cm).** 칩마다 배선이 한 벌이라(S-2 §8) chip07 의 폭 측정은 다른 칩과 조건이 다르다 — chip07 의 폭 이동(세션 사이 −440ps · 계측 사건 +590ps)을 읽을 때 이 조건을 같이 본다. 소거 · 프로그램 시간은 칩 내부 동작이라 선 길이의 영향을 거의 받지 않는다.

**2026-09-30 — 라벨 상한을 chip20 까지 열었다** (칩 추가 구매). 새 칩은 `--mode newchip` 이 UID 를 읽고 다음 빈 라벨(chip11~)을 물어 행을 추가한다. chip05 행은 죽은 칩의 자리라 새 칩에 주지 않는다. 추가분의 개수·용도는 S-2 §1 배분표에 아직 없다.

## 기입 절차

1. `flash_prep` 실행 시 출력되는 `#PREP UID <16hex>` 를 읽는다
2. 이 표에 UID를 기입한다. **최초 1회만** — UID는 불변이다. `host/run/run_sweep_chip.py`가
   `#PREP UID`를 받아 공란 행을 자동으로 채운다 (`host/capture/chip_registry.py` — 공란 채우기·행

3. P/E는 이 표에 적지 않는다. `docs/chip_pe.md`에 작업마다 증분 행이 append 된다
   (블라인드 칩은 `--blind`로 증분을 `(MASK)` 처리 — 절차는 미설계, 로그 23 부록 D)

## 새 데이터 규칙 (2026-08-20 이후 · 2026-09-07 정정)

모든 chip 측정 CSV는 **`uid` 열**(전 행 반복)과 **파일명 `sweep_<label>_<uid16>_<stamp>.csv`**
에 UID를 갖는다 (계약 수정안 #3, `docs/interface/amendments/3.uid_pipeline.md`). 수집 경로:

- `flash_prep`이 `#PREP UID <16hex>` 출력 (PS SPI 경로, `4Bh`, 3회 일치)
- `host/run/run_sweep_chip.py`가 UART를 계속 쥔 채 그 값을 받아 이 표에서 라벨을 역조회하고,
  `host/capture/sweep_uart_capture.py`에 넘긴다. **캡처는 UID 없이 chip CSV를 만들지 않는다**

(정정: 종전에는 "CSV 헤더에 `#UID <16hex>` 주석 행"으로 적었으나, 주석 행은 `csv.DictReader`가
헤더로 읽어 분석이 통째로 깨진다. 열 방식으로 바꿨다 — 로그 23 §8.)

스윕 중에는 PS가 칩과 직접 통신할 수 없으므로(스윕은 PL 경로, prep은 PS SPI 경로) UID와
스윕의 연결은 **같은 세션**이라는 절차적 근거에 의존한다. 세션 중간에 칩을 교체하지 않는다.
PL에서 UID를 직접 읽어 헤더에 박는 완전 자동화는 계약 변경 안건이다(BASE_SECTOR와 묶음).

## 누적 P/E의 정본

등록부의 `누적 P/E` 열은 **값을 갖지 않는다** — 값을 두 곳에 두면 어긋난다. 호스트 측 기록은
`docs/chip_pe.md`의 **증분 이력**(append-only, 누적은 읽는 쪽이 합산)이고, 정본은 **칩 자신의
이력(tally) 섹터**에 있다(`docs/workflow/5.*` 전원 장애 복구 절). 이력과 칩 tally가 어긋나면
**칩이 진실**이다 — UID와 같은 원칙이다. 칩은 자기가 누구인지(UID)와 얼마나 살았는지(tally)를
스스로 들고 다닌다. 등록부는 **불변 사실**(UID·라벨·최초 측정)만 사람이 관리한다.
