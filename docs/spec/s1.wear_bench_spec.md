## 1. 1사이클 정의

| 항목       | 값                                                                                                             |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| 구성       | ① 0x00 프로그램 112페이지 → ② 7섹터 소거                                                                    |
| 마모 패턴  | **파라미터** (`WEAR_PAT_EVEN`/`WEAR_PAT_ODD` 레지스터 2개). **파일럿 고정값 `0x00`** — 아래 |
| 시간 (typ) | 7 × 45ms + 112 × 0.8ms =**405ms**                                                                      |
| 계수       | 프로그램+소거 1쌍 = 1사이클. 체크포인트의 소거+PRBS 기록도 1사이클이지만 **영역별 누적**(§9 C `area_cumulative_cycles`)에만 넣는다 — 엔진의 사이클 카운터(§13 A1)는 **마모 루프만** 센다 |

> **2026-09-18 개정 — 마모 패턴은 파라미터(옵션화하여 패턴 선택할 수 있도록)다.** 2026-09-15 3인 회의에서 체커보드
> (`0x55`/`0xAA` 교대)도 **채택**해 본 실험은 여러 패턴으로 읽고 쓴다. 다만
> **파일럿은 마모 그룹이 하나뿐(§2.1)이라 패턴도 하나**이고 `0x00` 으로 확정했다
> (2026-09-18, 한영웅). 레지스터 설계와 "한 wear 그룹 안에서 패턴 변경 금지"는
> `docs/log/young/29.pe_engine_layer_decisions.md` `[D29-7]`.
>
> **2026-09-18 개정 — 세는 자리를 가른다** (한영웅). 체크포인트의 소거+PRBS 도 마모라는
> **사실은 그대로**이고, 그것을 **카운터가 아니라 영역별 누적에 기록한다.** §13 A5 가
> 「카운터 · A 로그 행수÷7 · B 의 cycle · **tally×100** 이 전부 100」을 요구하는데 tally 는
> 마모 루프 100사이클마다 1바이트이므로(§8.1), **카운터가 체크포인트까지 세면 A5 가
> 성립하지 않는다.** §13 은 이미 마모 루프를 전제로 쓰여 있었고 이 표의 계수 문구만
> 그것을 안 갈라 두었다. 경위는 `docs/spec/s4.blackbox_tb.md` §5.1 제안-8.
>
> **보류 둘** (2026-09-18, 한영웅).
> ① **본 실험 3그룹(§2.2)에 패턴과 목표 사이클을 어떻게 배정하나** — 축이 둘인데 그룹이
> 셋이라 하나를 고정하거나 그룹을 늘려야 한다.
> ② **패턴 간 비교를 사이클 수로 맞추나 누적 1→0 전이 수로 맞추나** — `0x00` 은 셀당

```

섹터   512           tally #1       측정 안 함
```

### 2.2 본 실험 (잠정 — §15 파일럿 후 확정)

```
섹터     0 ~     6   마모 그룹 1    BASE_SECTOR = 0
섹터     7 ~    13   마모 그룹 2    BASE_SECTOR = 7
섹터    14 ~    20   마모 그룹 3    BASE_SECTOR = 14

섹터   512 / 1,536   tally ×2       측정 안 함
```

**그룹 수·그룹별 목표 사이클·그룹별 패턴은 미정** (§1 개정 주석 · §15).

### 2.3 영역 규칙

| 영역                | 크기              | 소거 반복         | 스윕 측정 | PRBS 기록                |
| ------------------- | ----------------- | ----------------- | --------- | ------------------------ |
| 마모 그룹           | 7섹터 = 112페이지 | O                 | O         | 체크포인트마다           |
| 대조군 (근접·원격) | 7섹터             | X                 | O         | **체크포인트마다** |

```
1. UID 읽기 (4Bh) → 등록부 대조. 미등록이면 중단
2. tally 섹터 2개 소거 → 전체 0xFF 확인

6. 체크포인트 0 측정
```

## 6. 마모 루프

```
반복 {
    ① 0x00 프로그램 112페이지          → t_program_us 기록
   ①' 검사 주기 사이클이면 여기서       → program_fail_bits (§7)
        112페이지를 읽어 기대 패턴 대조     ※ 소거 전이라야 한다
    ② 7섹터 소거                        → 섹터별 t_erase_us 기록
    ③ 사이클 카운터 +1                  ※ 마모 루프만 센다 (§1)
    ④ 검사 주기 도달 시 (§7):
         - blank check (소거 직후 읽기 → erase_residual_bits)
         - tally 바이트 기록 (2벌 모두)
         - 다이 온도 읽기
         - UID 재확인
    ⑤ 체크포인트 도달 시 → 엔진은 멈추고 checkpoint_due (§5 는 호스트가 한다), 다음 체크포인트 산정 → §11
    ⑥ 이 사이클의 A 행 7개 출력 (검사 사이클이면 뒤에 B 행 1개)   ※ 매 사이클 실시간
}
```

> **2026-09-21 개정 — ⑥ 출력 단계를 넣었다 (S-4 §5.1 제안-6, 지민 회신 §4).** 종전 루프에는
> 출력 단계가 없어 A2 의 700행이 호스트에 닿는 경로가 문장에 없었다. 매 사이클 실시간이어야
> §8.3 의 `d` 규칙이 선다. ⑤ 의 「→ §5」는 엔진이 스윕을 부른다는 뜻이 아니다 — 엔진은
> `checkpoint_due` 로 멈추고 §5 는 호스트 도구가 한다 (`docs/interface/pe_engine.md` §2.1).

소거 시간은 **WIP 비트가 서 있는 구간의 지속시간**을 XTime으로 측정한다.

> **2026-09-19 개정 — 검사 사이클만 「프로그램 → 검사 → 소거」로 분기한다(①').**
> §7 은 `program_fail_bits` 를 *"프로그램 직후"* 에 재라고 하는데 이 루프는 검사를 ④
> 한 곳에 두어 **소거가 끝난 뒤** 였다. 그 시점엔 기대 패턴이 사라져 §7 의 그 줄이
> **실행될 수 없는 문장** 이었다 — 두 절이 어긋나 있었다. 읽기가 느는 것은 검사 주기
> (100사이클)뿐이고 나머지 99사이클은 그대로다.
>
> **그 사이클의 A 행 시간 정의가 달라진다.** ①' 의 읽기는 P/E 가 아니므로
> `t_program_us`·`t_erase_us` 에 **넣지 않는다** — 넣으면 A6(소거 시간)의 분포에
> 100사이클마다 한 번씩 튀는 점이 생긴다 (2026-09-19, 한영웅 · 로그 42 `[U42-3]`).

## 7. 무결성 검사 (blank check)

```
소거 직후    : 112페이지 읽기 → 0xFF가 아닌 비트    = erase_residual_bits
프로그램 직후: 112페이지 읽기 → 기대 패턴과 다른 비트 = program_fail_bits
```

| 항목          | 값                          |
| ------------- | --------------------------- |
| 기본 주기     | **100사이클**         |
| 조밀화 주기   | **10사이클**          |
| 조밀화 트리거 | 결함 비트**1회 검출** |
| 1회 비용      | 약 176ms (실측 확인 대상)   |

- 결함 비트의 **주소를 기록**한다. 초기엔 전량, 한 검사에서 64개 초과 시 처음 64개 + 총 개수
- 영구/일시 판정은 하지 않는다. 재현 횟수는 사후 분석에서 다룬다
- **두 숫자는 부를 때 실제로 읽어서 센다.** 마지막 결과를 캐시해 두지 않는다. 호스트는
  체크포인트(소거 직후)에 `blank_check` 를 불러 **세는 경로가 살아 있는지** 를 본다 —
  그 자리에서 `program_fail_bits` 의 정답은 `바이트 수 × popcount(~pattern)` (패턴 `0x00`
  이면 전량 229,376) 이다 (2026-09-19 추가 · 2026-09-21 정정)

> **2026-09-21 정정 — 합 불변식은 조건부다** (지민 회신 §5.1, 로그 44 `[D44-7]`). 종전 문장
> 「`erase_residual + program_fail = 전량` 이 항상 성립」은 **패턴 `0x00` 이고 두 값이 같은
> 읽기에서 나왔을 때만** 참이다. 기대 비트가 1인 자리에서는 두 값이 같은 것을 세므로 `0x55`
> 에서 깨지고, B 로그의 두 값은 프로그램 직후·소거 직후의 **서로 다른 두 읽기** 라 B 행에는
> 애초에 적용되지 않는다. 경로 점검은 위 `probe` 기대값으로 한다.

> **왜 이 한 줄이 필요한가.** 신품 100사이클에서는 `program_fail_bits = 0` 이 **정답** 이라,
> 「제대로 재고 0」과 「세는 경로가 죽어서 0」이 로그에서 같아 보인다 — 관측값이 정답과
> 같으면 그 관측에는 정보가 없다. 체크포인트(소거 직후)에 호스트가 blank check 를 부르면
> `program_fail_bits` 가 **전량** 이어야 하므로, 거기서 `0` 이 나오면 경로가 죽은 것이다.
> **정답에서 제일 먼 값이 나오는 자리** 를 일부러 고른 것이다 (로그 42 §8).

## 8. 카운트 영속화 (tally)

### 8.1 방식

| 항목          | 값                                                        |
| ------------- | --------------------------------------------------------- |
| 초기화        | 실험 시작 시 tally 섹터 2개를 각 1회 소거 → 전체`0xFF` (엔진 경계 10 `tally_erase` — `run_wear.py tally-erase`, 사람이 UID 를 타이핑해야 하고 지우기 전 값이 `chip_pe.md` 에 먼저 남는다) |
| 기록          | 100사이클마다 다음 바이트 하나에`0x00` (2벌 동일하게)   |
| 판독          | 누적 =`0x00` 바이트 수 × 100                           |
| 용량          | 4,096바이트 →**409,600 사이클**                    |
| 기록 비용     | 0.004% (2벌 합산)                                         |
| 바이트 재기록 | **금지** — 각 바이트를 딱 한 번만 쓴다             |

### 8.2 판독과 2벌 병합

| 값       | 처리                                 |
| -------- | ------------------------------------ |
| `0x00` | 센다                                 |
| `0xFF` | 안 씀                                |
| 그 외    | 세지 않되**±1 불확실**로 기록 |

두 벌을 **하나의 tally 값으로 합치는 것이 「병합」** 이다. 2벌은 같은 사이클에 동일하게
쓰므로(§8.1) 눈금이 같고, 불일치의 원인은 **한 벌을 쓰고 다른 벌을 쓰기 전에 끊긴 것**
하나다 — 그래서 차이의 크기로 가른다.

| `|a − b|` | 뜻 | 동작 |
| --------- | -- | ---- |
| `0` | 정상 | 그대로 쓴다 |
| `≤ 100` (1바이트) | 쓰는 중에 끊겼다 | **큰 쪽으로 병합** + 불일치와 두 원래 값을 기록 |
| `> 100` | **정상 차단으로 설명되지 않는다** — 한 벌의 기록이 반복 실패했거나 엔진이 한 벌만 쓰고 있다 | **중단하고 사람을 부른다** |

- **「병합」과 「채택」은 다른 말이다.** 병합은 **2벌 → tally 값 하나**(여기, 눈금이 같다),
  채택은 **tally 값과 호스트 로그 중 최종 사이클 수**(§8.3, 눈금이 다르다)를 고르는 일이다.
  **§8.3 의 「큰 쪽 채택」은 폐기됐고**(`[D41-20]`) 병합은 그 대상이 아니다
- 병합은 **호스트가 한다.** 엔진은 2벌을 따로 돌려준다 — `docs/interface/pe_engine.md` §2

### 8.3 재개 절차

```
1. UID 읽기 → 등록부 대조. 불일치면 중단
2. tally 2벌 판독 → **2벌 병합** (§8.2)
3. d = (A 로그의 최대 cycle) − (tally × 100) 을 구한다
4. d 로 가른다 — 아래 표. **큰 쪽 채택이 아니다**
5. blank check → 부분 소거 상태면 해당 섹터 재소거 (경계 8 `reerase`, 별도 명령 · R 행 기록)
6. 이어서 진행 — `wear_start(cycle=채택값, delta=다음 체크포인트까지)`. 엔진은 `cycle` 이
   tally 와 `d` 규칙 밖이면 거부한다 (`E_CYCLE`)
```

| `d`            | 뜻                                                   | 동작                                                          |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| `0 ≤ d < 100` | 정상                                                 | **호스트 로그 채택**                                    |
| `d < 0`        | **호스트 죽음** — A 가 멈추고 tally 만 앞섰다 | **tally × 100 채택** + 결손 구간을 기록                |
| `d ≥ 100`     | tally 가 안 는다                                     | 채택하지 않고**tally 섹터의 다음 바이트를 본다** (아래) |

`d ≥ 100` 에는 두 경우가 섞인다. §6 ④ 가 tally 를 먼저 쓰고 행을 나중에 내보내므로
**A 행은 받았는데 tally 쓰기 전에 끊기는 창** 이 있는데, 그것은 정상 차단이라 사람을
부르면 과하다.

| 다음 바이트     | 뜻                             | 동작                                |
| --------------- | ------------------------------ | ----------------------------------- |
| `0xFF`        | 아직 안 썼다 — 정상 차단의 창 | 호스트 로그 채택하고 계속           |
| 그 외           | 전원 차단 중 부분 프로그램     | §8.2 의**±1 불확실**로 기록 |
| write 시험 실패 | **플래시가 안 써진다**   | **중단하고 사람을 부른다**    |

복원 불확실성: 최대 100사이클 (+소거 중 차단 시 ±1)

> **2026-09-18 개정 — 「큰 쪽 채택」을 폐기한다** (한영웅, `[D41-20]`).
> 폐기 대상은 **이 절의 3번**(tally 와 호스트 로그를 부등호로 고르던 것)이고,
> §8.2 의 **2벌 병합은 눈금이 같은 다른 규칙이라 그대로 둔다.**
> tally 는 100사이클마다 1바이트라 **해상도가 100** 이다(§8.1). 147사이클에서 tally×100 =
> 100, 호스트 로그 = 147 이므로 **`tally < 호스트로그` 는 늘 참** 이고, 부등호로는 아무것도
> 안 가려진다 — 「호스트만 죽었다」와 「정상 중단」이 같은 모양으로 온다. 가르는 것은
> **차이의 크기** 다. 경위는 `docs/log/young/41.blackbox_tb_and_engine_interface.md` §12 ·
> `[D41-20]`·`[D41-21]`.
>
> **전제** — A 로그가 **매 사이클 실시간** 으로 나간다(§9 A). 일괄로 내보내면 `d` 가 버스트
> 단위로 튀어 이 표를 다시 써야 한다. §6 ④ 에 그 출력 단계를 넣는 개정이 따로 걸려 있다.
>
> **엔진은 채택하지 않는다.** tally 2벌의 원본값·다음 바이트·write 가능 여부만 돌려주고
> 판단은 호스트가 한다 — `docs/interface/pe_engine.md` §2 경계 3. 중단 판단이 사람을
> 불러야 하는 일이라 엔진이 혼자 정하면 호스트가 이유를 모른다(§8.3 1 과 같은 원리).

### 8.4 실험 종료 시

```
1. 최종 카운트를 docs/chip_registry.md에 확정 기입
2. tally 섹터 해제 (이후 정상 섹터로 사용 가능)
```

### 8.5 파일럿에서 검증할 것

파일럿 종료 시 tally 섹터를 전량 읽어 `0x00`/`0xFF` 외의 값이 있는지 확인한다.
있으면 마크 간격 또는 페이지당 기록 바이트 수를 조정한다.

## 9. 로깅

```
A. 사이클 로그   (매 사이클, 섹터별 1행)
   cycle, sector, t_erase_us, t_program_us, timestamp

B. 무결성 로그   (검사 주기마다 1행 — 두 읽기의 값을 한 행에)
   cycle, erase_residual_bits, program_fail_bits,
   p_addr_count, p_addrs, p_worst_page, p_worst_bits,     ← 프로그램 직후 읽기
   e_addr_count, e_addrs, e_worst_page, e_worst_bits,     ← 소거 직후 읽기
   die_temp_c, uid_ok, timestamp

R. 사건 로그     (사건 1건마다 1행 — 재소거 · WIP 타임아웃 · 프로그램/소거 실패 · UID 불일치 · 사람 정지)
   kind, cycle, sector, op, t_us, ok, resid_before, resid_after, timestamp

C. 체크포인트 로그 (스윕 1개당 1행)
   cycle, area, sweep_csv, chip_id(UID), base_sector, n_sectors, n_reads,
   pattern, repeat_idx, area_cumulative_cycles, git_rev, die_temp_c, timestamp
```

공통 필수: `chip_id`(UID), `git_rev`, `base_sector`, `timestamp`

- `p_addrs`·`e_addrs` — 결함 비트 주소 목록 (페이지·바이트·비트). 각 최대 64개 + 총 개수.
  프로그램 실패(전하가 안 들어감)와 소거 잔류(전하가 안 빠짐)는 다른 고장이라 phase 별로
  보존한다 (2026-09-21, 로그 44 `[D44-13]`)
- `R` 의 재소거는 **카운터에도 `area_cumulative_cycles` 에도 더하지 않는다.** 전원 차단 당시
  진행 중이던 P/E 의 완료 여부가 ±1 불확실하다는 뜻이고, 그 데이터 지점은 회복 사건이 있었음을
  표시해 민감도 분석에서 뺄 수 있게 한다 (지민 회신 §3.4). 호스트는 `docs/chip_pe.md` 에 증분
  행을 남긴다
- `area_cumulative_cycles` — 대조군의 재기록 누적 사이클을 포함한 값
- 온도는 B·C에만 (A는 매 사이클이라 같은 값 반복)

| ⑥ | tally 기록 방식              | 페이지당 256회 부분 프로그램이 성립하는가 (§8.5) |

**파일럿 결과 전에는 종단 마모 3칩을 착수하지 않는다.**

> **2026-09-23 추기 — 파일럿의 정지 기준과 사전 가설** (한영웅, chip01 파일럿 29,600사이클 시점 · 세션 `1790091548`).
> §11 의 종점 300,000 은 데이터시트 내구 10만의 3배라는 자리표시자이지 물리에서 나온 수가 아니다.
> 파일럿은 다음 셋 중 먼저 오는 것으로 멈춘다 — 이는 파일럿의 기준이며 실행기에 넣지 않는다.
>
> 1. **측정 불능** — 체크포인트 prep 이 마모 섹터에 PRBS 를 써서 검증하지 못하거나, 엔진이 스스로 서는 때
>    (WIP 2초 타임아웃 · 소거 잔류 4,588비트 초과). 폭을 더 잴 수 없으니 칩의 수명이 끝난 것이다.
>    소거 시간이 데이터시트 최대 400ms 를 넘는 것은 정지 사유가 아니다 — 늙었다는 표시지 못 잰다는 뜻이 아니다
> 2. **답이 나옴** — 폭이 재장착 σ 의 3배(≈42ps, S-2 §6.2)를 넘게 움직인 체크포인트가 나오고 그 뒤 2~3점으로
>    기울기가 서면 ①·④ 는 닫힌다. §11 의 조밀화 트리거 1.83ps 는 7월 반복 σ 로 만든 값이라 체크포인트 간
>    흔들림(8점에서 6ps)에도 걸리므로 파일럿에서는 쓰지 않는다
> 3. **300,000** — 위 둘이 오지 않으면.
>
> **사전 가설.** 29,600사이클까지 소거 시간 p50 은 32.8 → 62.6ms 로 2배가 됐고 폭(25MHz · θ=10⁻²)은
> 8점이 39,666~39,672ps 로 6ps 안에 있다. 이를 데이터로 삼아 나머지 구간의 예측을 미리 적는다 —
> **(H1) 25MHz SPI 타이밍 마진은 측정 불능(기준 1)까지 3σ(42ps) 안에서 움직이지 않는다.
> (H2) 소거 시간은 단조 증가한다.** 근거는 구조다 — 출력 엣지는 클럭에 맞춰 도는 출력 레지스터가 내고,
> 셀 열화로 길어지는 어레이 접근 시간은 25MHz 의 40ns 주기 안에서 여유가 커 엣지에 이르지 못한다. 반면
> 소거 시간은 소거 검증 루프가 산화막의 갇힌 전하를 그대로 반영한다. H1 이 참이면 결론은 "이 정밀도의
