## 1. 변경 요지

측정 CSV가 **자기가 어느 개체를 어떤 조건으로 쟀는지 스스로 들고 있게 한다.**

지금은 네 가지가 사람 메모에만 있다.

| 사실 | 지금 어디 있나 | 무슨 일이 생기나 |
| ---- | -------------- | ---------------- |
| 어느 칩인가 | `--target chip01` — 사람이 주장, 아무도 검증 안 함 | 라벨 오독이 완주한 스윕에 조용히 남는다 |
| 재장착했는가 | `docs/results/data/*.md`의 "재장착 없음" 문장 | 로그 22 §3: 7월 σ와 8/23 값을 비교해도 되는지 매번 사람이 판단 |
| 몇 회차인가 | 파일명 타임스탬프 + 기억 | 반복 집계 시 사람이 골라 넘긴다 |
| 어느 묶음인가 | **없음** | "이 5개가 한 배치"라는 근거가 파일에 없다 |

## 2. 변경 내역 (승인 시 `contract.md` §6에 반영)

### 2.1 파일명

```
현행   sweep_<target>_<stamp>.csv                target = loopback | chip01~chip10
변경   chip*    : sweep_<label>_<uid16>_<stamp>.csv
       loopback : sweep_loopback_<stamp>.csv     (종전 유지)
```

- `<uid16>` = `4Bh` Read Unique ID 64비트를 **대문자 16 hex**로
- `_invalid`는 맨 뒤, `_reads`는 같은 basename — **규칙 불변**
  (`sweep_chip01_A1B2C3D4E5F60718_20260907T131500Z_invalid_reads.csv`)
- 라벨을 남기는 이유: 16 hex 10줄은 사람이 구분하지 못하고, 기존 문서 전부가 `chip01`을
  참조하며, **`<label>_<uid>` 조합이 등록부와 어긋나면 파일명만 보고 드러난다**(로그 23 §4)

### 2.2 메타 열 — 12열 → 16열

현행 §6 표의 마지막 행:

> | `target`, `generated_at`, `git_rev` | str | 런 메타데이터 (전 행 반복) |

변경:

> | `target`, `generated_at`, `git_rev` | str | 런 메타데이터 (전 행 반복) |
> | `uid` | str | `4Bh` UID, 대문자 16 hex. **loopback은 빈 문자열** (전 행 반복) |
> | `reseat` | int | 0 = 배치 내 재장착 없음 / 1 = 매 회차 재장착 (전 행 반복) |
> | `repeat_idx` | int | 배치 내 회차, 1부터 (전 행 반복) |
> | `batch_id` | str | 배치 **시작** 시각 `YYYYmmddTHHMMSSZ`. 개별 CSV의 stamp와 다르다 (전 행 반복) |

- `target`은 종전대로 라벨(`chip01`)이다. 다만 **값의 출처가 바뀐다** — 사람 입력이 아니라
  UID로 등록부(`docs/chip_registry.md`)를 역조회한 결과다
- 열 방식을 택하고 주석 행(`#UID …`)을 버린 이유: `csv.DictReader`가 첫 줄을 헤더로 읽으므로
  주석 행은 **분석기 전부를 깨뜨린다.** 열은 읽기 쪽이 관대해서(키가 늘어날 뿐) 기존 소비자가
  그대로 돈다
- **소급하지 않는다.** 7월·8/23 데이터는 12열 그대로이며 `uid` 등이 없다. 그 데이터의 재장착
  여부·묶음은 계속 유래 md의 문장이 근거다. 두 형식은 열 유무로 구분되므로 혼동되지 않는다

### 2.3 생성 거부 — chip target은 UID 없이 CSV를 만들 수 없다

> **R13 (§6)**: target이 `chip*`인 스윕은 `uid`가 확보되지 않으면 **CSV 파일을 생성하지
> 않는다.** `loopback`은 UID 없이 허용한다(계측기 자기 점검이며 DUT가 없다).
> 진단용 원문 덤프(`--raw`)는 CSV를 만들지 않는다.

집행 주체는 **캡처(`sweep_uart_capture.py`)** 다. 래퍼가 아니라 캡처에 두는 이유는
모든 경로가 캡처를 지나기 때문이다 — 래퍼를 안 쓰고 캡처를 직접 불러도 규칙이 선다.
`bathtub_analysis.py`가 `_invalid`를 다시 거부하는 것과 같은 층이다(로그 23 §6).

### 2.4 UID 확보 절차 (§6 부기)

> UID는 `flash_prep`이 JEDEC 검사 직후 `4Bh`로 **3회 읽어 전부 일치**해야 확보된 것으로
> 본다. 전송 실패는 3회 재시도, 값 불일치는 즉시 중단(`#PREP FAIL`). 출력
> `#PREP UID <16hex>`. 라벨은 UID로 등록부를 역조회한 값이며 사람이 입력하지 않는다.

SPI에는 체크섬이 없어 접촉이 튀면 전송 성공(`XST_SUCCESS`)으로 틀린 값이 온다. `flash_prep`의
JEDEC 검사가 전송 성공이 아니라 **값**(`EF 40 17`)을 보는 것과 같은 층이며, UID는 기대값이
없으므로 자기 일관성으로 대신한다.

| # | 항목 | 결정 | 크리티컬 이유 |
| - | ---- | ---- | ------------- |
| 23 | 개체 신원·측정 조건의 파일 내 기록 | 파일명 `<label>_<uid16>` + 메타 열 4개 + chip은 UID 없이 생성 거부 | 라벨 오독·재장착 여부·묶음이 메모에만 있으면 완주한 스윕이 조용히 오염되고 사후 복구가 불가능 |

## 3. 관계

### 3.1 수정안 #1 §5를 대체한다

#1 §5는 UID를 CSV **선두 주석 행** `#UID <16hex>`로 넣자고 했다. 본 문서는 그것을 **열**로
바꾼다(§2.2 이유). #1 승인 시 §5는 본 문서로 갈음하며 #1의 나머지(§2 BASE_SECTOR)는
영향 없다. `docs/chip_registry.md`의 "CSV 헤더에 `#UID`" 문장도 같은 정정 대상이다.

### 3.2 수정안 #1의 `base_sector` 열과의 순서

#1이 승인되면 §6에 `base_sector` 열이 하나 더 붙는다(#1 §2.6). 본 문서와 #1이 모두 승인되면
17열이며, 열 순서는 **#1의 `base_sector`가 앞, 본 문서의 4열이 뒤**로 고정한다.
둘 다 읽기 쪽에서는 키 이름으로 접근하므로 순서는 재현성 표기 이상의 의미가 없다.

### 3.3 승인 전 측정분

캡처를 새 형식으로 먼저 바꾸면 승인 전 측정이 미승인 형식으로 쌓인다(로그 23 미결 2).
이 수정안은 **기존 열을 하나도 바꾸지 않고 뒤에 덧붙이기만** 하므로, 미승인 상태에서 찍힌
16열 파일도 12열 소비자(`bathtub_analysis.py`, `repeatability_aggregate.py`)가 그대로 읽는다.
**부결되면 4열을 떼어내는 것으로 충분하다.** 거꾸로(12열 유지)는 UID가 또 유실되므로 택하지
않는다.

## 5. 인수 기준 (판정: 장세은)

### A1. 16열 생성

`bathtub_analysis.py --selftest`가 만드는 CSV와 실칩 캡처 CSV가 **같은 16열 헤더**를 가진다.

### A2. 하위 호환

기존 12열 파일 `data/sweep_chip01_20260823T130847Z.csv`가 변경 후 분석기에서 그대로 읽히고
`width@1e-2 = 39741.65ps`가 재현된다.

### A3. 생성 거부

캡처를 chip 대상으로 UID 없이 실행하면 **파일이 하나도 생기지 않고** 비영 종료한다.
`--loopback`은 종전대로 생성된다. `--raw`는 CSV를 만들지 않는다.

### A4. 실칩 1회

chip01 세션 1회: `#PREP UID`가 찍히고, 그 값이 등록부 chip01 행에 기입되며, 산출 CSV의
파일명·`uid` 열·등록부 세 곳의 UID가 일치한다.
