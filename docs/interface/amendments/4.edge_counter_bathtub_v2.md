## 1. 변경 요지

1. **에지 계수기** — 지금 `flash_rx.v` 는 정렬 3개(`t0 + 3/4/5`)의 오류 수 중 최솟값 `e_i` 만 낸다. 틀린 비트가 상승 에지에서 났는지 하강 에지에서 났는지가 남지 않는다. 정렬마다 카운터를 정답 비트 0 · 1 로 나눠(3 × 2 = 6개) 읽기마다 **여섯 값을 전부** 남긴다 — 정렬별 총 오류 수 `e_c`(c = 0 · 1 · 2)와 정렬별 정답 1 오류 수 `e1_c`. 승자는 PC 가 정한다(동률 규칙이 해석에 끼지 않게 — 로그 55 [D55-16]). 정답 0 오류 수는 `e_c − e1_c` 로 파생한다(§6 「파생량은 저장하지 않는다」). `e_i`(= min)는 그대로 낸다 — v1 이 쓴다.
2. **욕조 v2 파일** — 벽 집중 스윕은 바닥 대부분을 1회 훑기로만 지나간다. v1 의 「전 스텝 같은 N · 결측 금지」 와 맞지 않아 **파일 이름부터 따로 둔다**(`bathtub2_*`). v1 파일(`sweep_*`)과 v1 소비자는 그대로다([D55-10]).
3. **캡처 완주 검사** — v2 는 스텝 수가 실행 중에 정해진다. BEGIN 의 `steps × n` 대신 END 줄에 실제로 보낸 행 수를 싣는다.

## 2. 변경 내역 (승인 시 `contract.md` 에 반영)

### 2.1 §2 core ↔ flash 신호 — 1행 추가

| 신호 | 방향 (core 기준) | 폭 | 의미 |
| ---- | ---------------- | -- | ---- |
| `log_rd_cand` | in | 96 | `log_rd_addr` 가 가리키는 읽기의 [15:0] `e_c0` · [31:16] `e_c1` · [47:32] `e_c2` · [63:48] `e1_c0` · [79:64] `e1_c1` · [95:80] `e1_c2`. `log_rd_data` 와 같은 사이클에 유효 |

e_i 버퍼 옆에 같은 깊이(2,048)의 버퍼를 하나 더 둔다(2,048 × 96b — BRAM 약 6개, Zynq-7020 은 140개).

### 2.2 §3 레지스터 맵 — 2곳

| 오프셋 | 이름 | 접근 | 리셋값 | 내용 |
| ------ | ---- | ---- | ------ | ---- |
| 0x00 | `ID` | RO | **0x4D42_0200** | 버전 올림 — v2 펌웨어는 시작 때 이 값을 확인하고 아니면 거부한다 |
| 0x2C | `LOG_C0` | RO | 0 | `LOG_ADDR` 가 가리키는 읽기의 [15:0] `e_c0` · [31:16] `e1_c0` |
| 0x30 | `LOG_C1` | RO | 0 | 같은 형식, 정렬 1 |
| 0x34 | `LOG_C2` | RO | 0 | 같은 형식, 정렬 2 |

0x28 은 수정안 #1 의 `BASE_SECTOR` 자리라 비워 둔다. `LOG_DATA`(0x24)는 바꾸지 않는다 — v1 펌웨어가 그대로 돈다.

### 2.3 §4 규약 — R8 확장 · R13 신설

- **R8** 무결성 검사에 둘을 더한다: ④ 모든 읽기에서 `min(e_c0, e_c1, e_c2) == e_i` ⑤ 모든 c 에서 `e1_c ≤ e_c`. v1 펌웨어는 ④⑤를 보지 않는다(읽지 않으므로).
- **R13 정렬별 계수**: 정렬 c 는 0 = `t0 + 3`, 1 = `t0 + 4`, 2 = `t0 + 5` 출발로 맞댄 비교다. `e_c` 는 그 정렬의 불일치 수, `e1_c` 는 그중 **기대 비트가 1 인 자리의 불일치 수** 다. 승자 선택 · 방향 해석(상승 · 하강, 이른 · 늦은)은 계약이 아니라 호스트 분석의 몫이다 — 해석이 틀려도 RTL 을 고치지 않는다.

### 2.4 §5 수치 계약 — 결과 카운터 행

| 항목 | 값 |
| ---- | -- |
| 결과 카운터 폭 | `ERR_*` 32비트 그대로. `e_c` · `e1_c` 각 16비트(`e_i` 와 같은 폭, B ≤ 65,528) |

### 2.5 §6 스키마 — 욕조 v2 파일 신설

- **파일**: `bathtub2_<target>_<UID>_<stamp>.csv` + 동반 `bathtub2_<target>_<UID>_<stamp>_reads.csv`. 접두사가 달라 v1 소비자(`sweep_*` glob)가 읽지 않는다. 메타 열(`target` · `uid` · `generated_at` · `git_rev` · `reseat` · `repeat_idx` · `batch_id` · `reason`)은 v1 과 같다.
- **메인 CSV — 행 = (단계, 위상 스텝) 하나.** v1 열 전부 + 아래 열.

| 열 | 타입 | 뜻 |
| -- | ---- | -- |
| `pass` | str | `scan`(훑기) · `ceil`(천장 한 묶음) · `wall`(벽 집중) · `rescan`(끝 훑기) |
| `mode` | str | `std` · `deep` (전 행 반복) |
| `flags` | str | 유효 런의 주의 표시 — 빈 값 또는 `;` 로 이은 식별자(§2.6). 전 행 반복 |

- **결측 규약(v2)**: `scan` 과 `rescan` 은 `phase_step` 0 부터 UI 끝까지 **연속 · 결측 금지**. `ceil` · `wall` 은 잰 스텝만 있다 — 한 스텝이 여러 단계에 나올 수 있고, `(pass, phase_step)` 은 겹치지 않는다. `n_reads` 는 행마다 다르다(훑기 1 · 천장 112 · 벽 N).
- **동반 `_reads.csv`**: 열 `phase_step, pass, read_idx, err_count, e_c0, e_c1, e_c2, e1_c0, e1_c1, e1_c2`. 초심부도 필수다([D55-9]) — 약 4,000만 행, 스윕당 약 1.7GB.
- **무효 런 추가**: ⑨ `multi_block` — 훑기에서 오류 덩어리 사이 0 틈이 K 이상(덩어리 둘 이상) ⑩ `wall_cap` — 벽 집중이 덩어리 경계에서 바깥으로 상한(명세 S-6)까지 갔는데도 0 오류 K 연속이 안 왔다 ⑪ `id_mismatch` — `ID` 가 0x4D42_0200 이 아니다.
- **유효 런의 주의 표시(`flags`)**: `block_out_of_range` — 덩어리 중심이 이력 범위 밖(범위는 명세) · `drift` — `rescan` 의 덩어리 경계가 `scan` 과 1스텝 넘게 다르다. 표시가 붙어도 분석 입력에서 빼지 않는다 — 판단은 분석이 한다.

### 2.6 §6 캡처 완주 검사

v2 의 END 줄은 `main_rows=<n> reads_rows=<m>` 을 싣는다. 캡처는 받은 행 수와 대조해 하나라도 다르면 무효 ⑤(미완주 · 결측)로 처리한다. v1 은 그대로 BEGIN 의 `steps × n` 으로 본다.

## 4. 인수 기준

### A1. 하위 호환 회귀 — 새 비트스트림에서 v1 이 그대로인가

새 비트스트림 + v1 ELF 로 루프백 스윕과 기지 칩 스윕을 1회씩 뜬다. CSV 열 · 행 수 · R8 이 v1 과 같고, 덩어리 위치와 천장 오류 수가 v1 이력 범위 안이다.

### A2. 계수기 시뮬레이션 — 해석표가 맞는가

가짜 플래시 모델에 「상승 에지가 일찍 오는 칩」 과 「하강 에지가 일찍 오는 칩」 을 각각 넣고, 위상을 덩어리 전체에 걸쳐 쓸어 여섯 값을 받는다. 확인할 것:

- 개념 16 의 해석(방향 = 정답 비트, 일찍 · 늦게 = 승자)이 두 칩의 정답(어느 에지가 먼저인가)을 내는가
- 정렬 번호(0 · 1 · 2)와 「앞 비트 · 다음 비트」 의 대응이 위상에 따라 어떻게 바뀌는가 — 프리앰블의 첫 1 도 상승 전이라서다. 「한 칸 앞」 이 이기는 경우의 해석도 여기서 확정한다
- 동률(최소 오류 정렬이 둘 이상)이 위상마다 얼마나 자주 나는가
- R8 ④⑤ 가 전 읽기에서 성립하는가

### A3. 루프백 v2 완주

루프백으로 v2 스윕(`std`)을 끝까지 돌려 `scan` · `rescan` 결측이 없고, END 행 수 대조를 통과하고, 일부러 한 줄을 버린 캡처는 무효 ⑤ 가 되는지 본다.

### A4. 실칩 1회

기지 칩 하나로 v1 스윕과 v2 스윕(`std`)을 같은 장착에서 연달아 뜬다. v2 의 `scan` 덩어리 위치가 v1 과 같고, 천장 오류 수가 한쪽 방향 전이 수(112읽기 기준 56,572)와 같고, 정답 1 오류(`e1_c`)가 해석대로 한쪽(정답 0 또는 1)에 몰리는지 본다.

### A5. 75MHz 실칩 정답 대조 — 계수기 해석이 실제 칩에서 맞는가

75MHz 비트스트림(사다리 빌드 경로 `fpga/scripts/build_g3_chip.tcl`)으로 칩 1-2개에 v2 스윕(`std`)을 1회씩 뜬다. 75MHz 는 기존 데이터만으로 선반의 정답이 알려져 있다 — 왼쪽 선반 = 「1 0 1」 상승, 오른쪽 선반 = 「1 1 0」 하강(로그 55 §7 추기). 계수기 해석표가 선반마다 같은 방향(왼쪽 상승 · 오른쪽 하강)을 내야 통과다. 25MHz 는 두 에지가 붙어 있어 계수기가 틀려도 그럴듯한 결과가 나올 수 있으므로, 이것이 실제 칩 위의 유일한 정답 대조다. 장의 데이터가 아니라 계수기 검증에만 쓴다 (2026-11-11, 한영웅).
