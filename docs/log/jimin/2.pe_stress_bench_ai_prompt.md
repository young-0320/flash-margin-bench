- 성격: 구현 작업 지시용 프롬프트. 이 문서 자체는 구현 또는 실측 기록이 아니다.

## 사용 방법

아래 `AI 작업 프롬프트` 전체를 저장소를 열 수 있는 AI 코딩 도구에 전달한다.

AI가 해야 할 범위는 다음과 같다.

1. 최신 저장소와 사양을 다시 읽는다.
2. 현재 구현 상태와 사양의 충돌을 보고한다.
3. P/E 스트레스 벤치 코드를 구현한다.
4. 실제 칩을 건드리지 않는 테스트로 먼저 검증한다.
5. 실칩 100사이클 시험 직전에서 멈춘다.

AI가 해서는 안 되는 일은 다음과 같다.

- 실제 Flash에 임의로 P/E 실행
- 동결 사양서를 설명 없이 수정
- 미승인 수정안을 승인된 기능처럼 가정
- 오류가 있는데도 자동 재시도하여 실험 이력을 숨김
- near, far, tally 영역을 wear 영역과 함께 지움
- 실제 실칩 검증을 하지 않았는데 완료됐다고 기록

# AI 작업 프롬프트

## 0. 역할과 목표

당신은 `flash-margin-bench` 저장소에서 SPI NOR Flash용 P/E 스트레스 벤치를 구현하는
선임 FPGA/임베디드 소프트웨어 엔지니어다.

최종 목표는 다음 한 문장이다.

> Winbond W25Q64JV의 지정된 wear 영역에만 Program/Erase를 반복하고, 진행 횟수,
> Program/Erase 시간, 무결성 오류, UID와 체크포인트를 기록하며, 전원이 끊긴 뒤에도
> 잘못된 영역을 건드리지 않고 안전하게 재개할 수 있는 벤치를 구현한다.

이 작업에서 실제로 마모되는 대상은 FPGA가 아니라 외부 W25Q64JV Flash다. 구현 계층은
저장소 workflow가 잠정적으로 제안한 **Zynq PS의 C 프로그램 + PC의 Python 실행기**를
우선 검토한다. RTL P/E 엔진은 자동으로 선택하지 말고, 현재 문서와 팀 결정에 근거가
없다면 새로 만들지 않는다.

실제 하드웨어 P/E는 비가역적이다. 코드 작성, 빌드, 정적 검사, 단위 테스트, 가짜 시리얼과
가짜 XSCT 검증까지만 자율적으로 수행한다. JTAG, UART, USB 장치를 통해 실제 Flash에
Program 또는 Erase를 실행하려면 반드시 작업을 멈추고 사람에게 승인받는다.

## 3. 구현해야 할 실험 정의

### 3.0 파일럿 고정값과 의미

이 구현의 파일럿 조건은 다음 값으로 고정한다. 과거 문서나 코드에 남아 있는 `N=100`은
7월 기준선 또는 전환 비교용 조건이며, **이번 P/E 파일럿의 측정값은 `N_READS=112`**다.

| 항목 | 파일럿 값 | 의미 |
|---|---:|---|
| `N_READS` | 112 | 한 번의 sweep에서 읽는 페이지 수 |
| 페이지/섹터 | 16 | W25Q64JV의 4KB 섹터를 256B 페이지로 나눈 값 |
| 측정 영역 크기 | 7섹터 = 112페이지 | `N_READS`와 정확히 일치하는 한 그룹 |
| wear | 섹터 0–6, `BASE_SECTOR=0` | 장시간 P/E를 반복할 마모 영역 |
| near control | 섹터 7–13, `BASE_SECTOR=7` | wear 옆에서 간섭 가능성을 관찰할 근접 대조군 |
| far control | 섹터 2041–2047, `BASE_SECTOR=2041` | 공통 환경 변화를 비교할 원거리 대조군 |
| tally A/B | 섹터 512 / 1536 | 전원 장애 후 완료 cycle을 복구할 전용 영역 |

`N=112`는 간섭이 112페이지까지 퍼진다는 뜻이 아니다. `16 pages/sector × 7 sectors =
112 pages`이므로, 각 영역을 섹터 경계부터 끝까지 빠짐없이 읽기 위한 측정 길이다. 과거의
`N=100`으로는 7섹터 중 마지막 12페이지가 측정되지 않았다.

### 3.0.1 완충을 두지 않고 near/far를 함께 두는 이유

논리 섹터 번호와 Flash die 내부의 실제 셀·word line·bit line 배치는 공개되어 있지 않다.
따라서 논리적으로 인접한 두 섹터가 물리적으로 반드시 바로 옆이라고 단정할 수 없고,
임의로 몇 섹터를 비워도 간섭이 차단된다고 보장할 수 없다. 체커보드 등 특정 패턴의 영향이
인접 셀 하나에서 끝난다는 보장도 없다.

여기서 체커보드는 간섭 범위를 설명할 때 나온 일반적인 예일 뿐, 현재 파일럿의 채택
패턴이 아니다. 현재 고정값은 **wear loop의 마모 패턴 `0x00`**, 체크포인트 측정 패턴
**PRBS-15**다. 별도 팀 결정 없이 체커보드 패턴으로 바꾸지 않는다.

파일럿은 근거 없는 완충 폭으로 간섭을 피하려 하지 않고 다음 비교로 간섭 가능성을
**관찰**한다.

- `wear`: 반복 P/E로 의도적으로 스트레스를 받는다.
- `near`: wear loop에는 넣지 않고, wear와 논리적으로 가장 가까운 비교 영역으로 둔다.
- `far`: wear loop에는 넣지 않고, wear에서 논리적으로 먼 비교 영역으로 둔다.
- `near`가 `far`보다 더 변하면 근거리 간섭 또는 disturb 가능성을 후속 검토한다.
- `near`와 `far`가 비슷하게 변하면 온도, 전원, 재장착, 측정 반복 같은 공통 요인을 먼저
  검토한다.

이 비교만으로 간섭이 물리적으로 몇 셀까지 퍼졌다고 확정하지 않는다. 그 범위를 찾으려면
거리별 대조군을 둔 별도 실험이 필요하다. 또한 `near`와 `far`도 체크포인트에서 측정용
PRBS를 다시 준비할 때 Erase+Program을 1회 받으므로 완전한 P/E 0 영역은 아니다. 로그에는
`wear_loop_cycles`와 `wear/near/far` 각각의 실제 누적 P/E 횟수를 분리해 기록한다.

### 3.1 P/E 1사이클

파일럿 wear 영역의 1사이클은 다음 순서다.

```text
1. wear 영역 112페이지에 0x00 Program
2. 필요한 완료 상태와 오류 확인
3. wear 영역 7개 섹터 Erase
4. 필요한 완료 상태와 오류 확인
5. 두 작업이 성공한 경우에만 cycle을 1 증가
```

기본 파일럿 영역은 다음과 같다.

| 용도 | 섹터 |
|---|---:|
| wear | 0–6 |
| near control | 7–13 |
| far control | 2041–2047 |
| tally A | 512 |
| tally B | 1536 |

wear loop는 sector 0–6 이외의 영역을 절대 Program 또는 Erase해서는 안 된다.
특히 near와 far는 완충 영역이 아니라 체크포인트 비교용 측정 영역이다. 두 영역에 대한
Erase+Program은 wear loop가 아니라 명시적인 checkpoint 준비 경로에서만 허용한다.

### 3.2 주소 보호 불변식

모든 Program/Erase 함수가 실행되기 전에 공통 주소 검사를 거치게 한다.

검사는 최소한 다음을 보장해야 한다.

- sector와 page 계산에서 overflow가 없다.
- 지정된 W25Q64JV 전체 범위를 넘지 않는다.
- wear 명령은 승인된 wear 영역 안에서만 동작한다.
- 일반 wear 명령은 near와 far를 건드릴 수 없다.
- tally 섹터는 일반 erase/program 함수가 건드릴 수 없다.
- tally 변경은 전용 함수에서만 가능하다.
- 체크포인트 준비가 control 영역을 변경할 때는 명시적 checkpoint 모드가 필요하다.
- 범위 하나가 두 용도와 겹치면 실행 전에 실패한다.

검사 실패 시 Flash 명령을 한 번도 발행하지 않고 명확한 오류 로그와 비영 종료 상태를
반환한다.

### 3.3 카운트 원칙

- Program과 Erase 한 쌍이 정상 완료된 경우에만 wear cycle을 증가시킨다.
- Program 또는 Erase 중 하나가 실패한 경우 완료 cycle로 세지 않는다.
- 실패 도중 Flash가 실제로 받은 부분 스트레스는 별도 불확실 상태로 기록한다.
- 체크포인트의 Erase+PRBS Program도 해당 영역의 누적 P/E를 1 증가시킨다.
- wear loop cycle과 영역별 누적 P/E를 같은 변수로 처리하지 않는다.
- 최소한 `wear_loop_cycles`, `wear_pe_actual`, `near_pe_actual`, `far_pe_actual`을 서로 다른
  필드로 보존한다.

부분 실패 시 어느 작업까지 물리적으로 발행됐는지 로그에 남겨야 한다. 실패를 없었던
사이클처럼 조용히 버리지 않는다.

## 4. PS C 프로그램 구현

저장소의 기존 이름과 빌드 패턴을 확인한 뒤, 전용 프로그램을 예를 들어
`ps/src/flash_wear.c`로 구현한다. 기존 `flash_prep.c`를 복사해 숫자만 바꾸지 말고 공통
Flash 명령 코드의 재사용 가능성을 검토한다. 다만 작은 프로젝트에 과도한 추상화를
추가하지 않는다.

### 4.1 시작 시 검사

Flash를 변경하기 전에 다음을 수행한다.

1. SPI 초기화
2. JEDEC ID 읽기
3. 기대값 `EF 40 17` 확인
4. UID를 3회 읽어 모두 같은지 확인
5. UID가 실행 인자로 지정된 기대 UID와 같은지 확인
6. wear/near/far/tally 주소 배치 검증
7. resume 여부와 시작 cycle 확인

하나라도 실패하면 Program/Erase 없이 중단한다.

### 4.2 Flash 명령

기존 코드와 W25Q64JV 데이터시트를 기준으로 다음 기능을 구현하거나 재사용한다.

- Write Enable
- Page Program
- 4KB Sector Erase
- Status Register의 WIP polling
- Fast Read 또는 검증용 Read
- JEDEC ID
- Unique ID

WIP polling에는 timeout을 둔다. 현재 S1의 잠정 기준은 2초다.

```text
WIP가 2초 안에 해제됨 → 계속
WIP가 2초를 넘음      → 즉시 정지, 자동 재시도 금지
```

자동 재시도 금지 이유는 같은 Program/Erase가 실제로 한 번 수행됐는지 두 번 수행됐는지
알 수 없게 만들기 때문이다.

### 4.3 시간 측정

기존 Zynq PS 환경의 `XTime` 사용 패턴을 찾아 WIP가 1인 지속시간을 측정한다.

- 페이지 또는 섹터 Program 시간
- 섹터별 Erase 시간
- 마이크로초 단위 변환

S1의 로그 계약에 맞춰 매 cycle, 매 wear sector에 대해 다음을 출력한다.

```text
cycle, sector, t_erase_us, t_program_us, timestamp
```

100사이클 시험에서 7개 섹터에 대한 로그가 700행이어야 한다. `t_program_us`가 섹터의
16페이지 합계인지 다른 정의인지 S1과 기존 로그를 확인하고 한 정의로 고정한다.

### 4.4 무결성 검사

기본적으로 100사이클마다 다음을 검사한다.

```text
Erase 직후:
112페이지를 읽고 0xFF가 아닌 비트 수 계산
→ erase_residual_bits

Program 검사 시점:
기대 패턴과 다른 비트 수 계산
→ program_fail_bits
```

첫 결함 비트가 한 번이라도 검출되면 검사 주기를 10사이클로 줄인다.

기록 항목:

- 전체 결함 비트 수
- 처음 64개 결함의 page/byte/bit 주소
- 오류가 가장 많은 페이지 번호와 비트 수
- FPGA die temperature를 얻을 수 있으면 해당 값
- UID 일치 여부
- timestamp

영구 결함인지 일시 결함인지는 PS 프로그램 안에서 억지로 판정하지 않는다. 원시 사실만
남기고 재현성 판단은 사후 분석으로 넘긴다.

## 5. Tally와 전원 장애 복구

### 5.1 Tally 기록

- sector 512와 1536을 tally 전용으로 사용한다.
- 실험 시작 시 두 섹터를 각각 한 번 Erase하고 전체 `0xFF`인지 확인한다.
- 100 wear cycles마다 두 섹터의 다음 미사용 바이트 하나를 `0x00`으로 Program한다.
- 같은 바이트를 두 번 Program하지 않는다.
- 일반 wear 또는 prep 경로는 tally 섹터를 hard guard로 거부한다.

판독 규칙:

| 바이트 값 | 의미 |
|---|---|
| `0x00` | 완료된 tally mark |
| `0xFF` | 아직 사용하지 않은 위치 |
| 그 외 | 전원 차단 중 부분 Program 가능성, ±1 불확실 |

누적 cycle은 `0x00 바이트 수 × 100`으로 계산한다. 두 tally가 다르면 큰 값을 채택하되
불일치와 두 원래 값을 반드시 기록한다.

### 5.2 Resume 절차

재개는 다음 순서를 따른다.

```text
1. UID 재확인
2. tally A/B 판독
3. PC 호스트 로그의 마지막 완료 cycle 판독
4. 세 값의 불일치 기록
5. 가장 큰 확실한 완료값을 후보로 선택
6. wear 영역 blank check
7. 부분 Erase이면 해당 상태를 기록하고 사양에 따라 재소거
8. 재개 지점과 불확실 범위를 출력
9. 사람 또는 명시적 --resume 승인 후 계속
```

재개가 새 실험 시작처럼 조용히 동작해서는 안 된다. `--resume`과 신규 시작을 명확히
분리하고, 기존 로그가 있는데 신규 초기화를 시도하면 거부한다.

## 6. 호스트 Python 실행기 구현

기존 `host/run/run_sweep_chip.py`의 성공 패턴과 로그 23~25의 리뷰 내용을 읽고,
예를 들어 `host/run/run_wear.py`를 구현한다.

### 6.1 실행기의 책임

- 실행 시작과 동시에 세션 로그 생성
- Git revision, 시각, 요청한 칩 UID, 영역, 목표 cycle 기록
- PS wear ELF 빌드 또는 기존 빌드 산출물 검증
- XSCT 호출과 반환 코드 확인
- UART의 구조화된 wear 로그 캡처
- tally와 호스트 로그의 cycle 교차검증
- checkpoint 도달 시 안전한 정지와 상태 저장
- 중단 및 예외 시 마지막 상태와 완료 횟수 기록
- 명시적 resume 처리

### 6.2 기존 래퍼에서 반드시 유지할 교훈

- UART 포트는 첫 출력 줄을 잃지 않도록 XSCT 실행 전에 연다.
- 줄 앞에 쓰레기 바이트가 붙어도 `#WEAR` 등 유효 접두를 탐색할 수 있어야 한다.

- label을 알기 전 실패해도 UID와 이미 발생한 P/E 사실이 유실되지 않아야 한다.
- 결과 파일은 기존 파일을 덮어쓰지 않는다.
- invalid 결과도 삭제하지 말고 `_invalid` 등 명확한 이름으로 보존한다.
- 전체 완료와 일부 완료를 exit code와 마지막 요약 줄에서 구분한다.

### 6.3 안전 옵션

CLI 이름은 저장소 관례에 맞추되 최소한 다음 개념을 표현한다.

- dry-run 또는 mock mode
- expected UID
- target cycles
- wear base sector와 sector 수
- new run과 resume 구분
- serial port와 baud rate
- checkpoint 사용 여부
- 실제 하드웨어 실행을 위한 명시적 확인 옵션

단순 `--force` 하나로 모든 보호 기능을 끌 수 있게 만들지 않는다.

## 7. 체크포인트 연동

S1의 기본 체크포인트 규칙은 다음과 같다.

- 첫 지점 0
- 두 번째 지점 300
- 변화가 작을 때 다음 cycle = 현재 cycle × 2.15
- 직전 window 변화가 1.83ps보다 클 때 × 1.47
- 최대 300,000

체크포인트에서 wear, near, far 영역에 PRBS를 준비하고 sweep을 수행한다. 해당
Erase+Program은 각 영역의 누적 P/E를 1 증가시킨다.

각 영역은 `N_READS=112`로 독립 sweep한다. 한 번의 `N=112`를 세 영역이 나눠 쓰는 것이
아니며, `BASE_SECTOR`를 각각 0, 7, 2041로 설정하여 영역마다 112페이지 전체를 측정한다.
현재 S1 §5.2에 남아 있는 `BASE_SECTOR=21 또는 2041`의 `21`은 본 실험 배치의 근접
대조군 값이다. **파일럿에서는 S1 §2.1의 확정 표를 따라 near=7을 사용한다.** 이 불일치를
구현 보고서에 기록하고 파일럿 코드에 21을 섞지 않는다.
체크포인트 결과와 세션 로그에는 최소한 다음 값이 함께 남아야 한다.

```text
region, base_sector, n_reads,
wear_loop_cycles, region_pe_actual,
chip_uid, checkpoint_cycle, timestamp
```

해석 시 단순 cycle 숫자가 아니라 baseline 대비 wear/near/far의 window 변화량을 비교한다.
`near - far` 차이는 간섭 가능성을 탐색하는 지표이지, 물리적 인접 거리의 직접 측정값은
아니다.

다만 다음 세 문제를 코드 작성 전에 반드시 확인한다.

1. 현재 `run_sweep_chip.py`는 `base_sector != 0`을 거부하는가?
2. 실제 RTL과 PS 빌드가 수정안 #1의 11비트 `BASE_SECTOR[10:0]`를 구현했는가?
3. 실제 sweep 빌드의 `N_READS`가 112로 설정되었는가?

수정안 #1의 `BASE_SECTOR` 정의는 8비트가 아니라 **11비트(0–2047)**다. 따라서 far의
`BASE_SECTOR=2041`은 표현 가능하며, `N=112`일 때 마지막 읽기 페이지는
`2041×16+111=32767`로 칩의 최종 페이지에 정확히 맞는다. 다만 문서에 값이 있다고 해서
구현과 승인이 끝난 것은 아니므로, RTL 레지스터 폭, 주소 계산, PRBS 시드 계산, 설정 범위
검사와 수정안 승인 상태를 각각 확인한다. 구현이 아직 11비트가 아니라면 far 위치를 임의로
바꾸지 말고 blocker로 보고한다.

체크포인트 전체 자동화가 이 문제로 막히더라도 wear cycle, 로그, tally와 dry-run까지
완성 가능한 범위를 분리해 구현하고, 막힌 부분은 명확한 blocker로 보고한다.

### 8.1 순수 단위 테스트

- page/sector/address 변환

## 9. 실칩 100사이클 직전 합격 기준

실제 칩 실행 승인을 요청하기 전에 먼저 **Flash 명령을 발행하지 않는 mock으로 100사이클**을
완주해 다음 구조가 성립해야 한다. 그다음 사람 승인을 받아 실제 보드에서 `target=1` 수준의
짧은 dry-run으로 주소와 로그를 확인하고, 다시 승인받은 뒤 실제 100사이클로 진행한다.

| 항목 | 기대값 |
|---|---|
| 완료 cycle | 100 |
| 섹터별 cycle 로그 | 700행 |
| 무결성 로그 | 100사이클 지점 1행 이상 |
| tally A | `0x00` mark 1개에 해당 |
| tally B | `0x00` mark 1개에 해당 |
| 카운트 교차검증 | 모두 100 |
| UID | 시작과 종료가 동일 |
| wear 주소 | sector 0–6만 포함 |
| near/far/tally | wear 명령에서 접근 0회 |
| 측정 길이 | 각 영역 `N_READS=112` |
| 측정 시작 섹터 | wear=0, near=7, far=2041 |
| 영역별 P/E | wear loop와 wear/near/far 실제 누적값이 별도 기록 |
| WIP timeout | 2초 초과 시 중단, 재시도 없음 |
| 결과 파일 | 기존 파일 덮어쓰기 없음 |
| 중단 로그 | 원인과 마지막 확실한 cycle 포함 |

실칩 100사이클은 별도의 사람 승인 후 실행한다. 승인을 받더라도 처음에는 `target=1` 또는
아주 작은 횟수로 실제 주소와 로그를 확인한 뒤 100으로 늘리는 방안을 제시한다.
