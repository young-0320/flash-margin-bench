- 작성일: 2026-09-15

- 현재 상태: **WSL의 Python 가상환경과 cocotb·pytest 설치 완료. 테스트벤치 구현과 회귀 실행은 아직 시작 전**
- 작업 위치: `sim/tb/`
- 최우선 기준: `docs/spec/s3.g1_test_plan.md`

## 1. 이 작업을 한 문장으로 설명하면

> FPGA RTL이 우리가 정한 인터페이스 계약과 SPI Flash 동작을 제대로 지키는지, Python으로
> 자동 시험하고 같은 검사를 언제든 다시 실행할 수 있게 만드는 작업이다.

이번 프로젝트에서 cocotb는 실제 Flash를 마모시키는 프로그램이 아니다. 실제 FPGA 보드나
Flash 없이 PC 시뮬레이터 안에서 RTL 입력을 넣고 출력을 관찰한다. 따라서 P/E 스트레스
실험과 달리 반복 실행해도 실제 칩은 손상되지 않는다.

```text
Python cocotb 테스트
        ↓ 입력 신호를 넣음
Verilog RTL 시뮬레이션
        ↓ SPI 신호와 결과를 출력
Python assertion
        ↓ 예상값과 실제값 비교
PASS 또는 FAIL
```

## 2. 내가 맡은 역할

### 기존 GitHub에서 이미 정해진 내용

`docs/roles.md`와 `sim/README.md`에서 박지민의 역할은 다음과 같이 정해져 있다.

- `fpga/rtl/`의 RTL 설계 및 유지보수
- `sim/tb/`의 cocotb 환경 구축
- Winbond 공식 행동 모델 통합
- G1 회귀 실행과 유지
- 자동 회귀 결과를 근거로 최종 블록 승인 집행

즉, 단순히 cocotb를 설치하는 것이 내 역할의 끝은 아니다. 내가 만들어야 하는 핵심 산출물은
**RTL을 자동으로 반복 검사하는 테스트벤치와 그 결과**다.

### 이 문서에서 새로 제안하는 진행 방법

한 번에 23개 테스트와 벤더 모델을 모두 붙이면 어디서 문제가 났는지 알기 어렵다. 따라서
이 문서에서는 다음 순서로 작업하는 방법을 제안한다.

```text
환경 확인
→ 가장 작은 cocotb 테스트 1개
→ 기존 smoke 시험을 cocotb로 이관
→ core 시험
→ 통합 시험
→ Winbond 공식 모델 연결
→ 전체 커버리지 확인
```

이 순서는 초보자가 문제를 한 단계씩 분리하기 위한 작업 순서 제안이다. 합격 항목과 PASS
기준 자체는 새로 정하지 않고 동결된 `docs/spec/s3.g1_test_plan.md`를 그대로 따른다.

## 3. cocotb를 왜 사용하는가

기존 `sim/smoke/`에는 순수 Verilog로 작성한 smoke test가 있다. 이것은 RTL의 기본 기능이
한 번 동작했는지 빠르게 확인하는 데 유용하다. 하지만 프로젝트가 바뀔 때마다 모든 조건을
사람이 다시 확인하기 어렵고, 복잡한 입력 조합과 결과 정리도 불편하다.

cocotb를 사용하면 Python으로 다음 작업을 할 수 있다.

- clock과 reset 생성
- 레지스터와 입력 신호 설정
- SPI MOSI·MISO·CS·SCLK 관찰
- 의도적인 오류와 timeout 상황 주입
- 여러 N, B, 위상, 지연 조건 반복
- 결과를 assertion으로 자동 판정
- JUnit XML인 `results.xml` 생성
- 이후 RTL 변경 때 같은 시험을 다시 실행

이 프로젝트에서는 특히 **우리가 만든 RTL을 우리가 만든 단순 모델만으로 검사하는 순환
문제**를 줄이기 위해 Winbond 공식 행동 모델도 사용한다.

```text
우리 RTL + 우리가 만든 Flash 모델
→ 둘 다 같은 오해를 하면 잘못된 구현도 PASS할 수 있음

우리 RTL + Winbond 공식 행동 모델
→ 제조사 모델이 독립적인 SPI 동작 기준 역할을 함
```

단, 공식 모델도 실제 실리콘을 완전히 대신하지는 않는다. cocotb는 논리·프로토콜 회귀이고,
실제 배선·전압·온도·칩 편차는 실칩 시험이 담당한다.

## 6. 테스트 대상

### Flash DUT

최상위 DUT는 `fpga/rtl/flash/flash_top_spi.v`다. 이 모듈 아래에 연결된 다음 모듈까지
전체가 검증 대상이다.

- `flash_spi_ctrl.v`: 0x0B Fast Read 명령과 주소, SCLK 진행 제어
- `flash_spi_shim.v`: FPGA primitive와 SPI 핀 연결
- `flash_rx.v`: MISO 데이터 수신과 기대 패턴 비교
- `flash_prbs15.v`: 페이지 주소에 따른 PRBS-15 기대 패턴 생성
- `flash_logbuf.v`: 읽기별 오류 개수 저장
- `flash_sync2.v`: clock domain crossing 동기화

### Core DUT

최상위 DUT는 `fpga/rtl/core/core_top.v`다.

- `core_axil_regs.v`: AXI-Lite 레지스터
- `core_phase_ctrl.v`: 위상 증가·감소와 상태 제어
- `core_mmcm.v`: Xilinx MMCM primitive 래퍼

Icarus Verilog는 Xilinx primitive를 직접 알지 못하므로, core 시험에서는 기존
`sim/smoke/unisim_stub.v`와 같은 stub이 필요하다. stub으로 대체한 MMCM 내부 동작 자체는
cocotb가 증명했다고 주장하지 않는다.

## 7. G1 합격 항목 이해

S-3에는 총 23개 항목이 있다.

| 그룹 | 개수 | 의미 |
|---|---:|---|
| F1~F12 | 12 | Flash SPI RTL의 프레임, 타이밍, 주소, 오류 계산과 경계 조건 |
| W1~W2 | 2 | Winbond 공식 모델이 있어야 확인할 수 있는 실제 칩 모델 반응 |
| C1~C6 | 6 | Core 레지스터, 위상 제어, busy·sticky flag 동작 |
| I1~I3 | 3 | Core, Flash, 호스트 흐름이 연결된 통합 동작 |

`BASE_SECTOR` 수정안 #1이 아직 미승인이라면 F11·F12를 제외해 **21개**를 요구한다.
승인 후에는 다음 명령의 `--amendment1`을 사용해 **23개 전체**를 요구한다.

중요한 항목을 쉬운 말로 정리하면 다음과 같다.

| ID | 쉽게 말한 시험 내용 |
|---|---|
| F1 | SPI 명령이 0x0B이고 주소·dummy·데이터 길이가 정확한가 |
| F2 | CS와 SCLK가 SPI mode 0 타이밍을 지키는가 |
| F3 | 읽는 페이지 주소와 PRBS 정답 시드가 같은 페이지를 가리키는가 |
| F4 | 샘플링 위상을 움직여도 프레이밍이 갑자기 깨지지 않는가 |
| F5 | Flash 출력 지연을 바꿨을 때 예상한 성공·실패 경계가 나타나는가 |
| F6 | 비트 하나를 틀리게 만들면 error count도 정확히 1인가 |
| F7 | 완료 신호가 오지 않으면 watchdog timeout 후 안전하게 끝나는가 |
| F8 | 잘못된 N 또는 B 설정을 실행 전에 거부하는가 |
| F9 | Flash가 연결되지 않은 상황을 예상한 오류 형태로 보여주는가 |
| F10 | N과 B의 최소·최대 경계가 정상 동작하는가 |
| F11 | BASE_SECTOR를 옮기면 SPI 주소와 PRBS 시드가 함께 이동하는가 |
| F12 | Flash 마지막 주소를 넘는 요청을 거부하고 정확한 끝 주소는 허용하는가 |
| W1 | 잘못된 SPI 명령을 공식 모델이 조용히 정상 처리하지 않는가 |
| W2 | CS 간격 위반을 공식 모델의 timing assertion이 실제로 검출하는가 |
| C1~C6 | reset, ID, 위상 증감, busy 차단, 명령 오류, sticky flag가 계약대로인가 |
| I1~I3 | 호스트의 한 스텝 흐름, 오류 합계, invalid 결과 저장이 연결되는가 |

상세 PASS 조건은 반드시 S-3 원문을 따른다. 이 표는 이해를 돕기 위한 요약이며 기준을
대체하지 않는다.

## 8. 테스트 이름 규칙

모든 cocotb 테스트 함수는 다음 이름을 사용한다.

```text
test_<항목ID>_<설명>
```

예시:

```python
@cocotb.test()
async def test_F2_mode0_timing(dut):
    ...
```

```python
@cocotb.test()
async def test_C1_reset_and_id(dut):
    ...
```

이 규칙은 단순한 파일 정리 방식이 아니다. `sim/check_coverage.py`가 `results.xml`에서
`test_F2_`, `test_C1_` 같은 이름을 찾아 어떤 항목이 실행됐는지 판단한다. 이름을 다르게
쓰면 테스트가 실제로 실행돼도 커버리지에서는 누락으로 표시된다.

또한 커버리지 23/23은 테스트 이름이 존재한다는 뜻일 뿐이다. `assert True`만 적어도 항목은
covered로 잡힐 수 있으므로, assertion이 S-3의 값을 실제로 측정하는지는 별도 코드 리뷰가
필요하다.

## 9. 제안하는 `sim/tb/` 구조

다음 구조는 이 문서의 작업 편의를 위한 제안이다. 기존 저장소 관례와 cocotb 2.1 runner를
확인한 뒤 이름을 확정한다.

```text
sim/tb/
├── conftest.py 또는 runner.py
├── test_flash_spi.py
├── test_core.py
├── test_integration.py
├── helpers/
│   ├── clock_reset.py
│   ├── spi_monitor.py
│   └── flash_model_adapter.py
└── vendor/
    └── README.md
```

- `test_flash_spi.py`: F 항목
- `test_core.py`: C 항목
- `test_integration.py`: I 항목
- `spi_monitor.py`: MOSI에서 명령·주소·dummy·payload를 해석
- `vendor/README.md`: 공식 모델의 출처, 정확한 부품명, 버전, 라이선스와 설치 방법 기록

공식 모델 파일의 재배포가 허용되지 않으면 저장소에 모델 자체를 커밋하지 않는다. 대신
사용자가 어디에서 받아 어느 경로에 두어야 하는지 README에 적고, 파일이 없을 때는 명확한
오류로 종료하게 한다.

## 10. 단계별 작업 계획

### 단계 A. 환경 확인

- 가상환경 활성화
- Python, cocotb, pytest, iverilog 버전 기록
- 기존 `sim/smoke/` 4개 회귀가 여전히 PASS하는지 확인

기존 smoke 실행 명령은 `docs/build_reproduction.md`와 각 TB 헤더를 따른다.

### 단계 B. 최소 cocotb 시험 1개

처음부터 Winbond 모델을 붙이지 않는다. `flash_top_spi`에 clock과 reset을 넣고, reset 뒤
출력값을 확인하는 가장 작은 테스트 하나를 만든다.

목표는 RTL 기능 전체 검증이 아니라 다음 연결을 확인하는 것이다.

```text
pytest 또는 runner 실행
→ iverilog compile
→ vvp 실행
→ cocotb가 DUT handle 획득
→ assertion 실행
→ results.xml 생성
```

### 단계 C. 기존 smoke를 cocotb로 이관

`sim/smoke/tb_flash_spi_smoke.v`에 이미 있는 검사를 참고하되 Verilog 코드를 그대로 번역만
하지 않는다. 각 검사를 S-3의 ID와 연결하고 Python assertion이 실제 신호를 관찰하게 한다.

추천 시작 순서는 다음과 같다.

1. F8: 잘못된 설정 거부
2. F9: MISO 무응답 서명
3. F6: 단일 비트 오류 정확 계수
4. F1: SPI 프레임 직접 디코드
5. F2~F5, F7, F10

F8부터 시작하는 이유는 벤더 모델 없이 입력과 상태 신호만으로 확인할 수 있고 실행 시간이
짧기 때문이다.

### 단계 D. Core 시험 이관

기존 `sim/smoke/tb_core_smoke.v`의 검사를 C1~C6으로 나눠 작성한다. reset, 레지스터 값,
busy 중 명령 무시, sticky flag와 정상 복구를 각각 독립 테스트로 만든다.

### 단계 E. Winbond 공식 모델 통합

정확한 W25Q64 부품 접미와 모델 파일을 확인한다. 프로젝트 대상은 W25Q64JV로 기록되어
있지만, 실제 칩 마킹과 데이터시트, 공식 모델 지원 부품명이 일치하는지 확인해야 한다.

모델을 compile source에 추가한 뒤 먼저 간단한 0x9F JEDEC ID 트랜잭션으로 모델이 실제로
구동되는지 확인한다. 기대 응답은 프로젝트의 W25Q64JV 기준 `EF 40 17`이다.

그다음 F1·F2·F3·F5와 W1·W2를 공식 모델을 사용하는 경로로 실행한다. 공식 모델이 출력한
warning 또는 timing violation을 무조건 숨기지 말고 테스트 결과에 포함한다.

### 단계 F. BASE_SECTOR 항목

수정안 #1의 승인 및 RTL 구현 상태를 확인한다.

- 미승인 또는 미구현: F11·F12는 제외 사실을 리포트 선두에 표시하고 21/21을 목표로 한다.
- 승인 및 구현 완료: F11·F12를 작성하고 `--amendment1`로 23/23을 확인한다.

F11은 BER만 확인하면 안 된다. PRBS 패턴이 1,024섹터마다 반복되므로 상위 주소 비트가
잘려도 BER=0으로 보일 수 있다. 따라서 MOSI의 실제 주소를 디코드하는 assertion과 BER
assertion을 둘 다 둔다.

### 단계 G. 통합과 최종 회귀

I1~I3을 작성하고 모든 테스트를 같은 실행에서 돌린다. 최종 PASS와 커버리지 결과가 서로
다른 실행에서 나온 것이면 G1 증거로 사용하지 않는다.

## 11. 회귀 실행과 커버리지 확인

실제 runner를 만든 뒤 실행 명령을 이 절에 확정하여 기록한다. 목표 형태는 다음과 같다.

```bash
source ~/.venvs/flash-cocotb/bin/activate
cd /mnt/c/Users/418cj/flash-margin-bench

# 실제 명령은 구현한 runner/Makefile에 맞춰 확정
pytest -v sim/tb/

# 수정안 #1 미승인
python3 sim/check_coverage.py --results sim/build/results.xml

# 수정안 #1 승인 후
python3 sim/check_coverage.py --results sim/build/results.xml --amendment1
```

성공 조건은 다음 두 가지가 모두 성립하는 것이다.

```text
cocotb 회귀: 모든 테스트 PASS
coverage: 21/21 또는 23/23 PASS
```

테스트가 FAIL하면 FAIL을 없애기 위해 기준을 바꾸지 않는다. 먼저 다음 중 어디가 원인인지
분류한다.

1. RTL 결함
2. cocotb 테스트의 잘못된 기대값
3. clock/reset 또는 simulator 설정 문제
4. Winbond 모델 사용법 또는 timing parameter 문제
5. S-3 기준과 현재 RTL 계약의 승인 상태 불일치

## 12. 남겨야 할 산출물

### 코드 산출물

- `sim/tb/`의 cocotb 테스트 코드
- simulator runner 또는 Makefile
- 공통 clock/reset, SPI monitor와 모델 adapter
- 공식 모델 설치 안내 문서

### 자동 결과

- `sim/build/results.xml`
- 전체 cocotb 실행 로그
- `sim/check_coverage.py` 출력
- 실패 시 assertion 메시지와 필요한 파형

`sim/build/`가 Git ignore 대상인지 확인한다. 생성물 전체를 무조건 커밋하지 않고, 프로젝트가
요구하는 최종 증거만 `docs/results/captures/g1/`에 승격한다.

### G1 증거 문서

다음을 한 묶음으로 남긴다.

- 실행한 Git commit hash
- 실행 날짜와 WSL 환경
- Python, cocotb, iverilog 버전
- Winbond 모델의 정확한 파일명과 판본
- 수정안 #1 적용 여부
- 전체 PASS/FAIL 결과
- 커버리지 `21/21` 또는 `23/23`
- 실행 로그와 커버리지 결과가 같은 회귀 실행에서 나온 증거

어서션이 기준을 제대로 검사하는지는 한영웅이 리뷰하고 `docs/spec/s3.g1_review.md`에
판정한다. 자동 회귀 PASS와 리뷰가 모두 끝난 뒤 박지민이 블록 승인을 집행한다.

## 13. 가장 먼저 할 작은 작업

설치 다음의 실제 첫 목표는 **23개 전체 구현이 아니라 cocotb 파이프라인 1개 완주**다.

```text
1. 기존 smoke 4종 PASS 확인
2. sim/tb/ 생성
3. flash_top_spi compile source 등록
4. clock/reset만 넣는 최소 테스트 작성
5. test_F8_invalid_config_rejected 작성
6. results.xml 생성 확인
7. check_coverage.py를 실행해 나머지가 MISSING으로 보이는지 확인
```

7번에서 FAIL이 나오는 것이 이 단계에서는 정상이다. F8 하나만 작성했으므로 나머지 항목이
누락됐다고 정확하게 알려줘야 커버리지 검사기가 제대로 연결된 것이다.

첫 작업의 성공 기준:

```text
F8 테스트 자체는 PASS
results.xml에 test_F8_... 이름이 존재
check_coverage.py는 F8을 covered로 표시
나머지 항목은 MISSING으로 표시
```

## 14. 현재 blocker와 팀에 확인할 것

### 14.1 Winbond 공식 모델 요청 현황

- 신청일: 2026-09-15
- 신청 경로: Winbond 공식 홈페이지 `Technical Support`
- Document Type: `Verilog Model`
- Product Line / Family: `Code Storage Flash / QSPI NOR`
- Winbond Part Number: `W25Q64JVBYIQ`
- Your Application: `Education`
- 요청 목적: 대학 연구 프로젝트에서 cocotb와 Vivado를 이용해 W25Q64JV SPI 동작을
  비상업적으로 시뮬레이션하고 RTL을 검증하기 위함
- 요청 내용: W25Q64JV-Q 계열의 공식 Verilog 행동 모델, 시뮬레이션 사용 방법 및
  라이선스 조건 제공 요청
- 현재 상태: **기술지원 요청 제출 완료, 확인 메일 또는 Winbond 담당자 회신 대기**

아직 모델 파일을 받은 것은 아니다. 회신을 받으면 정확한 파일명, 모델 판본, 지원 부품명,
시뮬레이터 요구사항과 재배포 가능 여부를 이 로그에 추가한다. 비밀번호, 인증 코드, 개인 연락처
등 계정 정보는 프로젝트 저장소에 기록하지 않는다.

### 14.2 남은 blocker

1. Winbond의 회신과 공식 W25Q64 행동 모델 파일 수령을 기다려야 한다.
2. 실제 칩의 정확한 접미와 공식 모델 지원 대상이 일치하는지 확인이 필요하다.
3. 공식 모델의 저장소 재배포 가능 여부를 라이선스에서 확인해야 한다.
4. BASE_SECTOR 수정안 #1의 팀 승인 및 RTL 구현 상태를 확인해야 한다.
5. 수정안 미승인 상태에서 먼저 21개 회귀를 완성할지 팀 일정 확인이 필요하다.

이 blocker가 있어도 환경 확인, 최소 cocotb 시험, S 출처 항목과 F 테스트의 공통 구동 골격은
진행할 수 있다. F1·F2·F3·F5처럼 V 출처로 지정된 항목은 내부 모델로 예비 실행할 수는 있지만,
그 결과를 최종 통과로 기록하지 않는다. 공식 모델이 필요한 V 항목의 최종 판정은 모델 확보
시점까지 보류한다.

## 15. 완료의 정의

다음 조건을 모두 만족해야 내 cocotb 작업이 완료된 것이다.

- `sim/tb/`에서 회귀를 한 명령으로 다시 실행할 수 있다.
- S-3의 활성 항목이 전부 실제 assertion으로 구현되어 있다.
- 모든 활성 테스트가 PASS한다.
- `results.xml`이 생성된다.
- `check_coverage.py`가 21/21 또는 23/23 PASS한다.
- 공식 모델 대상 항목은 실제 Winbond 모델로 실행했다.
- 버전, commit hash, 모델 판본과 실행 조건이 기록되어 있다.
- 한영웅의 assertion 리뷰가 완료됐다.
- 박지민의 블록 승인과 G1 증거가 기록됐다.

단순히 cocotb 설치가 성공하거나 예제 하나가 PASS한 상태는 **환경 구축 시작**이지 G1
완료가 아니다.
