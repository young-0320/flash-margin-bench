# 8. P/E 엔진 스펙 회신 검토와 개념 정리

- 작성일: 2026-09-20
- 작성: 박지민
- 관련 문서: `docs/spec/s1.wear_bench_spec.md`
- 관련 시험: `docs/spec/s4.blackbox_tb.md`, `host/tests/`
- 문서 성격: **P/E 엔진 스펙 회신을 읽고 이해한 내용과 구현 전 확인 사항을 정리한 학습·검토 로그**
- 주의: 이 문서는 실제 엔진 구현 완료 기록이 아니다. 확정된 결정과 아직 회신이 필요한 항목을
  구분해 기록한다.

---

## 1. 이 문서를 작성한 이유

P/E 엔진 스펙 회신에는 체크포인트, tally, 전원 장애 복구, 재소거, A/B 로그, UART 명령
프로토콜 등 여러 개념이 한꺼번에 들어 있었다. 각 문장의 뜻을 이해하지 않은 상태에서 단순히
동의하면 다음 문제가 생길 수 있다.

1. 누적 cycle과 추가 실행 cycle을 혼동해 계획보다 많은 P/E 스트레스를 줄 수 있다.
2. 상태 조회 명령이 실제 Erase까지 수행해 의도하지 않게 Flash를 변경할 수 있다.
3. Program 직후 검사와 Erase 직후 검사를 한 시점의 결과처럼 섞어 기록할 수 있다.
4. UART 명령이 손상되거나 중복 전송됐을 때 파괴적인 동작이 두 번 실행될 수 있다.
5. 아직 구체적이지 않은 tally 대안이 공식 규칙으로 굳을 수 있다.

따라서 이 로그에서는 상대에게 보낼 회신 문장보다 **각 결정이 왜 필요한지 이해하는 것**에
중점을 둔다.

---

## 2. 전체 구조를 먼저 이해하기

이번 P/E 스트레스 시스템은 다음과 같은 구조로 이해했다.

```text
PC의 호스트 프로그램
  - 실험 조건 전달
  - UART 응답과 #WEAR 로그 저장
  - tally와 A 로그를 비교해 복구 위치 판단
        |
        | USB-UART 명령/응답
        v
Zynq PS에서 실행되는 C 프로그램
  - P/E 절차와 체크포인트 정책 수행
  - Flash 명령 실행
  - 상태와 로그 출력
        |
        | PS SPI 또는 PL 측정 SPI
        v
SPI NOR Flash
  - wear 영역에 실제 Program/Erase 스트레스 누적
  - tally 영역에 복구용 진행 표식 저장
```

핵심은 PC, PS C 프로그램, PL RTL, Flash가 서로 다른 역할을 가진다는 점이다.

| 구성 | 주 역할 |
|---|---|
| PC 호스트 | 명령 전송, 로그 저장, 재개 위치의 최종 판단 |
| PS C | P/E 정책, WIP 확인, 시간 측정, 로그 생성 |
| PL | 기존 측정 경로와 PS SPI 사이의 Flash 핀 소유권 전환 |
| Flash | 실제 마모 대상과 tally 기록 저장 |

엔진은 PC 파일시스템에 저장된 과거 A 로그를 직접 읽을 수 없다. 따라서 엔진은 Flash에서 읽은
UID, tally, blank-check 결과 등의 원자료를 반환하고, PC 호스트가 자신의 로그와 비교하여 최종
재개 위치를 결정하는 구조가 자연스럽다.

## 3. 이번 문서에서 자주 나오는 용어

### 3.1 P/E cycle

P/E는 Program/Erase의 약자다. wear loop의 한 cycle은 정해진 영역에 Program과 Erase
스트레스를 한 번씩 가하는 단위다.

### 3.2 WIP

WIP는 Write In Progress 비트다. Program 또는 Erase가 아직 진행 중인지 알려준다.

```text
WIP = 1  Program/Erase 진행 중
WIP = 0  동작 완료
```

전원이 중간에 끊기면 해당 cycle이 완전히 끝났는지 확신할 수 없기 때문에, 복구 시 WIP와 실제
Flash 내용을 함께 확인해야 한다.

### 3.3 체크포인트

P/E를 계속 수행하다가 정해진 누적 cycle에서 멈춰 상태를 기록하고 욕조 곡선 등의 마진 측정을
수행하는 지점이다.

```text
P/E 반복
  -> 체크포인트 도달
  -> 엔진 정지
  -> 로그/상태 확인
  -> wear, near, far 측정
  -> 다음 구간 재개
```

### 3.4 snapshot

Flash를 특정 시점에 읽어서 얻은 상태다. Program 직후의 snapshot과 Erase 직후의 snapshot은
서로 다른 시점의 데이터이므로 섞어 해석하면 안 된다.

### 3.5 tally

Flash 내부에 남기는 거친 진행 표시다. 예를 들어 100 cycle마다 한 바이트를 기록하면 전원이
꺼져 PC 로그를 잃어도 Flash 자체에서 마지막 진행 구간을 복구할 수 있다.

### 3.6 A 로그와 B 로그

- A 로그: 각 wear 섹터의 Program/Erase 수행 시간과 cycle을 남기는 실행 기록
- B 로그: Program 실패 비트, Erase 잔류 비트, 결함 주소 등 무결성 검사 결과

## 4. 체크포인트에서는 엔진이 스스로 멈춘다

체크포인트 도달 여부를 PC가 뒤늦게 감지해 정지 명령을 보내는 방식보다, 엔진이 전달받은
구간만 실행한 뒤 스스로 멈추는 방식을 선택한다.

```text
WEAR START ... cycles=300
```

위 명령을 받으면 엔진은 300 cycle을 실행하고 `checkpoint_due` 상태로 전환한다. 그 뒤 호스트가
로그와 상태를 확인하고 다음 구간을 명시적으로 재개한다.

### 4.1 스스로 멈춰야 하는 이유

1. 정확한 cycle 경계에서 멈출 수 있다.
2. PC의 정지 명령이 늦게 도착해 목표보다 더 마모되는 일을 막을 수 있다.
3. 체크포인트 동안 P/E 로그가 계속 출력되어 UART 버퍼가 넘치는 일을 막을 수 있다.
4. 마진 측정 중 wear 엔진이 같은 Flash를 동시에 건드리는 일을 막을 수 있다.

### 4.2 `cycles`는 누적 목표가 아니라 delta

`cycles`는 현재까지의 누적값이 아니라 **지금부터 추가로 실행할 횟수**다.

예를 들어:

```text
현재 누적 cycle       = 300
다음 체크포인트       = 645
추가로 실행할 cycle   = 645 - 300 = 345
```

따라서 다음 명령은 잘못된 해석이다.

```text
WEAR RESUME cycles=645
```

이 명령을 delta로 해석하면 누적값이 `300 + 645 = 945`가 된다. 올바른 값은 다음과 같다.

```text
WEAR RESUME cycles=345
```

### 4.3 `checkpoint_due`로 바뀌기 전 완료할 것

엔진이 단순히 내부 카운터만 올리고 멈추면 안 된다. 마지막 cycle이 실제로 완료됐음을 확인하고
그 cycle의 로그가 안전하게 호스트로 전달될 수 있는 상태여야 한다.

```text
마지막 Program/Erase의 WIP = 0 확인
-> 완료 cycle 수 확정
-> 마지막 cycle의 A 로그 7행 생성
-> 로그가 UART 송신 경로에 안전하게 들어감
-> SPI idle, CS high, SCLK low 확인
-> checkpoint_due 전환
```

## 5. A 로그 7행의 의미

파일럿 wear 영역은 섹터 0~6의 7개 섹터다. 따라서 정상 완료된 cycle마다 섹터별 A 로그가
한 줄씩, 총 7줄 생긴다.

```text
cycle=100 sector=0 ...
cycle=100 sector=1 ...
...
cycle=100 sector=6 ...
```

전원 차단으로 7줄 중 일부만 저장됐을 수 있다.

```text
cycle=101 sector=0
cycle=101 sector=1
cycle=101 sector=2
전원 차단
```

이 경우 cycle 101을 완전하게 끝난 cycle로 인정하면 안 된다. 같은 cycle 번호의 7개 섹터 행이
모두 있고 각 행의 checksum이 유효해야 **마지막 완전한 A cycle**로 인정한다.

## 6. tally는 왜 필요한가

PC의 로그는 호스트 프로그램 종료, UART 손실, 파일 저장 실패 때문에 사라질 수 있다. tally는
Flash 안에 직접 남으므로 PC 로그와 독립적인 복구 근거가 된다.

100 cycle마다 tally 한 바이트를 기록한다고 가정하면 다음과 같다.

```text
초기 상태:     FF FF FF FF FF ...
100 cycle:     00 FF FF FF FF ...
200 cycle:     00 00 FF FF FF ...
300 cycle:     00 00 00 FF FF ...
```

`00`이 세 개이면 최소한 300 cycle 지점까지 tally 표시가 진행됐다고 볼 수 있다.

### 6.1 왜 두 벌을 두는가

tally를 A와 B 두 벌로 저장하면 전원 차단이 한쪽 기록 도중 발생했을 때 다른 쪽과 비교할 수 있다.

```text
tally A = 500
tally B = 400
```

두 tally는 모두 100 cycle 눈금을 사용한다. 차이가 한 칸, 즉 100 이하이면 한쪽을 먼저 쓴 뒤
전원이 끊긴 상황으로 설명할 수 있으므로 큰 값을 사용하되 불일치를 기록한다.

```text
차이 <= 100  -> 큰 값으로 병합하고 mismatch 기록
차이 > 100   -> 자동 선택하지 않고 중단
```

차이가 100보다 크면 단순한 기록 순서나 순간 전원 차단만으로 설명하기 어렵기 때문이다.

### 6.2 tally와 A 로그는 단순히 큰 값을 고르면 안 된다

tally는 100 cycle 단위지만 A 로그는 매 cycle을 기록한다. 두 자료의 해상도가 다르다.

예:

```text
tally = 300
A 로그 마지막 완전 cycle = 347
```

이는 정상일 수 있다. 300 tally를 쓴 뒤 47 cycle이 더 진행됐지만 아직 다음 400 tally 시점에
도달하지 않았기 때문이다.

따라서 다음 차이를 계산한다.

```text
d = A 로그의 마지막 완전 cycle - tally 병합값
```

이해한 판정의 핵심은 다음과 같다.

| 조건 | 의미 |
|---|---|
| `0 <= d < 100` | 정상적인 tally 해상도 범위. A 로그를 기준으로 재개 가능 |
| `d < 0` | tally가 A 로그보다 앞섬. 호스트 로그 유실 가능성 확인 필요 |
| `d >= 100` | tally가 한 칸 이상 뒤처짐. 다음 tally 바이트와 쓰기 상태 확인 필요 |

최종 판단은 PC 호스트가 수행한다. 엔진은 tally 두 벌, mismatch, 다음 tally 바이트, 쓰기 가능
여부, UID와 blank-check 결과를 반환한다.

### 6.3 tally 부분 Program과 아직 확정하지 않은 대안

현재 계획은 tally 섹터를 매번 Erase하지 않고, 100 cycle마다 지워진 바이트 하나를 `0x00`으로
추가 Program하는 방식으로 이해했다.

```text
100 cycle  -> 첫 번째 바이트 Program
200 cycle  -> 같은 페이지의 두 번째 바이트 Program
300 cycle  -> 같은 페이지의 세 번째 바이트 Program
```

같은 페이지에 여러 번 부분 Program했을 때 실제 칩에서 이전 tally가 유지되고 새 바이트가
안정적으로 기록되는지는 파일럿에서 확인해야 한다.

원문에는 이 방식이 성립하지 않을 때 “페이지당 1바이트 등 대안”을 사용한다고 되어 있다.
하지만 `등`이라는 표현만으로는 다음을 결정할 수 없다.

- 각 페이지의 어느 바이트를 쓸지
- 한 mark가 몇 cycle을 뜻하는지
- 섹터 하나가 가득 차면 다음 영역을 어디에 둘지
- tally A/B를 어떻게 배치할지
- 기록 도중 전원이 끊겼을 때 어떤 규칙으로 복구할지

따라서 이 대안은 지금 공식 규칙으로 동결하지 않는다. 우선 현재 방식을 실칩 파일럿에서
검증하고, 실제 실패가 확인되면 결과를 근거로 배치, 용량, 기록 간격과 복구 규칙을 구체적으로
정해야 한다.

## 7. `wear_resume()`와 `reerase()`를 분리하는 이유

### 7.1 `wear_resume()`의 역할

`wear_resume()`는 이름 때문에 P/E를 바로 재시작하는 함수처럼 보일 수 있지만, 이번 회신에서는
복구 판단에 필요한 자료를 읽어 반환하는 조회 경계로 유지하는 방향을 선택했다.

```text
UID
tally A/B
tally mismatch
다음 tally 바이트
tally 쓰기 가능 여부
live blank-check 결과
```

호스트는 이 자료와 자신의 A 로그를 비교해 어디서 재개할지 판단한다.

### 7.2 조회와 재소거를 한 함수에 넣으면 생기는 문제

`wear_resume()`을 단순 조회 목적으로 호출했는데 내부에서 자동 Erase까지 실행하면 Flash 상태가
비가역적으로 바뀐다.

```text
의도: 현재 상태만 확인
실제: wear_resume() 호출과 동시에 특정 섹터 Erase
```

또한 다음 두 문제를 따로 시험하기 어려워진다.

1. 부분 소거 상태를 올바르게 찾아냈는가.
2. 찾아낸 섹터를 재소거하는 기능이 올바르게 동작했는가.

그래서 조회는 `wear_resume()`, 실제 복구 Erase는 별도의 명시적 `reerase()`로 분리한다.

### 7.3 `reerase()`의 안전 조건

`reerase()`는 실제 Flash를 지우는 파괴적 명령이다. 단순히 wear 영역 안이라는 이유만으로
실행해서는 안 된다.

최소한 다음 조건이 필요하다.

- 엔진이 running 상태가 아니다.
- 방금 수행한 live 검사에서 복구가 필요한 정확한 섹터가 확인됐다.
- 요청한 섹터가 그 검출 결과와 정확히 일치한다.
- 대상이 wear 영역 안에 있고 near, far, tally 영역과 겹치지 않는다.
- 다른 Program/Erase가 진행 중이지 않다.
- 명령 checksum, 요청 번호와 범위 검사가 유효하다.

재소거 후에는 WIP가 0이 될 때까지 기다리고 다시 live blank check하여 실제로 깨끗하게
지워졌는지 확인한다. 자동 재시도는 하지 않고 결과를 기록한다.

### 7.4 재소거를 일반 P/E cycle에 더하지 않는 이유

정상 P/E cycle은 Program과 Erase가 한 쌍이다. 복구 재소거는 중단된 상태를 정리하기 위한
추가 Erase 한 번이므로 완전한 P/E 한 쌍이 아니다.

따라서:

```text
wear_loop_cycles       -> 증가시키지 않음
area_cumulative_cycles -> 일반 P/E 한 회처럼 더하지 않음
reerase_count          -> 별도로 증가
```

그렇다고 재소거를 기록에서 숨기면 안 된다. 추가 Erase도 물리적 스트레스를 주기 때문에 대상,
횟수, 시간, 성공 여부를 별도 recovery event로 남겨야 한다.

### 7.5 ±1 cycle 불확실성의 의미

±1은 재소거 한 번을 P/E 한 번으로 센다는 뜻이 아니다. 전원이 꺼진 순간 진행 중이던 cycle이
완료됐는지 알 수 없어서 생기는 불확실성이다.

```text
300 cycle 완료는 확실
301번째 cycle 도중 전원 차단
-> 실제 스트레스는 300 또는 301 cycle 상당일 수 있음
-> cycle_uncertainty = 1
```

## 8. Program 직후 검사와 Erase 직후 검사

검사 cycle에서는 두 개의 서로 다른 snapshot이 필요하다.

```text
Program
-> Program 직후 readback
-> program_fail_bits 계산
-> Erase
-> Erase 직후 blank read
-> erase_residual_bits 계산
```

### 8.1 Program 직후

파일럿 패턴이 `0x00`이면 모든 비트가 0이어야 한다.

```text
기대값: 00000000
실제값: 00010000
```

1로 남은 비트는 제대로 Program되지 않은 비트이며 `program_fail_bits`에 포함한다.

### 8.2 Erase 직후

Erase 후에는 모든 비트가 1이어야 한다.

```text
기대값: 11111111
실제값: 11101111
```

0으로 남은 비트는 제대로 지워지지 않은 비트이며 `erase_residual_bits`에 포함한다.

### 8.3 두 count를 하나의 snapshot에서 계산하면 안 되는 이유

Program 직후와 Erase 직후는 Flash 내용이 달라진 서로 다른 시점이다. Program 직후 값을 읽어
놓고 Erase 뒤에도 같은 캐시를 재사용하면 실제 Erase 결과를 검사하지 못한다. `blank_check`는
호출될 때마다 실제 Flash를 다시 읽어야 한다.

또한 다음 등식은 같은 `0x00` snapshot을 0과 1로 나누어 셀 때만 성립한다.

```text
0인 비트 수 + 1인 비트 수 = 전체 비트 수
```

Program 직후의 `program_fail_bits`와 Erase 직후의 `erase_residual_bits`는 서로 다른 두
snapshot에서 가져오므로 두 값을 더해 전체 비트 수가 된다고 요구해서는 안 된다.

## 9. B 로그에서 발견한 경계 문제

B 로그에는 두 count가 있다.

```text
program_fail_bits=<n>
erase_residual_bits=<n>
```

두 count는 각각 Program 직후와 Erase 직후 snapshot에서 가져오는 것으로 이해했다. 하지만
상세 위치 필드는 한 벌뿐이다.

```text
defect_addrs=...
worst_page_idx=...
worst_page_bits=...
```

예를 들어:

```text
Program 실패 주소 = 0x0010, 0x0020, 0x0030
Erase 잔류 주소   = 0x0100, 0x0200

Program 최악 페이지 = 12번, 8비트
Erase 최악 페이지   = 35번, 4비트
```

현재 문법만으로는 단일 `defect_addrs`와 worst-page 필드에 어느 결과를 넣을지 알 수 없다.

가능한 해석은 다음과 같다.

1. Program 실패 주소만 기록한다.
2. Erase 잔류 주소만 기록한다.
3. 두 주소를 합집합으로 기록한다.
4. 한 행 안에서 Program과 Erase 필드를 분리해 모두 기록한다.

두 B 행으로 늘리면 “B 로그 정확히 1행”이라는 기존 기준과 충돌할 수 있다. 따라서 두 phase를
모두 보존해야 한다면 다음처럼 한 행 안에서 필드를 분리하는 공식 문법이 필요하다.

```text
program_defect_addrs=...
program_worst_page_idx=...
program_worst_page_bits=...
erase_defect_addrs=...
erase_worst_page_idx=...
erase_worst_page_bits=...
```

이 부분은 임의로 구현하지 않고 정본에서 확정받아야 한다.

## 10. PS C와 PL pin mux를 선택한 이유

P/E 반복 정책, WIP timeout, 체크포인트, 복구 규칙은 변경 가능성이 높다. 이를 모두 RTL FSM으로
구현하면 규칙이 바뀔 때마다 RTL 수정, Vivado 재합성, cocotb 보강이 필요하다.

PS bare-metal C에 정책을 두면 코드 수정과 시험이 상대적으로 쉽고, `XTime`으로 Program/Erase
시간을 측정할 수 있다.

하지만 P/E용 PS SPI와 기존 욕조 곡선 측정용 PL SPI가 같은 Flash 핀을 사용해야 한다. 매번 다른
bitstream을 올리면 체크포인트마다 보드 재프로그램과 초기화가 개입한다. 따라서 하나의
bitstream 안에서 Flash 핀 소유권만 선택하는 최소 mux를 PL에 두는 방향을 선택했다.

```text
P/E 구간       -> PS SPI가 Flash 핀 소유
마진 측정 구간 -> PL SPI가 Flash 핀 소유
```

mux는 다음 안전 조건이 필요하다.

- PS와 PL이 모두 idle일 때만 전환
- CS가 high이고 SCLK가 low일 때만 전환
- 두 master가 동시에 Flash를 구동하지 못하도록 상호 배제
- reset 중 안전한 기본 소유자와 핀값 정의

## 11. UART 명령 채널

명령 채널은 새로운 케이블이 아니라 기존 USB-UART를 양방향으로 사용하는 텍스트 프로토콜이다.

```text
PC -> 보드: 실행 명령
보드 -> PC: 성공/거부 응답과 실험 로그
```

이 방식을 사용하면 base sector, 섹터 수, pattern, 다음 구간 cycle 수를 바꿀 때마다 C 소스와
ELF를 다시 빌드할 필요가 없다.

### 11.1 외부 명령과 내부 경계

원문에 있는 내부 경계는 다음 일곱 개다.

```text
wear_start()
wear_status()
wear_resume()
blank_check()
tally_read()
tally_dump()
uid_read()
```

복구 Erase를 조회와 분리하기 위해 `reerase()`를 별도 경계로 추가하는 방향을 선택했다.

예상 명령 예시는 다음과 같다.

```text
WEAR START base=0 n_sectors=7 pattern=0x00 cycles=300 req=17 sum=<4hex>
WEAR STATUS req=18 sum=<4hex>
WEAR RESUME cycles=345 req=19 sum=<4hex>
WEAR REERASE base=3 n_sectors=1 req=20 sum=<4hex>
```

### 11.2 접두사 구분

같은 UART에 명령, 응답과 로그가 섞이므로 앞부분으로 종류를 구분한다.

| 접두사 | 의미 |
|---|---|
| `WEAR` | 호스트가 보드에 보내는 명령 |
| `OK` | 보드가 보낸 성공 응답 |
| `REJECT` | 보드가 보낸 거부 응답 |
| `#WEAR` | 보드가 출력한 실험 로그 |

### 11.3 입력 명령에도 checksum이 필요한 이유

원래 명령이 다음과 같다고 가정한다.

```text
cycles=300
```

통신 오류로 숫자가 `800`으로 바뀌면 계획보다 500 cycle을 더 수행할 수 있다. 출력 로그의
checksum만으로는 이미 잘못 실행된 명령을 막을 수 없다. 따라서 Flash를 바꾸는 입력 명령도
실행 전에 checksum을 확인해야 한다.

### 11.4 `req` 요청 번호와 중복 방지

호스트가 `req=20`인 재소거 명령을 보냈고 보드는 실행했지만, 응답만 유실될 수 있다. 호스트가
같은 명령을 재전송했을 때 보드가 다시 Erase하면 추가 스트레스가 생긴다.

```text
req=20 최초 수신 -> 한 번 실행하고 결과 저장
req=20 재수신   -> 실제 동작은 다시 실행하지 않음
```

보드는 이전 결과를 반환하거나 명시적으로 중복 요청을 거부해야 한다.

### 11.5 명령 실행 전 확인 순서

```text
문법 확인
-> checksum 확인
-> req가 신규 요청인지 확인
-> base/n_sectors/cycles 범위 확인
-> 현재 state에서 허용되는 명령인지 확인
-> 파괴적 명령의 추가 guard 확인
-> 실제 실행
```

응답에는 `req`와 보드가 파싱한 주요 인자를 되돌려 호스트가 원래 의도와 일치하는지 확인할 수
있게 한다.

### 11.6 host TB의 음성 대조

여기서 음성 대조는 소리가 아니라 negative test, 즉 일부러 잘못된 입력을 넣는 시험이다.

```text
잘못된 checksum       -> REJECT되는가
같은 req 재전송       -> 파괴 동작이 반복되지 않는가
범위 밖 섹터          -> REJECT되는가
running 중 START      -> REJECT되는가
근거 없는 REERASE     -> REJECT되는가
```

## 12. 정본 기본값과 내가 따로 결정하지 않아도 되는 세부사항

다음은 `docs/spec/s4.blackbox_tb.md` 등의 정본과 기존 parser/TB가 이미 규정한 형식을 그대로
따르는 항목이다.

- H/A/B 로그 행의 기본 문법
- 로그 본문 checksum 방식
- `REJECT <code>` 오류 코드
- `defect_addrs` 인코딩
- 온도값 `die_temp_mc`와 미확보 시 빈 값
- timestamp 단위와 폭
- `t_program_us` 정의
- 공통 필수값을 `#WEAR H` 세션 헤더에 기록하는 방식

### 12.1 checksum 바이트 범위

checksum은 로그 문자열의 어느 문자부터 어느 문자까지 포함하는지가 보드와 호스트에서 같아야
한다. 공백이나 줄바꿈 포함 여부가 달라지면 정상 로그도 checksum 불일치로 판정된다. 하지만 이
범위는 정본에 이미 정해져 있으므로 회신에서 새롭게 해석하거나 변경할 필요가 없다.

### 12.2 빈 `die_temp_mc`

온도를 얻지 못했을 때 `die_temp_mc=`처럼 값이 비어 있을 수 있다. 이는 0°C라는 뜻이 아니라
미측정값이라는 뜻이다. 이 파싱 규칙도 정본을 따르면 되며 별도 결정을 내릴 항목은 아니다.

## 13. 구현 전에 상대에게 확인할 네 가지

전체 방향과 별개로 다음 네 항목은 현재 문법만으로 하나의 답을 정할 수 없다.

### 질문 1. B의 두 count는 서로 다른 snapshot이 맞는가

내 이해는 다음과 같다.

```text
program_fail_bits     = Program 직후 readback에서 계산
erase_residual_bits   = 마지막 Erase 직후 blank read에서 계산
```

이를 공식 기준으로 확정할 필요가 있다.

### 질문 2. 단일 결함 주소와 worst-page는 어느 phase인가

B 로그에 count는 두 종류지만 주소와 worst-page는 한 벌뿐이다. Program 결과, Erase 결과,
합집합 중 무엇인지와 두 결과가 모두 필요할 때의 한 줄 문법을 확정해야 한다.

### 질문 3. recovery event는 어디에 어떤 형식으로 남기는가

전원 차단 후 재소거했다면 다음 정보를 보존해야 한다.

```text
대상 섹터
재소거 횟수
소거 시간
성공/실패
발생 이유
cycle_uncertainty
```

이 정보를 `#WEAR RECOVERY` 같은 UART 로그로 남길지, 별도 파일이나 기존 문서에 남길지 공식
위치와 문법이 필요하다.

### 질문 4. 파괴적 UART 명령 보호를 공식 요구사항으로 둘 것인가

`START`, `RESUME`, `REERASE`에 checksum과 단조 증가 req를 적용하고, 중복 요청이 실제 동작을
재실행하지 않도록 할지 확인해야 한다. 손상·중복 명령 거부 시험을 공식 host TB에 포함할지도
같이 확정해야 한다.

이 네 질문은 내가 구현을 맡겠다는 약속이 아니다. 구현자가 서로 다르게 해석할 수 있는 경계를
정본에서 먼저 확정해 달라는 검토 의견이다.

## 14. 확정된 방향과 열린 질문 구분

### 14.1 이번 회신에서 동의한 방향

- 체크포인트에서 엔진이 스스로 멈춘다.
- `cycles`는 다음 체크포인트까지의 delta다.
- 재개 위치의 최종 판단은 호스트가 한다.
- `wear_resume()` 조회와 `reerase()` 실행을 분리한다.
- 재소거는 일반 P/E cycle에 더하지 않고 별도 기록한다.
- 정상 완료 cycle마다 wear 섹터별 A 로그 7행을 남긴다.
- Program 직후와 Erase 직후에 각각 실제 Flash를 읽는다.
- P/E 정책은 PS C, 단일 bitstream을 위한 최소 핀 mux는 PL에 둔다.
- 기존 USB-UART를 런타임 명령 채널로 사용한다.
- 정본과 기존 parser/TB가 정한 기본 로그 문법은 유지한다.

### 14.2 아직 확정이 필요한 항목

- B 로그의 두 snapshot과 상세 주소/worst-page 표현 방식
- recovery event의 정본 위치와 문법
- 파괴적 입력 명령의 checksum·req·중복 방지를 공식 요구사항과 TB에 포함할지
- 현재 tally 부분 Program이 실칩에서 실패했을 때 사용할 구체적인 대체 배치

## 16. 내가 최종적으로 이해한 핵심

이 설계의 핵심은 단순히 Flash를 반복해서 지우고 쓰는 것이 아니다. 장시간 P/E 중 전원이
끊기거나 UART 로그가 유실돼도 **어디까지 확실히 완료했는지 복구할 수 있어야 하고**, 복구
과정에서 실시한 추가 Erase를 정상 P/E 횟수와 섞지 않아야 한다.

또한 결함의 개수만 남기는 것이 아니라 그 값이 **Program 직후인지 Erase 직후인지**를 분명히
해야 한다. 명령과 로그도 손상되거나 중복될 수 있으므로, 결과 로그뿐 아니라 Flash를 실제로
변경하는 입력 명령까지 보호해야 한다.

이번 회신에서 내가 할 일은 엔진 구현을 약속하는 것이 아니라 다음을 명확히 하는 것이다.

1. 내가 동의한 설계 방향과 그 이유를 전달한다.
2. 현재 문서만으로 결정할 수 없는 경계를 구체적인 질문으로 남긴다.
3. 상대의 답을 받은 뒤 정본과 시험 기준이 서로 모순되지 않는지 확인한다.
