## 1. 이번 작업의 목적

cocotb 테스트를 새로 작성하기 전에 다음 두 가지를 먼저 확인했다.

1. WSL에서 Python, cocotb, pytest, Icarus Verilog를 실행할 수 있는가.
2. 현재 RTL이 기존 `sim/smoke/` Verilog 테스트에서는 정상 동작하는가.

이 과정을 먼저 수행하면 이후 cocotb 테스트가 실패했을 때 원인을 다음처럼 분리할 수 있다.

```text
기존 smoke도 실패
→ RTL 또는 기본 시뮬레이터 환경 문제 가능성

기존 smoke는 PASS, cocotb만 실패
→ cocotb runner, 테스트 코드 또는 기대값 문제를 우선 확인
```

이번 작업은 실제 FPGA 보드나 Flash 칩을 사용하지 않는 PC 시뮬레이션이다. Flash에
Erase나 Program을 수행하지 않았으므로 P/E 횟수도 증가하지 않았다.

## 3. 기존 smoke 시험의 의미

기존 smoke 시험은 순수 Verilog로 작성된 임시 최소 회귀다. `iverilog`가 RTL과
테스트벤치를 시뮬레이션 실행 파일로 만들고, `vvp`가 그 가상 회로를 실행한다.

```text
Verilog RTL + Verilog 테스트벤치
        ↓ iverilog
시뮬레이션 실행 파일(.vvp)
        ↓ vvp
신호 동작 검사 및 PASS/FAIL
```

아래 네 시험을 모두 실행했고, 각각 마지막에 `PASS: all checks passed`가 출력됐다.

### 3.1 Core smoke

```bash
cd /mnt/c/Users/418cj/flash-margin-bench/sim/smoke
iverilog -g2005 -o /tmp/tb_core.vvp \
  tb_core_smoke.v unisim_stub.v ../../fpga/rtl/core/*.v \
&& vvp /tmp/tb_core.vvp
```

확인한 기능:

- ID와 레지스터 reset 값
- 위상 증가·감소와 signed `PHASE_POS`
- busy 중 추가 명령 차단
- 잘못된 동시 명령 거부와 `CMD_ERR` sticky
- START/BUSY/DONE 흐름
- 오류 합계와 로그 메모리 접근
- `CFG_ERR`, `TIMEOUT` sticky 및 다음 정상 START에서의 클리어

결과: **PASS**

### 3.2 Flash 내부 smoke

```bash
iverilog -g2005 -o /tmp/tb_flash.vvp \
  tb_flash_smoke.v unisim_stub.v ../../fpga/rtl/flash/*.v \
&& vvp /tmp/tb_flash.vvp
```

확인한 기능:

- PRBS 기대 패턴 생성과 수신 데이터 비교
- 위상 및 경로 지연 변화에서의 프레이밍
- 단일 비트 오류의 정확한 계수
- R11 설정 오류 거부
- R10 watchdog timeout과 정상 복구
- `N=2048` 풀 버퍼 경계

결과: **PASS**

### 3.3 SPI Flash smoke

```bash
iverilog -g2005 -o /tmp/tb_spi.vvp \
  tb_flash_spi_smoke.v unisim_stub.v ../../fpga/rtl/flash/*.v \
&& vvp /tmp/tb_spi.vvp
```

확인한 기능:

- `0x0B Fast Read` 명령, 주소와 dummy clock
- SPI mode 0의 CS, SCLK, MOSI, MISO 흐름
- 주소와 PRBS 기대값의 정합
- Flash 출력 지연 `tCLQV` 변화
- 단일 비트 오류 계수
- 무칩 또는 MISO 단선 시 예상 오류 서명
- 설정 오류, watchdog과 최대 N 경계

결과: **PASS**

이 시험에서 사용한 Flash는 테스트벤치 내부에 작성된 단순 행동 모델이다. 새로 받은 Winbond
공식 `W25Q64JV.v` 모델은 이번 smoke 실행에 사용하지 않았다.

### 3.4 G0 통합 smoke

```bash
iverilog -g2005 -o /tmp/tb_g0.vvp \
  tb_g0_smoke.v unisim_stub.v \
  ../../fpga/rtl/core/*.v ../../fpga/rtl/flash/*.v \
&& vvp /tmp/tb_g0.vvp
```

확인한 전체 흐름:

```text
AXI-Lite 레지스터 설정
→ 위상 이동
→ 측정 START
→ Flash 측정
→ DONE
→ 오류 결과와 읽기별 로그 회수
```

R11 설정 거부가 Core의 `CFG_ERR` sticky로 이어지는 경로와, R10 watchdog이 Core의
`TIMEOUT` sticky로 이어지는 경로도 확인했다.

결과: **PASS**

## 4. 이번 PASS가 의미하는 범위

이번 결과로 다음을 확인했다.

> 현재 Git commit `7f4f2f7`의 RTL은 Icarus Verilog 12.0에서 기존 Verilog smoke 4종이
> 검사하는 기본 조건을 모두 통과한다.

그러나 아직 다음을 완료한 것은 아니다.

- cocotb 테스트 구현
- G1의 활성 항목 21/21 또는 최종 23/23 통과
- Winbond 공식 행동 모델을 사용한 검증
- 실제 FPGA 보드 검증
- 실제 Flash의 전압·온도·열화 검증
- P/E 스트레스 시험

따라서 현재 상태는 **G1 완료가 아니라 cocotb 구현 전 기준선 확보 완료**다.

## 5. Winbond 공식 모델 확보 상태

Winbond에서 다음 파일 묶음을 받았다.

```text
SFCSI
SFDP
SREG
W25Q64JV.v
W25Q64JV_test.v
```

현재 판단:

- `W25Q64JV.v`: 공식 Flash 행동 모델
- `W25Q64JV_test.v`: 제조사가 제공한 예제 테스트벤치
- `SFCSI`, `SFDP`, `SREG`: 모델이 참조할 가능성이 있는 보조 데이터 파일

정확한 사용법과 Icarus 호환성, 모델 판본, 지원 부품, timing assertion 제공 여부 및
재배포 라이선스를 확인하기 전까지 파일 묶음을 그대로 보관한다. 라이선스를 확인하지 않은
상태에서는 모델 파일을 GitHub에 커밋하지 않는다.

## 6. 다음 작업

가장 가까운 다음 목표는 G1 전체 구현이 아니라 cocotb 파이프라인 한 개를 끝까지 연결하는
것이다.

```text
1. sim/tb/ 생성
2. cocotb 2.1 Python runner 작성
3. flash_top_spi와 하위 RTL, unisim_stub 컴파일
4. test_F8_invalid_config_rejected 작성
5. F8 PASS 확인
6. sim/build/results.xml 생성 확인
7. check_coverage.py에서 F8만 covered, 나머지는 MISSING인지 확인
```

F8은 잘못된 측정 설정을 넣었을 때 RTL이 측정을 시작하지 않고 `cfg_err`로 거부하는지
검사한다.

```text
N=0 또는 B<8 또는 B%8!=0
→ cfg_err 발생
→ meas_busy 상승 없음
→ meas_done 발생 없음
→ 이후 정상 설정으로 복구 가능
```

이 최소 시험이 통과한 뒤 기존 smoke 항목을 F, C, I 항목별 cocotb 테스트로 이관하고,
마지막 단계에서 Winbond 공식 모델을 연결한다.
