## 1. 이번 작업의 목적

6번 로그에서 Python, cocotb, Icarus Verilog 환경과 기존 Verilog smoke 시험을 확인했다.
이번 작업에서는 처음으로 cocotb가 실제 Flash RTL을 구동하고 결과를 자동 판정하는 경로를
연결했다.

```text
Python cocotb 테스트
        ↓ 신호 입력과 관찰
Icarus Verilog에서 실행되는 flash_top_spi RTL
        ↓
assertion으로 기대값과 실제값 비교
        ↓
JUnit results.xml과 G1 상태표 생성
```

이번 작업은 PC 안에서 수행한 RTL 시뮬레이션이다. 실제 FPGA 보드와 Flash 칩을 사용하지
않았고, 실제 Flash의 P/E 횟수도 증가하지 않았다.

## 3. F8 — 잘못된 N/B 설정 거부

### 3.1 확인하려는 기능

측정 횟수 `N`과 한 번에 비교할 비트 수 `B`가 잘못됐을 때 RTL은 측정을 억지로 시작하지
않고 `cfg_err`로 거부해야 한다. 잘못된 요청 뒤에도 정상 요청은 받을 수 있어야 한다.

시험한 잘못된 설정은 다음 세 가지다.

| 입력 | 잘못된 이유 |
|---|---|
| `N=0, B=8` | 읽기 횟수는 0일 수 없음 |
| `N=1, B=4` | 최소 burst 길이보다 작음 |
| `N=1, B=100` | byte 단위가 아니므로 8의 배수가 아님 |

각 입력에서 다음을 확인했다.

```text
cfg_err      = 한 clock 동안 1
meas_busy    = 0
meas_done    = 0
meas_timeout = 0
```

그 뒤 `N=1, B=8`의 정상 설정으로 다시 START를 보내 측정이 실제로 시작되는 것도 확인했다.
즉, 오류 요청을 거부한 뒤 RTL이 멈추거나 고장 난 상태로 남지 않는지도 함께 검사했다.

### 3.2 결과

```text
F8 PASS
```

의미: 이번 cocotb가 넣은 세 가지 잘못된 설정은 모두 거부됐고, 그 뒤 정상 설정으로 복구됐다.

## 4. F9 — Flash 무응답 서명

### 4.1 확인하려는 기능

Flash가 없거나 MISO가 단선되어 입력이 계속 0으로 보이는 상황을 모사했다.

```text
spi_miso = 0 고정
N = 2
B = 2,048
```

이 상황은 전송 회로 자체가 멈춘 것이 아니다. SCLK와 CS 동작은 끝까지 진행되지만 수신한
데이터가 기대 PRBS와 다르다. 따라서 기대 동작은 다음과 같다.

- watchdog `TIMEOUT`이 아니라 정상적인 측정 완료로 끝난다.
- `meas_busy`가 내려가고 CS가 비활성 상태로 돌아간다.
- 수신값 0과 기대 PRBS가 다른 비트가 오류로 계산된다.
- 전체 오류 합계와 읽기별 오류 로그가 서로 일치한다.

### 4.2 처음 기대값이 달랐던 이유

처음에는 각 페이지의 명목 PRBS에서 1의 개수만 세어 총 `1,856`을 기대했다. 실제 RTL은
`1,854`를 반환했다. 이것은 RTL 오류가 아니라 기대값 계산에서 정렬 후보를 빠뜨린 것이었다.

`flash_rx`는 세 정렬 후보의 오류 수 `e0`, `e1`, `e2`를 계산한 뒤 가장 작은 값을 보고한다.

```text
e_i = min(e0, e1, e2)
```

따라서 cocotb도 각 페이지에서 `B+2`개의 PRBS 비트를 독립 생성하고, 시작 위치가 0, 1,
2인 세 후보의 1 개수를 비교해 최솟값을 기대값으로 사용하도록 수정했다.

| page | 세 후보의 오류 수 | RTL과 비교할 기대값 |
|---|---|---|
| 0 | 927, 926, 926 | 926 |
| 1 | 929, 928, 928 | 928 |
| 합계 | - | `ERR_BITS=1,854` |

읽기 두 번 모두 오류가 있으므로 `ERR_READS=2`다.

### 4.3 결과

```text
F9 no-Flash signature: err_bits=1854, per_read=[926, 928]
F9 PASS
```

의미: MISO가 계속 0이어도 RTL은 timeout으로 오판하지 않고 측정을 완료했으며, 세 정렬 후보
규칙에 맞는 오류 수를 전체 합계와 읽기별 로그에 정확히 남겼다.

## 5. F6 — 단일 비트 오류 정확 계수

### 5.1 확인하려는 기능

정상 PRBS 응답을 보내는 cocotb SPI Flash 응답기를 만들고, 읽기 번호 2의 payload 19번
비트 하나만 반전했다.

```text
N = 4
B = 64
오염 위치 = read 2, payload bit 19
```

오염되지 않은 읽기는 `e_i=0`, 오염된 읽기만 `e_i=1`이어야 한다. 또한 R8의 세 가지
집계 관계를 함께 확인했다.

```text
R8-1: sum(e_i) = ERR_BITS
R8-2: count(e_i > 0) = ERR_READS
R8-3: 모든 e_i <= B
```

SPI 응답기는 controller 내부의 페이지 번호를 정답으로 사용하지 않는다. 실제 SPI wire에서
`0x0B` 명령과 24비트 주소를 직접 읽고, 그 주소로 PRBS를 독립 생성해 MISO로 응답한다.
따라서 잘못된 내부 신호를 그대로 따라가며 거짓 PASS가 나는 가능성을 줄였다.

### 5.2 결과

```text
F6 single-bit injection:
read=2 bit=19
per_read=[0, 0, 1, 0]
err_bits=1
err_reads=1

F6 PASS
```

의미: 의도적으로 뒤집은 한 비트가 해당 읽기의 오류 한 개로만 기록됐고, 전체 오류 비트 수,
오류가 있는 읽기 수, 읽기별 원시 로그가 모두 일치했다.

## 6. F1 — SPI Fast Read 프레임 규격

### 6.1 확인하려는 기능

F1은 내부 controller 상태를 보는 시험이 아니라 실제 `CS`, `SCLK`, `MOSI` wire를 관찰해
각 읽기 프레임을 직접 해독한다. `N=3`, `B=64` 조건에서 다음을 검사했다.

- command가 `0x0B Fast Read`인가.
- 24비트 주소가 읽기마다 `page(i) x 256`인가.
- 주소 하위 8비트가 0인가.
- dummy byte가 8비트의 `0x00`인가.
- CS가 low인 한 프레임에 SCLK 상승 에지가 정확히 `40+B=104`개인가.

기대 주소는 다음과 같다.

| read index | 기대 주소 |
|---:|---:|
| 0 | `0x000000` |
| 1 | `0x000100` |
| 2 | `0x000200` |

같은 SPI 응답기가 wire에서 해독한 주소로 PRBS를 생성해 응답했으며, 세 읽기의 오류 로그도
모두 0인지 확인했다.

### 6.2 결과

```text
F1 PASS
```

의미: 시험한 세 프레임에서 command, 주소, dummy, 프레임 SCLK 수가 모두 규격과 일치했고
정상 PRBS 응답도 오류 없이 수신됐다.

## 7. F2 — SPI mode 0 타이밍

F2는 `N=3`, `B=64`, 25 MHz 조건에서 실제 `CS`, `SCLK` wire를 관찰했다. CS가
내려가고 올라가는 순간 SCLK가 low인지 확인했으며, CS 하강 후 첫 SCLK 상승까지의
`tSLCH`는 최소 5 ns에 대해 140 ns, 프레임 사이의 `tSHSL1`은 최소 10 ns에 대해
160 ns로 측정됐다.

두 번째 하위 시험은 로컬의 Winbond 공식 `W25Q64JV.v` 모델을 연결했다. 라이선스가 있는
원본은 저장소에 넣지 않고 `WINBOND_MODEL_DIR`로만 지정했으며, runner가 실행용 사본과
PRBS `MEM.TXT`를 `sim/build/vendor_model/`에 생성했다. 모델은 `t_clk=40.000 ns`, 즉
25 MHz를 인식했고 `timing_error=0`을 유지했다. 공식 모델이 반환한 세 번의 읽기도 모두
오류 0이어서 `ERR_BITS=0`, `ERR_READS=0`, `TIMEOUT=0`을 확인했다.

`SECSI.TXT`와 `SFDP.TXT`가 모델 내부 배열보다 짧다는 `$readmemh` 경고와 SREG 배열 방향
경고는 있었지만 파일 열기 실패는 없었고, 메모리 적재와 공식 모델 읽기 assertion은 모두
통과했다.

```text
F2 wire timing: CS-to-first-SCLK=140 ns, CS-high-gap=160 ns
CLK LOCKED: t_clk=40.000 ns
F2 Winbond timing clean
F2 PASS
```

### 7.1 F2 독립 검토 후 보강

초기 F2는 CS 경계와 공식 모델의 `timing_error=0`만 확인해, SCLK 파형의 high/low 폭이나
공식 모델의 타이밍 감시 기능이 실제로 작동하는지는 충분히 증명하지 못했다. 다음 검사를
추가했다.

- 모든 프레임의 SCLK 상승·하강 에지를 직접 관찰한다.
- SCLK high와 low가 각각 18 ns 이상인지 확인한다.
- 연속 상승 에지 사이의 SCLK period가 40 ns 이상인지 확인한다.
- 마지막 SCLK 상승에서 CS 해제까지 3 ns 이상인지 확인한다.
- CS 하강·상승 순간 모두 SCLK가 low인지 다시 확인한다.
- 공식 모델에 들어갈 `MEM.TXT`의 page 0과 page 1에서 서로 달라지는 두 번째 byte까지
  검사하여, 모델이 실제 주소별 PRBS 데이터를 읽고 있음을 확인한다.
- 공식 모델에 의도적으로 2 ns짜리 잘못된 SCLK high pulse를 넣고
  `timing_error=1`이 되는 음성 대조를 추가한다.

마지막 음성 대조가 중요한 이유는 정상 시험의 `timing_error=0`만으로는 모델의 감시기가
꺼져 있어도 PASS할 수 있기 때문이다. 알려진 위반을 실제로 검출함으로써 정상 구간의
무발화 결과를 신뢰할 수 있게 했다. 음성 대조는 모델의 sticky 오류를 세우므로 모든 정상
벤더 시험 뒤에 실행되도록 runner 순서를 배치했다.

```text
F2 wire mode-0 timing PASS
F2 official-model clean timing PASS
F2 deliberate 2 ns timing violation detected PASS

보강 당시 전체 회귀: TESTS=89 PASS=89 FAIL=0 SKIP=0
```

## 8. F3 — 주소와 PRBS 시드 정합

읽기 `i`가 보내는 주소와 RTL이 비교에 사용하는 PRBS 시드는 같은 페이지에서 유도돼야
한다. 주소는 page 1인데 기대 PRBS는 page 0인 식으로 어긋나면 정상 데이터도 대량 오류가
된다.

초기에는 page 0~16을 검사했지만 독립 검토에서 높은 주소 경계 증거가 부족하다고 판단했다.
공식 모델 메모리를 512페이지로 늘리고 page 0부터 page 256까지 서로 다른 PRBS 데이터를
넣어 `N=257`, `B=16`으로 다시 실행했다. `B=16`은 PRBS-15 시드 전체가 비교 데이터에
반영되는 최소 byte 배수 조건이다.

cocotb는 DUT 내부 페이지 카운터를 정답으로 사용하지 않고 실제 MOSI wire를 해독해 주소가
`0x000000`, `0x000100`, ..., `0x010000`인지 확인했다. 특히 page 255의 `0x00FF00`에서
page 256의 `0x010000`으로 넘어가는 주소 바이트 carry를 검사했다. 동시에 Winbond 모델이
해당 주소의 데이터를 반환했을 때 읽기별 오류 257개가 모두 0인지 확인했다.

```text
test_F3_wire_address_selects_matching_vendor_PRBS_page PASS
pages=0..256
addresses=0x000000..0x010000
address carry=0x00FF00..0x010000
per-read errors=모두 0
ERR_BITS=0, ERR_READS=0, TIMEOUT=0
```

의미: 시험한 257개 페이지에서 SPI 주소와 RTL의 기대 PRBS 시드가 같은 페이지를 가리켰고,
주소 바이트 carry 경계도 통과했다. page 257~2,047의 N 경계와 full log buffer는 F10에서
별도로 확인한다.

## 9. F4 — 0~1 UI 샘플 위상 스윕

F4는 데이터가 도착하는 시점과 `clk_sample`의 상대 위상이 바뀌어도 `flash_rx`의 세 후보
프레이밍 재정렬이 갑자기 무너지지 않는지 확인한다. 초기에는 기존 Verilog smoke를 따라
3 ns 간격의 14개 지점을 검사했다. 독립 검토 후 표본 사이의 좁은 실패 구간을 놓칠 가능성을
줄이기 위해 25 MHz의 1UI=40 ns를 0.5 ns 간격으로 다시 나누고 양 경계 근처를 추가했다.

```text
0.1 ns
0.5, 1.0, 1.5, ..., 39.0, 39.5 ns
39.9 ns
총 81개 위상
```

각 지점은 `N=2`, `B=64`, Flash 출력 지연 8 ns 조건으로 정상 PRBS를 읽었다. 모든 지점에서
다음 조건을 요구했다.

- 읽기별 오류 로그가 `[0, 0]`이다.
- `ERR_BITS=0`, `ERR_READS=0`이다.
- `TIMEOUT=0`이다.

### 9.1 결과

```text
F4 81개 위상 test case 모두 PASS
최소 위상 0.1 ns PASS
최대 위상 39.9 ns PASS
위상 전환 구간에서 framing cliff 없음
```

81개의 test case가 모두 F4라는 하나의 승인 항목을 검증하므로, JUnit의 전체 test 수에는
81개가 추가되지만 G1 상태표의 PASS 항목 수에는 F4 한 개가 추가된다. 정확한 0 ns와 40 ns는
modulo 1UI로 같은 위상이고 simulator 동시 에지 순서에 의존하므로, 각각에 가까운 0.1 ns와
39.9 ns로 양쪽 경계를 확인했다.

## 14. 2026-09-19 F5 첫 실행 — 기존 1UI oracle의 오류 발견

공식 Winbond 모델의 출력에 시험 전용 경로 지연을 추가해 F5를 처음 실행했다. 유효 지연

## 15. F7 — R10 워치독 정확 경계와 정상 복구

### 15.1 기존 smoke에서 부족했던 점

기존 Verilog smoke는 `rx_done`을 차단하고 `T_max+200`사이클 안에 TIMEOUT이 나오는지만
확인했다. 따라서 워치독이 계약보다 한 사이클 늦게 동작해도 PASS할 수 있었다. R10 계약은
`T_max=2×N×(B+64)` **이내**에 DONE을 보장하므로 cocotb에서는 정확한 사이클을 센다.

RTL을 검토한 결과 START가 승인된 뒤 다음 사이클부터 `wd_cnt`를 올리면서
`wd_cnt >= t_max`를 비교해 실제 종료가 `T_max+1`이 될 수 있었다. SPI 경로
`flash_spi_ctrl.v`와 루프백 경로 `flash_ctrl.v`를 모두 `wd_cnt >= t_max-1`로 수정했다.

### 15.2 cocotb 검사 내용

`N=2`, `B=64`로 설정해 다음 값을 사용했다.

```text
T_max = 2 × 2 × (64 + 64) = 512 clk_core cycles
```

시험 wrapper가 동기화된 `rx_done` 경로를 강제로 0에 고정한 뒤 다음을 확인했다.

- 정확히 512번째 사이클에 DONE과 TIMEOUT이 동시에 발생한다.
- DONE과 TIMEOUT은 한 사이클 펄스다.
- 종료 시 BUSY=0, CS=high, SCLK=low, CFG_ERR=0이다.
- fault 해제 후 CDC 완료 경로가 idle로 돌아온다.
- 바로 다음 정상 `N=2`, `B=64` 측정이 TIMEOUT 없이 완료된다.
- 복구 측정의 읽기별 오류는 `[0,0]`, `ERR_BITS=0`, `ERR_READS=0`이다.

### 15.3 결과

## 16. F10 — 읽기 수와 버스트 길이 경계의 클린 런

### 16.1 검사 목적과 구성

F10의 기준은 `N=2,048` 풀 로그 버퍼, `B=8` 최소 버스트, `B=2,048` 계약 기본
버스트가 각각 정상 완료되는지 확인하는 것이다. 기존 smoke는 실행 후 오류 합계가 0인지만
확인했으므로, cocotb에서는 세 경계를 독립 시험으로 나누고 다음 조건을 함께 확인했다.

- TIMEOUT과 CFG_ERR 없이 DONE에 도달한다.
- DONE 뒤 BUSY가 내려가고 CS가 해제된다.
- `ERR_BITS=0`, `ERR_READS=0`이다.
- 읽기별 로그 `e_i`가 모두 0이다.
- `sum(e_i)=ERR_BITS`, `count(e_i>0)=ERR_READS`, `e_i<=B`의 R8 조건이 성립한다.

F10은 기준 문서에서 출처가 S(self)인 항목이다. 실제 Winbond 명령 해석을 채점하는 시험이
아니므로 `WINBOND_MODEL_DIR`를 해제하고, 독립 Python 응답기가 각 주소에 맞는 PRBS를
돌려주는 구성으로 실행했다.

### 16.2 `N=2,048` 풀 로그 버퍼 보강

클린 런의 로그 값은 모두 0이므로, 2,048칸을 읽는 것만으로는 주소가 겹치거나 마지막 칸이
기록되지 않은 문제를 놓칠 수 있다. 이를 막기 위해 RX의 로그 쓰기 신호를 관찰하여 다음을
추가로 검사했다.

- 로그 쓰기가 정확히 2,048번 발생한다.
- 쓰기 주소가 `0, 1, ..., 2047` 순서로 한 번씩 나타난다.
- 각 쓰기 데이터가 0이다.
- 완료 후 로그 2,048칸을 모두 읽었을 때 첫 항목과 마지막 항목을 포함해 전부 0이다.

실행 결과는 다음과 같다.

```text
F10 full log: N=2048 B=8 entries=2048 first=0 last=0
test_F10_N2048_full_log_buffer_is_clean_through_last_entry PASS
```

따라서 최대 읽기 수에서 마지막 로그 주소까지 실제 쓰기와 읽기가 완료됐음을 확인했다.

## 17. W1 — 1비트 손상 명령의 공식 Winbond 모델 거부

### 17.1 검사 목적

W1은 정상 Fast Read 명령 `0x0B`의 한 비트가 손상됐을 때 Flash가 이를 정상 읽기로
조용히 받아들이지 않는지 확인하는 시험이다. 다음 두 손상 명령을 사용했다.

```text
0x0B -> 0x0A  (bit 0 반전)
0x0B -> 0x1B  (bit 4 반전)
```

공식 `W25Q64JV.v` 모델은 알 수 없는 opcode를 받으면 `Invalid Opcode`를 출력한 뒤
`$stop`으로 시뮬레이션 전체를 중단한다. 그대로는 후속 오류 계수까지 검사할 수 없으므로,
저장소 밖 라이선스 원본은 변경하지 않고 runner가 만든 실행용 복사본에만 다음 관찰점을
추가했다.

- 잘못된 opcode가 검출됐는지 나타내는 sticky 값
- 마지막으로 거부된 opcode
- 거부 횟수
- `$stop` 대신 현재 CS가 해제될 때까지 대기하는 처리

### 17.2 검사 방법

각 손상 opcode마다 `N=2`, `B=2,048`로 두 프레임을 실행했다. 공식 모델이 잘못된
명령을 거부하면 유효한 읽기 데이터가 나오지 않으므로, DUT 입력 MISO는 결정적인 0으로
고정했다. 이는 실제 부유 배선의 아날로그 거동을 재현하는 것이 아니라, 무응답이 정상
데이터로 오인되지 않는지 검증하기 위한 결정적 음성 대조다.

각 경우 다음을 확인했다.

- 공식 모델이 두 프레임을 모두 거부한다.
- 모델이 기록한 마지막 opcode가 주입한 `0x0A` 또는 `0x1B`와 일치한다.
- 두 읽기의 PRBS 오류 수가 MISO=0일 때의 정확한 기대값 `[926, 928]`과 일치한다.
- `ERR_BITS=1,854`, `ERR_READS=2`이며 TIMEOUT은 발생하지 않는다.
- 따라서 손상 명령이 오류 0의 정상 읽기로 조용히 통과하지 않는다.

### 17.3 실행 중 발견한 시험 순서 문제

첫 실행은 0 ns에서 `vendor_model_present`를 읽어 초기 `Z` 값을 정수로 변환하지 못하고
종료됐다. 이때 SPI 프레임은 아직 시작되지 않았으므로 W1 기능 실패가 아니었다. 클럭 시작과
리셋 완료 후 모델 존재 신호를 확인하도록 순서를 수정한 뒤 다시 실행했다.

### 17.4 결과

```text
Invalid Opcode. (a)
Invalid Opcode. (a)
W1 opcode 0x0A: vendor_rejections=2 per_read=[926, 928] timeout=0

Invalid Opcode. (1b)
Invalid Opcode. (1b)

TESTS=1 PASS=1 FAIL=0 SKIP=0
```

W1 단독 회귀는 PASS로 확정했다. 실행 초기에 보인 `SECSI.TXT`와 `SFDP.TXT`의
`Not enough words` 경고는 공식 모델이 선언한 전체 배열보다 제공 파일의 초기화 데이터가
짧다는 뜻이다. W1에서 사용하는 opcode decode와 거부 횟수, PRBS 오류 계수에는 영향을
주지 않았으며 시험 실패 메시지도 아니다.

현재 `results.xml`은 W1만 선택해 실행한 결과다. W1을 G1 누적 상태표에 반영하려면 다음
단계에서 필터를 해제한 전체 회귀를 한 번 실행해야 한다.

### 17.5 W1 포함 전체 회귀 결과

Winbond 공식 모델을 연결하고 `G1_TEST_MODULES` 필터를 해제해 F1~F10과 W1을 한 번의
동일 실행에서 다시 검사했다. 기존 F 계열은 모두 유지됐고 W1도 PASS로 집계됐다.

따라서 W1의 공식 모델 runtime-copy 계측과 명령 손상 주입이 기존 F1~F10 시험을
회귀시키지 않았음을 확인했다. `INCOMPLETE`는 실패가 아니라 W2·C1~C6·I1~I3가 아직
구현되지 않았다는 뜻이다.

## 2026-09-23 W2 완료 및 C1 착수

W2 tSHSL 시험을 정상 간격 60/100/150ns와 1ns 음성 대조로 실행했다. 정상 간격에서는
타이밍 오류가 없었고, 1ns 대조에서는 모델의 tSHSL 위반이 검출됐다. F1~F10·W1·W2
전체 회귀 결과는 다음과 같다.

```text
F1~F10 PASS, W1 PASS, W2 PASS
PASS 12/21 | FAIL 0 | MISSING 9 | EXCLUDED 2
OVERALL: INCOMPLETE
```

W2의 PASS는 `sim/build/g1_status.md`에 생성된 기계 판정표와 함께 보관한다. 남은
MISSING 항목 중 다음 작업은 `core_top`의 AXI 레지스터를 대상으로 하는 C1이다.

### C1 구현 범위

C1은 실제 Flash나 Winbond 모델을 사용하지 않고, `core_top`을 별도 wrapper로 띄워
리셋 직후의 ID·기본 설정·초기 상태를 읽는다. 시험 파일은
`sim/tb/C1_register_reset_id.py`, wrapper는 `sim/tb/core_cocotb_top.v`에 둔다.

### C1 실행 결과

사용자 환경에서 C1 단독 시험을 실행해 PASS를 확인했다. C1은 ID, `N_READS=100`,
`BURST_BITS=2048`, 초기 locked/idle STATUS, `PHASE_POS=0`을 모두 확인한다.

### C2 착수

C2는 같은 core wrapper를 사용해 `CTRL=PHASE_INC`와 `CTRL=PHASE_DEC`를 보낸다.
`PHASE_POS`가 `0→1→0→0xffffffff(-1)`로 변하는지 확인해 signed 누적과 DEC 방향을
검증한다. 실제 Flash와 보드는 필요하지 않다.

### C2 실행 결과 및 C3 착수

C2 단독 시험에서 `PHASE_POS`가 `+1`, `0`, `-1(0xffffffff)` 순서로 변하는 것을 확인해
PASS했다. 다음 C3는 `PS_BUSY` 중 두 번째 위상 명령과 `MEAS_BUSY` 중 위상 명령이 모두
조용히 무시되고 `CMD_ERR`를 만들지 않는지 검사한다.

### C3 실행 결과 및 C4 착수

C3 단독 시험에서 `PS_BUSY` 중 두 번째 위상 명령과 `MEAS_BUSY` 중 위상 명령이 모두
무시되고 `CMD_ERR`가 0으로 유지되는 것을 확인해 PASS했다. 다음 C4는 잘못된 다중 비트
CTRL 명령을 거부하고 `CMD_ERR`를 sticky로 유지하는지 검사한다.

### C4 실행 결과 및 C5 착수

C4 단독 시험에서 다중 비트 CTRL을 거부하고 `CMD_ERR`를 세운 뒤, 정상 위상 명령 이후에도
그 플래그가 유지되는 것을 확인해 PASS했다. 다음 C5는 `DONE` sticky가 다음 유효 START에서
자동으로 지워지는지 검사한다.

### C5 실행 결과 및 C6 착수

C5 단독 시험에서 `DONE` 펄스를 주입한 뒤 sticky 상태를 확인하고, 다음 유효 START에서
자동으로 클리어되는 것을 확인해 PASS했다. 다음 C6는 `CFG_ERR`와 `TIMEOUT`의 sticky 및
유효 START 복구 규칙을 검사한다.

### C6 실행 결과 및 I1 착수

C6에서는 `CFG_ERR`와 `TIMEOUT`을 오류 상태로 만든 뒤, 잘못된 START가 오류를 지우지
않는지와 다음 유효한 START가 새 측정을 시작할 때 두 sticky 플래그를 지우는지를
확인했다. 시험 순서는 실제 동작과 맞도록 `MEAS_BUSY`를 먼저 세운 뒤 오류를 주입하고,
busy 중인 잘못된 START와 idle에서의 유효 START를 차례로 확인하도록 구성했다. 이
보강 후 C6 단독 시험은 PASS했다.

다음 단계는 실제 `core_top`과 `flash_top`을 한 wrapper로 연결하는 I1 통합 시험이다.
I1은 위상 증가 명령, 측정 START, DONE 대기, 오류 합계와 R8 로그 메모리까지 한 번의
호스트 흐름으로 확인한다. 이 단계에서도 실제 Flash 칩이나 FPGA 보드는 사용하지 않고,
RTL 내부 loopback을 사용한다.

### I1 실행 결과 및 I2 착수

I1 단독 시험을 실행해 PASS를 확인했다. 실제 `core_top`과 `flash_top`을 연결한 통합
wrapper에서 위상 증가 후 START를 발행했고, 측정이 DONE으로 끝나며 TIMEOUT·CFG_ERR가
없고 `ERR_BITS=0`, `ERR_READS=0`, 첫 두 개의 R8 로그 항목도 0인지 확인했다. 따라서
core 레지스터 흐름과 Flash loopback 경로가 한 번의 host step에서 함께 동작한다는
기준선을 확보했다.

다음 I2에서는 같은 통합 경로를 두 번 연속 실행해 각 step의 결과와 R8 로그가 독립적으로
보존되는지 확인한다. 첫 번째 결과가 두 번째 실행으로 덮어써지거나 로그 주소가 섞이면
실제 host 반복 측정에서 잘못된 결과를 기록할 수 있으므로, I2는 이 경계 조건을 확인하는
시험이다.

### I2·I3 실행 결과 및 G1 통합 블록 완료

I2는 통합 loopback에서 host step을 두 번 연속 실행했다. 두 step 모두 DONE까지
정상 종료했고 `ERR_BITS=0`, `ERR_READS=0`, R8의 `e_0`·`e_1`이 0으로 유지됐다.
따라서 두 번째 측정이 첫 번째 결과를 잘못 재사용하거나 로그를 섞지 않는다는 것을
확인했다.

I3는 UART 스윕 행이 일부 유실된 상황을 주입했다. PS의 END가 `valid=1`이어도 PC가
받은 행 수가 `steps` 및 `steps×N`과 다르면 `row_mismatch`로 판정하고, 메인 결과와
읽기별 결과를 각각 `_invalid.csv`, `_invalid_reads.csv`로 보존하는 것을 확인했다.

I1·I2·I3가 모두 PASS했으므로 G1의 통합 블록 구현과 최소 호스트 무효 경로 검증을
완료했다. 다음 확인은 전체 회귀를 한 번 실행한 뒤 `sim/build/g1_status.md`에서
F·W·C·I 항목을 같은 실행 결과로 갱신하는 것이다.

### 최종 G1 상태 기록

Flash/벤더 그룹은 `186/186 PASS`, Core 그룹은 `6/6 PASS`, 통합 그룹은 `3/3 PASS`였다.
세 그룹의 JUnit 결과를 함께 `sim/check_coverage.py`에 입력해 다음 최종 판정을 얻었다.

```text

OVERALL: PASS
```

전체 계획표에는 23개 항목이 있지만 F11·F12는 `BASE_SECTOR` 수정안이 아직 RTL에
구현되지 않아 제외됐다. 따라서 현재 결과는 승인된 21개 항목을 모두 PASS한 상태이며,
F11·F12를 검증했다는 뜻은 아니다.
