## 근거

### 1. 명령은 한 곳 — 런북 편입안은 버렸다

후보 둘. ⓐ 명령을 워크플로 런북으로 편입하고 조작 설명서는 링크만 둔다. ⓑ 조작 설명서를 단일
정본으로 두고 나머지가 링크한다. ⓐ 는 런북이 날짜순으로 쌓이며 서로를 대체한다는 성질(3 → 7 → 12)
때문에 「현행 명령이 어느 런북에 있나」를 매번 뒤져야 하고, `reproduce.py`·분석 재실행처럼 어느 날에도
속하지 않는 명령의 자리가 없다. 영웅님이 ⓑ 로 정했다. 조작 설명서 머리말이 이미 「워크플로는 그날의
계획, 여기는 항상 같은 조작법」이라고 선을 그어 두었으니 그 선언을 집행한 것이다.

역할이 문서마다 달랐는데도 낡은 이유는 같은 명령 문장이 세 곳(조작 설명서 §1 · 빌드 문서 최상단 ·
게이트 지도)에 복사되어 있었기 때문이다. 하나를 고치면 둘이 낡는다. 그래서 「층이 다르다」가 아니라
「문장을 한 곳에만」이 규칙이다. 「설명 X」는 완전히는 안 된다 — 명령 옆에 「언제」 한 줄이 없으면
어느 것을 칠지 몰라 결국 파이프라인을 열게 되고 명령 문서가 존재 이유를 잃는다. 경계는 「언제·무엇·
남는 것·실패 시 볼 곳」까지가 commands, 「왜」부터가 파이프라인이다.

빌드 문서의 `vivado -mode batch …` 원명령은 남긴다. 사람이 평소 치는 명령이 아니라 `reproduce.py` 가
무엇을 대신 치는지의 사양이고, commands §0 의 「최상단은 사람이, 중하단은 스크립트가」 구분과 같다.

### 2. 워크플로 색인 — 「런북이 있는지 모르겠다」의 답

로그는 `log/README.md` 목록으로 관리되어 46 이 어디 있는지 바로 보이는데 워크플로에는 그것이
없었다. 같은 모양의 색인을 만들고 「지금」 열에 이어짐·닫힘을 한 줄로 적었다. 정확한 상태는 각
문서 머리말이 정본이고 색인은 안내다 — 상태를 두 곳에 두면 또 어긋난다.

### 3. README 는 본질만

담당 역할·디렉토리 안내·진행 상태 세 절(63줄)이 각각 `roles.md`·`CONTRIBUTING.md` §1·`gate_map.md`
와 중복이었고 README 쪽이 먼저 낡았다(작업 일지 15편, `host/tests` 없음). 정면은 「이 리포가
무엇인가」(요약·방법·파라미터 근거·결과·한계·고도화 방향)와 「더 보려면」 표 하나로 줄였다.
CONTRIBUTING §1 이 폴더 지도의 정본이 됐으므로 그쪽의 낡은 줄(ps/ 가 「UART 명령 서버·온도 PID」,
host/run 에 run_wear 없음)을 같이 고쳤다.
