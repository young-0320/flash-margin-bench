## 2. 무엇이 깨져 있었나

네 군데였고, **세 번째가 진짜 벽**이었다. 앞의 둘만 고쳤으면 g3 에서 다시 막혔다.

### 2-1. `.bat` 런처 — 선검사는 통과하고 실행에서 죽는다

Windows 의 Vivado/Vitis 는 `vivado.bat` / `vitis.bat` 다.

- `shutil.which("vivado")` 는 `PATHEXT` 를 보므로 **`.bat` 를 찾아낸다** → 도구 선검사 통과
- `subprocess.run([...], shell=False)` 는 `CreateProcess` 를 부르고, 얘는 **`.exe` 만** 자동으로 붙인다 → `WinError 2`

"도구는 다 있다고 해놓고 첫 단계에서 죽는" 증상의 정체다. `tool()` 을 새로 두어
`.bat`/`.cmd` 면 `cmd /c` 로 감싼다. Linux 에서는 `which` 결과(절대경로)를 그대로 쓴다.

### 2-2. 셸 문자열 — glob 과 따옴표

`sim`·`selftest` 가 `&&` 로 이어붙인 문자열이었고 `shell=True` 로 돌았다. Windows 에서는
`cmd.exe` 가 받는데,

- `../../fpga/rtl/core/*.v` 를 **cmd.exe 는 펴주지 않는다** (bash 가 대신 해주던 일)
- `{log_dir}` 치환값에 인용이 없다 → 사용자명이 한글이거나 경로에 공백이 있으면 깨진다

셸을 아예 걷어냈다. `cmd` 를 argv 리스트 또는 **argv 리스트의 리스트**로 바꾸고, 앞이
실패하면 멈춘다(= `&&`). glob 은 `Path.glob` 으로 파이썬이 편다. 따옴표 문제는 셸이
없으니 애초에 생기지 않는다.

### 2-3. `exec env G3_MHZ=$mhz` — 이게 진짜 벽이었다

`build_g3_chip.tcl` 이 Vitis 를 체인 호출할 때 클럭을 이렇게 넘기고 있었다.

```tcl
exec env G3_MHZ=$mhz $vitis_exe -s .../build_g3_sweep.py
```

`env(1)` 은 POSIX 코어유틸이라 **Windows 에 없다**. `reproduce.py` 를 아무리 고쳐도
g3-25/45/75 세 단계는 여기서 죽는다. Tcl 은 `::env` 배열을 자식에게 그대로 넘기므로

```tcl
set ::env(G3_MHZ) $mhz
exec $vitis_exe -s .../build_g3_sweep.py
```

로 바꿨다. Linux 동작은 동일하고, 프로세스 하나를 덜 띄운다.

### 2-4. 잔가지

- `-source` 경로를 `as_posix()` 로. Tcl 은 Windows 에서도 `/` 를 받고, 백슬래시는
  Tcl 이스케이프(`\b`, `\f`)와 섞일 여지가 있다
- `vitis_exe` 탐색에 `.bat` 분기 추가 — 없으면 `XILINX_VIVADO` 가 잡혀 있어도
  PATH 폴백으로 새어나간다
- 로그·요약 파일 인코딩을 utf-8 로 고정 (Windows 기본 cp949 면 한글 요약이 깨진다).
  채점 문구는 전부 ASCII 라 판정에는 영향 없음
- 도구 누락 안내에 `settings64.bat` 추가

1. **§3.5 기준표(BASELINE)를 Windows 에서 어떻게 볼 것인가.** 현재 값은 Ubuntu 24 +
   Vivado 2025.2 로 구운 것이다. 같은 버전이면 Windows 에서도 대개 같은 수치가 나오지만
   보장은 없다. 지금은 손대지 않았다 — 불일치는 이미 WARN(실패 아님)이고 "로그에 적을 것"
   이라 안내한다. **다르게 나오면 그 값을 로그에 남기고, 플랫폼별 기준표로 나눌지 그때 정한다**

   Windows 에 없다. §4 보드 굽기라 `reproduce.py` 범위 밖이어서 **이번엔 건드리지 않았다**.
   세은이 보드까지 굽는다면 Tcl 내장 `zlib`/`vfs::zip` 이나 XSA 를 직접 여는 쪽으로 따로 정해야 한다
