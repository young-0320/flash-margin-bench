## 0. 문제는 편의가 아니라 세션 경계였다

착수 동기는 *"터미널 2~3개 띄우기 귀찮다"* 였는데, 파고 보니 UID가 3주째 미구현인
이유와 같은 곳에서 나왔다.

칩 스윕은 **물리적으로 두 세션**이다. 비트스트림이 다르고 칩에 가는 SPI 경로가 다르다.

| | 비트스트림 | 칩까지의 경로 | 산출 |
| --- | --- | --- | --- |
| 세션 1 | `g2_jedec` | PS SPI0 → EMIO → JB | `#PREP …` — **화면에만** |
| 세션 2 | `g3_chip_<mhz>` | PL(`flash_top_spi`) → JB | CSV 2개 |

**UID를 읽을 수 있는 것은 세션 1이고, 파일을 만드는 것은 세션 2다.** 사람이 중간에
끼어 있어 두 세션이 이어지지 않으므로 UID가 파일에 도달할 길이 없었다.

두 세션이 같은 물리 핀(V8/W8/U7/V7)을 쓰면서 주인만 바뀐다는 것은 xdc 두 개를 나란히
놓으면 보인다(`g3_chip_pins.xdc` 주석: *"G2 JEDEC과 동일 물리 배선 — 비트스트림만 교체"*).
그리고 PL 쪽으로 읽는 길은 `flash_spi_ctrl.v:120`이 `0x0B` 40클럭 프레임에 고정돼 있어
막혀 있다 — `4Bh`는 주소 없이 더미 4바이트라 프레임 구조가 다르다.

→ **한 프로세스가 UART를 계속 쥐면 두 세션이 연속된 시간이 된다.** 래퍼는 편의 도구가
아니라 UID 파이프라인의 전제였다.

## 1. 래퍼를 시나리오로 나눴다 — 셋

기준은 "스윕이냐"가 아니라 **하드웨어 세션의 모양**이다.

| 이름 | 세션 모양 | 선행 |
| ---- | --------- | ---- |
| `run_sweep_chip.py` | 한 세션에서 prep → 스윕 ×N | 없음 (지금 착수 가능) |
| `run_newchip.py` | 칩 순회 + 사람 개입 + 등록부 기입 + 중단·재개 | B-0·B-1·B-1b·blank |
| `run_wear.py` | 무인 장시간 + 전원 장애 복구 + 체크포인트 | B-2 사이클러 |

**루프백은 분리한다.** 비트스트림·프로그래밍 스크립트·prep 유무·UID 유무가 전부 다르고,
역할도 DUT 측정이 아니라 계측기 자기 점검이다. 묶으면 플래그 절반이 루프백에서 죽는다.
필요해지면 `run_sweep_loopback.py`를 따로 붙인다.

**공통 층은 지금 뽑지 않는다.** 시나리오가 하나뿐인 상태에서 추출하면 상상한 요구사항에
맞춰 설계하게 된다. 두 번째 래퍼에서 실제로 겹치는 것이 드러나면 그때 뽑는다.

## 2. `host/run/` 신설 — 바뀌는 이유가 다르다

기존 폴더 넷을 다 대봤고 전부 성격이 어긋났다. `host/analysis/`는 하드웨어를 모르고
(CSV→수치), `ps/scripts/`는 소유자가 다르며 래퍼가 그것을 *호출*한다.

`host/capture/`와의 구분만 애매했는데, 기준을 이렇게 잡았다.

```
capture  ←  계약 §6 이 바뀌면 바뀐다   (열, 파일명, _invalid 판정)
run      ←  실험 절차가 바뀌면 바뀐다  (반복 횟수, 재장착, 칩 순회)
```

**다른 이유로 바뀌는 코드는 폴더를 나눈다.** 그리고 CONTRIBUTING의 명명 기준
(*"폴더 이름은 '어디서 도는가'"*)에서 래퍼는 호스트에서 도니 `host/` 아래가 맞다.

부수로 확인된 것: **`host/capture/`가 CONTRIBUTING 폴더 지도에도 소유자 표에도 없다.**
2026-08-23 감사(`7a9214c` "리포 실제와 정합")에서도 안 잡혔다. `run/`을 추가하며 같이 넣는다.

### 이름 — 산출물 이름을 따라간다

```
계약 §6 산출물:  sweep_chip01_<stamp>.csv   /  sweep_loopback_<stamp>.csv
스크립트:        run_sweep_chip.py          /  run_sweep_loopback.py
```

**스크립트 이름이 자기가 만드는 파일 이름을 그대로 따라간다.** "이 CSV는 뭐가 만들었나"가
이름만으로 풀린다. 종전 후보 `sweep_runner`(CONTRIBUTING 등록명)는 버린다 — 스윕이 아닌
시나리오(P/E 사이클러·blank check)가 이미 예정돼 있어 접두가 사실과 어긋나고, 배정된
위치(`host/analysis/`)도 성격이 다르다.

## 3. 라벨을 사람이 입력하지 않는다 — 이번 국면의 핵심

현행 `--target chip01`이 두 가지를 겸하고 있었다.

```
① 파일명을 정한다
② "소켓에 이게 꽂혀 있다"고 사람이 선언한다   ← 아무도 검증하지 않는다
```

②가 틀려도 스윕은 정상 완주한다. 로그 21 §2가 지적한 "절차가 완주하면서 데이터만
망가지는 경로"와 같은 부류다.

**UID를 읽고 등록부에서 라벨을 역조회한다.** `--target`은 사라진다.

```
flash_prep 이 4Bh 로 UID 확보
   → chip_registry.md 에서 UID 로 라벨 역조회
   → 등록부에 없으면 신규 등록 프롬프트
```

라벨은 사람이 주장하는 값이 아니라 **등록부가 답하는 값**이 된다.

### 등록부는 md를 유지하고 파서를 빡빡하게 한다

CSV로 정본을 빼면 md의 표는 지우거나(사람이 못 읽음) 남기거나(어긋남) 둘 중 하나인데,
후자가 로그 20 §4(H5)에서 기각한 실패다. 등록부는 표만 있는 파일이 아니라 산문
(왜 UID인가 · 기입 절차 · 소급 적용 · 누적 P/E의 정본)이 본체다.

```
UID 는 정확히 16 hex   /  라벨은 chip01~chip10  /  UID 중복 없음
0행 파싱 → "등록 칩 없음"이 아니라 파서 고장으로 처리
```

마지막 줄이 H5의 교훈이다 — **비어 있음을 정상으로 받으면 안 된다.**

**쓰기는 행 추가만 허용하고 기존 행 수정은 사람이 한다.** UID는 불변이라 추가로 충분하고,
등록부는 커밋되는 파일이라 `git diff` 확인 층이 자동으로 붙는다.

## 4. 파일명에 UID를 넣는다 — 라벨은 남긴다

```
chip*     :  sweep_chip01_A1B2C3D4E5F60718_20260823T130847Z.csv
loopback  :  sweep_loopback_20260823T130847Z.csv          (종전 유지)
```

UID만 쓰는 안(`sweep_chipA1B2…`)도 검토했으나 라벨을 남기는 쪽을 택했다.

- 16자 hex 10줄은 사람이 구분하지 못한다. 배치에서 특정 칩을 되짚을 때마다 등록부를
  열어야 한다
- 기존 문서 전부(로그 13·15, 워크플로, `docs/results/` 유래 md)가 `chip01`을 참조한다
- **`chip01_<uid>` 조합이 등록부와 어긋나면 파일명만 보고 드러난다.** UID만 쓰면 값은
  정확하지만 "사람이 의도한 칩과 실제가 달랐다"는 사실 자체가 안 보인다

라벨 오독 우려는 **사람이 라벨을 입력한다는 전제**에서 나온 것이고, §3이 그 전제를 없앴다.

`chip_registry.md`의 *"파일명은 변경하지 않는다"* 는 **7월분 소급 개명**에 대한 것이지
새 규칙을 금지한 것이 아니다. 7월 데이터는 그대로 두며 두 규칙이 공존한다 — UID 유무로
구분되므로 혼동되지 않는다.

## 5. UID는 3회 읽어 일치를 요구한다

**SPI에는 체크섬이 없다.** 접촉이 튀면 `XST_SUCCESS`가 나오면서 틀린 비트가 담겨 온다.
"전송 성공"은 "값이 맞다"가 아니다.

리포에 이미 이 구분이 있다 — `flash_prep.c:104~110`의 JEDEC 검사는 전송 성공이 아니라
**값이 `EF 40 17`인지**를 본다. UID는 기대값이 없으므로 자기 일관성으로 대신한다.

```
UID 를 3회 읽는다
  ├ 전송 실패(XST_FAILURE)  →  최대 3회 재시도. 계속 실패면 중단
  └ 3개 값이 전부 일치       →  통과. 하나라도 다르면 중단 (경로 불안정)
```

비용은 **0.12ms**다(2.6MHz × 13바이트 = 40µs/회). 시간은 고려 대상이 아니다.

**신규 칩에서 특히 필요하다.** 등록된 칩이면 등록부 대조로 오독이 걸리지만, 신규 칩은
대조 상대가 없어 자기 일관성 말고는 검사 수단이 없고, 신규 등록은 되돌릴 수 없다.

## 6. 불변식은 래퍼가 아니라 캡처에 둔다

"chip은 UID 없이 CSV를 만들 수 없다"를 어디에 두느냐의 문제다.

| 두는 곳 | 결과 |
| ------- | ---- |
| 래퍼 | 래퍼마다 규칙을 다시 구현한다. 하나 빼먹거나 캡처를 직접 부르면 샌다 |
| **캡처** | **모든 경로가 캡처를 지난다.** 규칙이 한 곳이고 새 래퍼가 자동으로 따른다 |

리포에 이미 같은 패턴이 셋 있다.

- `bathtub_analysis.py:76` — 캡처가 이미 거른 `_invalid`를 **분석기가 다시 거부**
- `flash_prep.c:106` — 사람 주장 대신 **칩에게 `9Fh`로 물어본다**
- `program_g3.tcl` — ELF만 재로드하는 빠른 길을 **`phase_pos_mismatch`로 의도적 거부**

셋 다 *"사람의 주장을 받지 않고 기계가 확인한다"* 이며, `roles.md:49`의 자기 측정 의심
원칙이 코드로 나타난 형태다.

**"캡처 실행 금지"가 아닌 이유**: ⑴ 루프백이 캡처를 쓰므로 통째로 막으면 G0을 못 돌린다
⑵ 못 쓰게 하면 복사본을 만들어 쓰게 되고 **그 복사본에는 규칙이 없다** ⑶ 캡처의 책임은
"계약 §6을 만족하는 CSV를 만든다"이므로, 위반본을 안 만드는 것은 캡처 자신의 일이다.
호출자를 통제하는 문제가 아니다.

진단용 `--raw`는 연다. 단 **CSV를 만들지 않게** 한다 — 파일이 없으면 계약 위반이 애초에
표현 불가능하고, 우회 스크립트를 짤 이유도 사라진다.

## 7. 옵션으로 두면 안 되는 것

| 두지 않는다 | 이유 |
| ----------- | ---- |
| `--skip-prep-check` 류 | 안전장치를 끄는 플래그는 결국 쓰게 된다. 사전 쓰기 없이 스윕하면 전 위상 BER≈0.51이 나오고(7/8 실사례, 로그 14) 칩 문제로 오독된다 |
| `--dphi` | Δφ=15.873016ps는 VCO 고정이라 전 사다리 공통(계약 결정 16). 열면 안 맞는 값이 들어온다 |
| `--steps` | `56 × (1125/mhz)`로 파생된다. `--mhz`가 정하는 값이라 따로 두면 어긋난다 |

여는 것: `--repeat` · `--reseat` · `--n-reads` · `--base-sector`(#1 승인 시) ·
`--mhz` · `--pl` · `--port` · `--baud` · `--no-prep` · `--prep-only` ·
`--prep-sectors`(B-0 이후).

## 8. 계약 §6 수정안 #3의 범위

```
① 파일명    chip* : sweep_<label>_<uid16>_<stamp>.csv   /  loopback 종전
② 메타 열   +uid  +reseat  +repeat_idx  +batch_id       (12열 → 16열)
③ 생성 거부 chip target 은 UID 없이 CSV 불가 — 캡처가 집행
④ UID 확보  3회 일치 · 전송 실패 3회 재시도 · 라벨은 등록부 역조회
```

신규 열 3개의 근거는 **지금 사람 메모에만 있는 것을 데이터로 옮기는 것**이다.

| 열 | 지금 어디 있나 |
| -- | -------------- |
| `reseat` | `docs/results/data/*.md`의 "재장착 없음" 문장 |
| `repeat_idx` | 파일명 타임스탬프 + 사람 기억 |
| `batch_id` | **없음** — "이 5개가 한 묶음"을 사람이 골라서 넘긴다 |

`reseat`이 가장 무겁다. **로그 22 §3에서 D 판정이 막힌 원인이 이것**이다 — 7월
`±0.61ps`가 재장착 없이 잰 값이라는 사실이 데이터가 아니라 메모에 있어서, 8/23 값을
거기 대도 되는지를 매번 사람이 다시 판단해야 한다.

**소급되지 않는다.** 7월 데이터에는 이 열이 없으므로 그쪽 근거는 계속 유래 md의 문장이다.
본 변경은 앞으로를 고치는 것이지 D 판정을 자동으로 풀지 않는다.

### 영향 — `bathtub_analysis.py`는 "변경 불요"가 아니었다

읽기(`csv.DictReader`)는 키를 더 받을 뿐이라 변경이 없다. 그러나 **`selftest_csv()`
(`:338`)에 열 목록이 하드코딩**돼 있어 갱신하지 않으면 셀프테스트가 12열, 캡처가 16열을
쓰게 된다. 읽기가 관대해서 **아무것도 깨지지 않은 채로 어긋난다** — 문서상
*"계약 스키마 그대로"*(`:38`)라는 셀프테스트의 주장만 조용히 거짓이 된다.

| 대상 | 변경 |
| ---- | ---- |
| `sweep_uart_capture.py` | META_COLS · 파일명 · 거부 규칙 · 등록부 조회 |
| `ps/src/flash_prep.c` | `4Bh` — **수정안 밖.** RTL·계약 무관이라 승인 없이 가능 |
| `bathtub_analysis.py` | 읽기 없음 / **`selftest_csv()` 열 목록 갱신 필요** |
| `repeatability_aggregate.py` | 없음 (나중에 `batch_id`로 자동 묶기 가능) |
| `chip_registry.md` | "CSV 헤더에 `#UID`" 문장을 열 방식으로 정정 |
| 7월 데이터 | 개명·소급 없음. 두 규칙 공존 |
