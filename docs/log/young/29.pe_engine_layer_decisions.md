## 1. 무엇을 논의하고 있나

> **P/E 마모 사이클을 누가 돌리는가 — PS의 C 프로그램인가, PL의 RTL 엔진인가.**
> 그리고 그 선택이 체크포인트 경로·대조군 오염·계약 변경 범위를 어떻게 바꾸는가.

워크플로 9 §2-2가 오늘 3인 확정 안건으로 올려 둔 항목이고, 리포에 남아 있던 상정은 **PS C**다
(`roles.md` 미결). 지민의 프롬프트도 PS C 전제로 쓰였다. 그런데 지민의 산출물은 워크플로 9 §4에서
**"스트레스 RTL 설계서"**로 잡혀 있어 두 문서가 서로 다른 층을 가리킨다. 이 불일치를 닫는 것이
본 논의의 목적이다.

### 2.1 F2의 파생 — 파일럿 질문 3개 중 2개는 지금도 답할 수 있다

`BASE_SECTOR`가 없으면 `page(i) = i`이므로 **N=112는 페이지 0~111 = 섹터 0~6 = 정확히 wear 영역**이다.

| S-1 §15 파일럿 질문 | 수정안 #1 없이 |
| ------------------- | -------------- |
| ① 폭이 언제부터 움직이는가 | **가능** (wear를 `BASE_SECTOR=0`으로 그대로 잰다) |
| ② 잔여 비트가 어디서 실험을 무의미하게 만드는가 | **가능** (blank check는 SPI 경로, RTL 무관) |
| ③ 인접 섹터 간섭이 있는가 (근접 vs 원격) | **불가** — 읽기 창을 못 옮긴다 |

## 3. 결정 사항

| ID | 결정 | 상태 |
| -- | ---- | ---- |
| D1 | P/E 사이클을 **PL의 RTL 엔진**이 돌린다 | **잠정** — 근거 재검토 중 (§4) |
| D2 | 경계: **반복은 PL, 판단은 PS** | **확정** |
| D3 | 마모와 측정을 **단일 비트스트림**에 담는다 (비트스트림 교체 없음) | **보류** — D1에 종속 |
| D4 | 이번 재합성에 **수정안 #1(BASE_SECTOR)을 함께** 넣는다 | 동의. 단 승인 절차 필요 (§5) |
| D5 | 파일럿 칩 = **chip01** | **확정** (조건 2건, 아래) |
| D6 | 사이클 카운터의 정본은 **`wear_loop_cycles`** — 체크포인트의 소거+PRBS는 세지 않는다 | **확정** |
| D7 | 마모 패턴은 **레지스터 2개**(짝수/홀수 사이클 바이트), 기본 `0x00`/`0x00` | **확정** |
| D8 | N=112에 **RTL 수정은 불요** | 사실 확인 |

### D2 — 반복은 PL, 판단은 PS

- **PL**: erase/program 발행, WIP 폴링, 사이클 카운터, `t_erase_us`/`t_program_us` 측정, 결함 비트 카운트
- **PS**: 체크포인트 도달 판정, tally 바이트 선택·기록, resume 복원, UART 로그 포맷, UID 확인

근거: 45ms를 33시간 도는 루프는 PL이 안정적이고, tally의 "다음 미사용 바이트 찾기"·두 사본 비교·
부분 바이트 처리는 FSM으로 짜면 비대해지는데 소프트웨어로는 수십 줄이다.

### D5 — 파일럿 = chip01, 조건 2건

찬성 근거: 누적 P/E가 prep 수 회 수준이라 300k 대비 무시 가능하고, **baseline이 가장 두꺼운 개체**
(7월 n=5 + 8/23 + 9/15 재장착 3회)라 "폭이 언제부터 움직이나"에 유리하다.

- **조건 ①**: 기존 baseline이 N=100 계열이므로 **N=112 스윕 1회를 chip01로** 떠서 환산 근거를 남긴다
  (수정안 #2 §7의 D 2단계, 약 6분). 7월분은 2024.2 비트스트림이라는 점도 함께 기록한다
- **조건 ②**: chip01을 300k로 태우면 **장비 드리프트·재장착 MSA의 기준 개체가 사라진다.**
  대체 개체를 신품 중에서 지정하고, 그 칩만 M 트랙에서 baseline을 두껍게 뜬다
- 부기: chip01은 7월부터 prep이 여러 번 지웠으므로 **`blank_pre`(출고 blank)는 이미 소실**이다.
  실험에 필요한 `blank_post`(= S-1 §7 `erase_residual_bits`)는 그대로 얻어진다 — 파일럿 로그에 명시

### D6 — 카운터 기준

100사이클 후 체크포인트에서 소거+PRBS를 1회 하면 카운터가 100인가 101인가의 문제.

- S-1 §1은 "체크포인트의 소거+PRBS 기록도 1사이클로 계수" → 101
- **채택: 100.** tally 마크 1개 = 정확히 100 wear cycles가 되고, S-1 §13 A5의 "네 경로 카운트가
  전부 100"이 깨끗하게 성립한다. 체크포인트로 들어간 P/E는 영역별 `*_pe_actual`에 따로 적어
  정보 손실은 없다
- **S-1 §1 계수 문장을 정정해야 한다** (§6)

### D7 — 마모 패턴

```
WEAR_PAT_EVEN (8bit)   짝수 사이클에 프로그램할 바이트
WEAR_PAT_ODD  (8bit)   홀수 사이클에 프로그램할 바이트

0x00 / 0x00   현재 사양 (all-0, 매 사이클 동일)
0x55 / 0xAA   체커보드 교대
```

- 프로그램은 1→0 방향뿐이라 `0x55 → 0xAA`로 직접 못 간다. 매 사이클 erase가 끼므로 **교대**로 구현한다
- 기본값 `0x00`/`0x00` 유지 — 체커보드는 **보류**이지 채택이 아니다 (로그 26 §3)
- `0x00`은 셀당 8비트, `0x55`는 4비트가 1→0이라 **사이클당 스트레스가 2배 다르다.**
  로그·CSV의 `pattern` 필드 필수, **한 wear 그룹 안에서 패턴 변경 금지**
- 레지스터로 두면 재합성 없이 런타임에 바뀐다

### D8 — N=112는 RTL 수정이 필요 없다

`N_READS`는 AXI 레지스터 `0x0C`이고 PS가 스윕마다 써 넣는다(`g0_sweep.c:124`). 지금 100인 이유는
**C 상수**(`N_READS_CFG`)이기 때문이며, 수정안 #2 §4.1이 밝히듯 RTL 변경은 **리셋값 한 줄, 그마저
선택 사항**이다. 즉 수정안 #2 승인 시 **ELF 재빌드(약 1분)로 끝난다.**

단 ⑴ `run_sweep_chip.py --n-reads 112`가 ELF의 `BEGIN n=`과 대조하므로 빌드와 인자가 함께 가야 하고,
⑵ D4로 어차피 재합성한다면 **리셋값도 112로 맞추는 편**이 브링업 혼란을 줄인다.

## 4. 열린 쟁점 — D1의 근거가 충분한가

RTL 노선의 이점으로 거론된 것과 그 검증 결과다.

| 주장 | 검증 |
| ---- | ---- |
| 33시간 무인 실행이 안정적 | PS bare-metal도 OS·인터럽트가 없어 결정적이다. **차이가 크지 않다** |
| 시간 측정이 정밀 | PS `XTime`은 333MHz 글로벌 타이머(≈3ns)다. 45ms를 재는 데 **양쪽 다 과잉** |
| 비트스트림 교체가 없어진다 | **유일하게 실질적인 이점.** 다만 P/E를 PL로 옮기지 않고 **g3 비트스트림에 PS SPI 핀 mux만 추가**해도 같은 이득을 얻는다 — 비용이 한 자릿수 작다 |
| op_timer가 어차피 PL에 있다 | 현재 리포에 op_timer는 **없다**(F6). 새로 만드는 것은 양쪽 다 같다 |

반대로 RTL 노선이 새로 만드는 비용:

- **계약이 또 열린다.** P/E 레지스터 추가 = 계약 §3 변경 = 3인 합의 사안. 수정안 #1·#2·#3에 이어
  네 번째가 된다. PS C 노선은 계약 변경 0
- **G1이 자란다.** P/E 엔진은 새 검증 대상이라 S-3의 23항목이 늘어난다. 지민이 G1 cocotb(유일한
  미착수 게이트)와 P/E 엔진과 BASE_SECTOR RTL을 동시에 안게 된다
- 변경할 때마다 재합성(분 단위) — 파일럿은 파라미터를 자주 만질 국면이다

**엔지니어링 순수 비교로는 PS C가 유리하다.** RTL의 실질 근거는 ⑴ 소유권·일정(세은이 온도 트랙으로
가므로 펌웨어 잔무가 뜬다, 워크플로 9 §2-3) ⑵ 단일 비트스트림 — 이고 ⑵는 mux로도 얻는다.
**D1을 확정하기 전에 이 표를 한 번 더 본다.**

## 8. 임계 경로 — N=112가 M 트랙보다 먼저다

**M 트랙(신품 10개 전수)을 N=100으로 돌리면 파일럿(N=112)과 비교가 안 된다.** 개체 산포 σ는 파일럿의
해석 분모이므로, 같은 N으로 떠야 한다. 따라서 순서가 고정된다.

```
① 수정안 #2 서명 → N=112 치환 → ELF 재빌드        (재합성 없음, 약 1분)
② chip01 N=112 스윕 1회                            (N=100↔112 환산 근거, 6분)
③ W5-D 판정                                        (①②와 오늘 재장착 3회로)
④ M 트랙 10개 전수 @ N=112 (chip01 포함)
⑤ G5 판정
⑥ 파일럿 (chip01, 300k)
```

### 8.1 N 치환은 `build_g3_sweep.py`에서 한다 — `g0_sweep.c`를 고치지 않는다

`g0_sweep.c` 원본 무수정 원칙(R7·로그 8) 때문에 `build_g3_sweep.py`가 사본을 만들어 상수를 치환하는
구조다. 그런데 **`build_g0_sweep.py`는 같은 원본을 그대로 가져다 쓴다** — 소스를 직접 고치면 G0
루프백(계측기 자기 점검)까지 112로 끌려간다.

- **채택**: `build_g3_sweep.py`의 치환 목록에 `N_READS_CFG` 한 줄 추가. 실칩만 112
- G0 루프백은 **100 유지** — 자기 이력과 비교하는 경로이고 칩 데이터와 비교하지 않는다 (수정안 #2 §4.3의 모드 개념 그대로)
- `run_sweep_chip.py --n-reads 112`가 ELF의 `BEGIN n=`과 대조하므로 빌드와 인자가 함께 가야 한다

### 8.2 BASE_SECTOR 재합성과 M 트랙의 세대 문제

M을 현재 비트스트림으로 돌리고 나중에 재합성하면 **빌드 세대가 갈린다**(7/8 2024.2 vs 9/14 2025.2에서
이미 겪은 함정, 워크플로 7 §6).

- **채택**: N=112는 ELF 변경뿐이라 비트스트림이 그대로다 → **M은 지금 세대로 진행**
- BASE_SECTOR는 M과 **병렬로 개발**하고, 완료 후 수정안 #1 §4 **A1 회귀**(`BASE_SECTOR=0`, chip01,
  기준값 ±3σ)로 두 세대를 잇는다. A1은 원래 그 목적의 인수 기준이다
- 파일럿의 체크포인트 0은 새 세대에서 뜨므로 파일럿 내부 비교는 세대 혼합이 없다

### 8.3 M 트랙의 진짜 병목은 N이 아니다 — G-b·G-d가 미구현이다

S-2 §2는 chip02를 꽂기 전 조건 넷을 못박아 뒀다. 현재 상태를 대조하면:

| # | 조건 | 현재 |
| - | ---- | ---- |
| G-a | D 트랙 통과 (드리프트 없음) | **보류** — 오늘 재장착 σ 확보 후 판정 |
| G-b | B-1 소거 시간 계측 (`#PREP`에 섹터별 시간) | **미구현** — 리포에 `XTime` 사용 0건 |
| G-c | B-1b UID 출력 | **완료** (`flash_prep.c` 4Bh) |
| G-d | §5 blank check 판독 (소거 전·후) | **미구현** — `flash_prep`은 PRBS verify만 하고 `0xFF` 비트를 세지 않는다 |

**N=112는 이 넷 어디에도 없다.** N은 게이트가 아니라 *조건 통일* 항목이며, M을 여는 것은 G-a~G-d다.
따라서 M의 실제 병목은 **G-b·G-d(`flash_prep` 확장, 각각 수십 줄)** 이고, 둘 다 세은의 B 트랙인데
세은은 온도 트랙으로 이동 중이다 — **워크플로 9 §2-3(펌웨어 잔무 귀속) 미결이 M 전체를 막고 있다.**
오늘 닫아야 한다.

- G-b·G-d는 `flash_prep.c` 수정 → prep ELF 재빌드. N 치환은 `g3_sweep` ELF라 **서로 독립, 병렬 가능**
- **B-0(prep 파라미터화)은 M의 게이트가 아니다.** M은 전 범위 prep(약 1분/칩)으로 충분하고,
  파일럿의 영역별 준비는 D2에 따라 마모 벤치가 소유한다 → **B-0을 임계 경로에서 뺀다**
- chip01의 `blank_pre`는 이미 소실이므로(D5 부기) M에서 chip01 행은 그렇게 기록한다

## 9. P/E 벤치를 어떻게 개발하나 — D1이 늦어도 90%는 간다

D2(반복은 PL·판단은 PS) 덕분에 **"판단" 쪽은 구현 층위와 무관**하다. 그래서 엔진 경계에 인터페이스
하나만 두면 D1 확정 전에 대부분을 짤 수 있다.

```
[층위 독립 — 지금 짠다]                        [D1에 종속 — 나중에 채운다]
주소 보호 불변식 (겹침·범위 거부)
tally 기록·판독·두 사본 비교                    ┌─ wear_start(base, n_sectors, cycles, pattern)
resume 복원 (tally ↔ 호스트 로그)      ─────►  │  wear_status()  → cycle, state, err
로그 스키마 A/B/C                               │  wear_times()   → t_erase_us[], t_program_us[]
체크포인트 배치 계산 (×2.15 / ×1.47)            └─ blank_check(base, n_sectors)
호스트 실행기 · mock 장치 · chip_pe 연동
블랙박스 TB (S-1 §13 A·B·C)                     PS C 함수로 채우거나 / 레지스터 write 로 채운다
```

인터페이스 뒤를 **mock 엔진**으로 먼저 채워 100사이클 mock 완주까지 간다. 그 시점에 D1이 정해져
있으면 진짜 엔진으로 갈아 끼운다.

**작업 순서**

1. 블랙박스 TB 뼈대 — S-1 §13 A·B·C에서만 뽑고 **설계서를 보기 전에 커밋** (작성자·판정자 분리를 타임스탬프로)
2. 층위 독립 부분 + mock 엔진 구현
3. mock 100사이클 완주 (실칩 명령 0회)
4. D1 확정 → 진짜 엔진 구현 → 같은 TB로 판정
5. 실칩 `target=1` 짧은 dry-run → G5 판정 → 실칩 100사이클
6. 전원 장애 복구 시험 (S-1 §13 B)

**D1을 서두를 필요가 없다는 것이 이 구조의 요점이다.**
