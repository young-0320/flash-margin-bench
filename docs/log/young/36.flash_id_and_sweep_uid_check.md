## 2. 작업 내용

### 2-1. 왜 새 앱이 필요했나

UID(4Bh)는 g2 비트스트림(PS SPI) 위에서만 읽힌다. PL 경로는 `flash_spi_ctrl.v:120`이
`0x0B` 40클럭 프레임에 고정돼 막혀 있다(로그 23 §0). 그런데 **g2 위에서 도는 앱이
`flash_prep` 하나뿐이고 걔는 반드시 소거·쓰기를 한다.**

| | `--mode newchip` | `--mode sweep` (전) | `--mode sweep` (후) |
| --- | --- | --- | --- |
| 세션1 | `flash_prep` — UID 읽기 O, **P/E +1** | **없음** | `flash_id` — UID 읽기 O, **P/E 불변** |
| 신원 | 기계가 읽는다 | 사람 선언 | 기계가 읽어 **대조한다** |

앵커 재측정에서 P/E를 태우지 않으려고 세션 1을 통째로 뺀 것이 신원 확인까지 같이
없앤 것이었다. **읽기만 하는 앱**을 만들어 그 둘을 분리했다.

### 2-2. `flash_io` — 사본이 아니라 이전

`flash_id`가 필요로 하는 배관(UART 보 레이트·SPI0 초기화·전송·JEDEC·UID)은 전부
`flash_prep.c`에 이미 있었다. 복사하면 다섯 번째 사본이 된다.

**처음에는 새 코드만 부품으로 만들고 `flash_prep`은 두려고 했다** — 그것이 chip05~10을
측정할 바로 그 앱이라, 빌드가 바뀐 사실을 측정 도중에 알게 될까 봐. 그러나 그러면 같은
배관이 두 벌 남는다. **§2-7에서 `flash_prep`도 부품 위로 옮겼고, 값이 안 바뀌었다는
증거를 빌드 전후 비교로 확보했다.** 사본이 아니라 이전이다.

9/15 보 레이트 변경 때 네 파일을 다 고친 것이 이 중복의 비용이었다.

| 배관 | 작업 전 | 작업 후 |
| ---- | ------- | ------- |
| `uart_set_baud` | 4 (전 앱) | 3 (`flash_io` + `flash_jedec`·`core_smoke`·`g0_sweep`) |
| SPI0 초기화 | 2 | 2 (`flash_io` + `flash_jedec`) |
| JEDEC 읽기 | 2 | 2 (`flash_io` + `flash_jedec`) |
| UID 읽기 | 1 | 1 (`flash_io`) |

`flash_jedec`이 남은 이유는 기술적인 것이 아니다 — **장세은 소유(게재 2번 산출 경로)라
소유자 합의가 먼저다.** `core_smoke`(세은)·`g0_sweep`은 SPI를 안 쓰고 `uart_set_baud`만
겹치므로 마모 엔진 때 같이 본다.

구현은 `flash_prep.c`에서 **그대로 옮겼다.** 프리스케일러(`PRESCALE_64`)·보 레이트
(921600)·`UID_LEN=8`·4Bh 3회 읽기 — 값을 하나도 바꾸지 않았다. 읽기 경로가 같아야
"`flash_id`가 읽은 UID = `flash_prep`이 읽은 UID"를 주장할 수 있다.

**유일한 차이: `flash_io`는 아무것도 출력하지 않는다.** 실패 문구의 접두(`#PREP`/`#G2`)가
앱마다 다르고 호스트 파서가 그 접두로 종료를 판정하기 때문이다(로그 25 중요 1). 판정과
출력은 앱이 한다. UID 실패만 원인별로 갈라 돌려준다 — `-1` 전송 3회 실패 / `-2` 3회 읽기
불일치. 원본의 두 FAIL 문구를 앱이 그대로 낼 수 있게 하려는 것이다.

### 2-3. `flash_id` — 쓰기 명령을 한 바이트도 내보내지 않는다

소거·프로그램·WREN 없음. **그것이 이 앱의 존재 이유다.**

    #G2 ID — 읽기 전용 신원 확인 (소거·쓰기 없음)
    #G2 JEDEC ef 40 17 [OK] W25Q64 확인 — 보드-모듈 통신 정상
    #G2 UID D1642C74E7134527

**JEDEC을 같이 읽는 이유.** UID가 읽히면 통신은 이미 증명된다. JEDEC의 값어치는
**실패했을 때 원인을 가르는 것뿐**이다.

| 응답 | 뜻 |
| ---- | --- |
| `FF FF FF` | 무칩·오배선 — D0 배선표 + /WP·/HOLD 3V3 |
| `00 00 00` | 무칩·오배선·전원 — VCC·GND·CS |
| 그 외 ID | 다른 칩이거나 간헐 접촉 |

코드 3줄에 그 진단이 붙으므로 넣었다. 문구는 `flash_jedec.c`의 분기를 그대로 따랐다.
**이름이 `flash_uid`가 아니라 `flash_id`인 이유이기도 하다** — 신원(identity)에는 품종과
개체가 같이 들어간다.

### 2-4. 래퍼 통합 — `--chip`이 선언에서 검증으로

`run_id()`는 `run_prep()`과 같은 꼴이다. `program_g2 + flash_id`를 굽고 `#G2 UID`를 파싱해
등록부에서 역조회한 기대 UID와 대조한다. 어긋나면 **스윕을 시작하기 전에** 중단한다.

    칩 대조 실패 — 소켓의 칩이 chip04 가 아니다. 스윕을 시작하지 않는다
        읽은 UID : D1642C74E7134527 (chip02)
        기대 UID : D16484578B525622 (chip04)

읽은 UID의 라벨까지 찍는 것이 요점이다. "틀렸다"만으로는 사람이 다음 행동을 모른다 —
**무슨 칩을 꽂았는지**까지 답해야 소켓 앞에서 바로 고친다.

두 가지를 원본에서 그대로 지켰다.

- **드레인 스레드**(`run_xsct(..., ser=ser)`). 보드는 ELF가 뜨는 순간부터 뿜는데 xsct
  종료를 기다리며 안 읽으면 커널·FTDI 버퍼가 넘친다 — 2026-09-15 chip02에서 19스텝
  결측(무효 ⑤)으로 실현된 적이 있다
- **세션 로그 개명은 대조 통과 후.** 실패는 `session_idfail_*`로 남긴다. 확인되지 않은
  칩의 로그에 라벨을 박으면 그 파일이 나중에 증거로 읽힌다

### 2-5. `reproduce.py`의 선택 단계 `id`

`jedec`·`smoke`와 같은 꼴(`default=False`). 편의만이 아니다 — `run_step()`이
`PYTHONUTF8=1`을 자식에 강제하므로(로그 34 §2-1) **Windows에서는 이 경로로 빌드해야 한다.**
`flash_io.c`·`flash_id.c`도 한글 주석·문자열을 담고 있어 Vitis 내장 파이썬이 cp949로
읽으면 죽는 다섯·여섯 번째 파일이다.

    uv run python reproduce.py --only id

**⑥은 사람이 해야 한다 — §4 ②.** 컴파일이 통과했다는 것은 문법과 BSP API 사용이 맞다는
뜻일 뿐, **읽기 경로가 `flash_prep`과 같은 값을 낸다는 증거가 아니다.**

### 2-7. `flash_prep`을 부품 위로 — 그리고 값이 안 바뀌었다는 증거

같은 배관이 두 벌 남는 것이 이상해서 `flash_prep`도 옮겼다. 나간 것은 `uart_set_baud`·
SPI0 초기화·`XSpiPs_PolledTransfer`·JEDEC 읽기와 대조·UID 3회 읽기다. 순 **-20줄**이고
`XSpiPs`/`XUartPs` 참조가 **0**이 됐다.

남긴 것 하나: **`xfer()` 껍데기.** `flash_xfer`에 `#PREP ERROR`를 입히는 세 줄이다.
부품은 출력하지 않고 호스트 래퍼가 그 줄을 종료 신호로 읽으므로(로그 25 중요 1)
접두는 앱에 남아야 한다.

문제는 이것이 **측정 중인 앱**이라는 것이다. "값을 안 바꿨다"를 주장이 아니라 증거로
만들어야 해서, **리팩터 전 ELF를 먼저 빌드해 두고 비교했다.**

| 항목 | 전 | 후 | 판정 |
| ---- | --- | --- | ---- |
| `#PREP` UART 출력 문구 | 19개 | 19개 | **완전 동일** (diff 0) |
| text | 38,773 | 39,221 | +448 — `-O0`이라 호출이 인라인되지 않는다 |
| data | 1,528 | 1,528 | 동일 |
| bss | 23,652 | 23,684 | +32 = `flash_io`의 13B 버퍼 2개(정렬 포함) |
| 우리 소스 경고 | 0 | 0 | BSP·FSBL 경고만 남는다 |

**문구 diff가 0인 것이 핵심이다.** 호스트 파서가 보는 것이 정확히 그 문구들이므로,
래퍼 입장에서 이 앱은 같은 앱이다. 크기 증가분도 정체가 설명된다 — 설명 안 되는
증가가 있었다면 뭔가 더 바뀐 것이다.

한 군데는 손을 봐야 했다. JEDEC **전송 실패** 경로는 `xfer()` 껍데기를 못 거쳐서 문구를
직접 찍는데, 처음에 `"…len=4"`를 리터럴로 박았더니 **문자열이 하나 늘었다.** 기존 포맷에
`4u`를 넘기도록 고쳐 문자열 테이블을 기준선과 같게 맞췄다. 사람 눈에는 같은 출력이지만
**"19개 동일"이라는 증거를 깨는 차이**였다.

**그래도 이것은 보드 검증을 대신하지 못한다.** 위 증거는 "같은 문구를 낸다"까지다.
SPI 타이밍·전송이 같다는 것은 칩이 대답해야 증명된다 — §4 ②.


### 2-8. `id` 를 `reproduce.py` 의 기본 단계로 (로그 35 미결 4 확정)

처음에는 `jedec`·`smoke` 처럼 `default=False` 로 두었다. 그러나 `--mode sweep` 은 이 ELF 가
없으면 **시작도 못 한다** — 실제로 `missing …/flash_id.elf — vitis -s ps/scripts/build_flash_id.py
먼저` 로 멈춘다. 선택으로 두면 "빌드는 8/8 PASS 인데 보드 앞에서 측정을 못 하는" 상태가
만들어지고, 그 사실을 **빌드 시점이 아니라 측정 시점에** 알게 된다.

앵커 재측정(chip02 ②③④)이 W10-M 일정에 있어 측정하는 사람은 전부 필요하다. 비용은 17초다.

    FULL       = [sim, selftest, g0, g2, prep, id, g3-25, g3-45, g3-75]
    VITIS_ONLY = [sim, selftest, g0e, prep, id, g3e-25, g3e-45, g3e-75]

`id` 는 g2 XSA 를 쓰므로 `g2` 뒤, `prep` 옆이다. `--only id` 실측 **PASS (17s)** — 완료 문구·
산출물 경로·mtime 채점까지 확인했다. `docs/build_reproduction.md` 의 단계 나열도 갱신.

## 3. 남는 한계 (새로 생긴 것이 아니다)

**UID 대조는 "다른 칩을 꽂았다"만 잡는다. "재장착을 안 했다"는 못 잡는다.** 사람이 칩을
빼지 않고 엔터만 쳐도 UID는 당연히 일치한다. **재장착 σ의 신뢰는 여전히 사람 손에 있다.**

로그 23 부록 A가 이미 지적한 한계이며, 이번 작업이 좁힌 것이 아니다. 여기 다시 적는
이유는 "이제 기계가 확인한다"가 그 한계까지 덮는 것으로 읽힐 수 있어서다.

배치 중 칩이 바뀌지 않는다는 가정(UID를 배치 시작 시 한 번만 읽는다)도 그대로다.

## 4. 미결 의사결정

### ① `docs/workflow/9` §2-3의 `flash_uid.c` 행 — **닫았다 (한영웅 확정)**

행을 "완료 — 한영웅, 2026-09-16"으로 닫고, 그 앱이 **왜 모양이 달라졌는지**를 표 아래
적었다. "UID만 읽는 소형 앱"으로 출발했으나 배관이 `flash_prep`과 통째로 겹쳐서
**부품(`flash_io.h`/`.c`) + 앱(`flash_id.c`)으로 갈린 것**이다. 이름이 `flash_uid`가
아닌 것도 JEDEC 진단을 겸해서다. 항목이 없어진 게 아니라 자란 것이므로 그 경위가 표에
남아야 한다 — 안 남기면 다음에 "그래서 flash_uid.c는 어떻게 됐나"를 다시 묻는다.

**남은 것은 B-0·B-1의 담당뿐이다.** 원래 선택지 ②의 "`flash_uid.c`만 세은" 부분이
사라졌으므로 회의에서 그 둘만 정하면 된다.

같이 갱신한 현재 상태 문서 둘 — 로그(24·35 등)는 시점 기록이라 그대로 뒀다.

### ② 보드 검증 — 사람이 해야 한다. **chip05~10 측정 전에 닫을 것**

ELF는 둘 다 빌드돼 있다(§2-6 ①, §2-7). 남은 것은 보드 위의 4단계다.

```
1. xsct ps/scripts/program_g2.tcl build/vitis_id/flash_id/build/flash_id.elf
   → #G2 JEDEC EF 40 17 · #G2 UID <16hex> 가 등록부 값과 일치
2. 직후 flash_prep 을 돌려 UID 가 같게 나오는지 교차 확인    ← 읽기 경로 동치 증명
   그리고 #PREP PASS 까지 완주하는지                        ← flash_prep 이전(§2-7) 회귀
3. run_sweep_chip.py --mode sweep --chip chip04     → 대조 통과 후 스윕 진행
4. 일부러 다른 --chip 을 주면 스윕 전에 중단하는지
```

**2가 핵심이고, 이번에는 두 가지를 동시에 건다.** `flash_io`가 `flash_prep`의 코드를
그대로 옮겼다는 주장은 두 앱이 같은 칩에서 같은 UID를 낼 때만 증거가 되고, **`flash_prep`
자신이 부품 위로 옮겨간 것(§2-7)도 여기서 회귀 검사된다.** 문구 19개 동일은 호스트
파서에 대한 증거일 뿐, SPI 타이밍이 같다는 것은 칩이 대답해야 증명된다.

**순서가 중요하다.** `flash_prep`은 chip05~10을 측정할 앱이므로 **이 검증이 그 측정보다
먼저**여야 한다. 측정을 시작한 뒤에 빌드 문제를 알게 되면 그 측정이 통째로 의심스러워진다.

4도 빼지 말 것 — **안전장치는 걸리는 것을 봐야** 걸린다. 다만 2는 `flash_prep`이라
**P/E를 하나 쓴다.** 앵커(chip02)나 이미 마모 이력이 있는 칩에서 하고, 신품
chip05~10으로는 하지 말 것.

#### 2026-09-16 23:19 실측 — 1·3 통과, 2는 절반, 4는 미검증

`id` 단계를 `FULL`로 올린 뒤(§2-8) ELF 존재만 확인하려던 명령이 보드가 붙어 있는 채로
끝까지 돌았다. **의도한 검증이 아니라 우발 실행이다** — 그래서 무엇이 증명됐고 무엇이
아직인지 구분해 적는다. chip04(P/E 1), `--mode sweep`이라 **P/E는 늘지 않았다**.

**2가 절반인 이유를 분명히 해 둔다.** `flash_id`가 읽은 UID 는 `D16484578B525622` 로

읽은 것이다. 즉 이번 실측이 증명한 것은 "`flash_io`의 읽기 경로가 원본과 같다"까지이고,
**§2-7 에서 부품 위로 옮긴 `flash_prep` 자신이 보드에서 여전히 완주하는지는 아직
검증되지 않았다.** `#PREP PASS` 를 보드에서 한 번 봐야 한다. 그 검증이 **chip05 측정보다
먼저**라는 §4 ② 의 순서 지시는 그대로 유효하다.

**`--n-reads` 기본값(100)과 ELF(112) 불일치로 마지막에 중단됐다.** 방어가 작동한 것이고
CSV 는 남았다(`n_reads` 열이 진실). 기본값을 112 로 바꿀지는 미결 — 실칩 25MHz 가 112 라
매번 인자를 주는 것이 잊히기 쉽다 (`project_pipeline.md` 도 같은 지적을 적어 두었다).

### ③ 남은 중복 — `flash_jedec`은 소유자 합의가 먼저다

`flash_prep`은 옮겼고(§2-7), `flash_jedec`에는 `uart_set_baud`·SPI0 초기화·JEDEC 읽기가
그대로 남아 있다. **기술적 이유가 아니라 소유 문제다** — 장세은 소유(게재 2번 산출
경로)이고, 게재물 캡처가 그 앱의 출력이라 소유자 합의 없이 건드릴 파일이 아니다.
`core_smoke`(세은)·`g0_sweep`은 SPI를 안 쓰고 `uart_set_baud`만 겹친다.

셋 다 마모 엔진(`flash_wear`) 때 같이 본다. 그때 `flash_io`에 무엇을 더 넣을지가
드러난다 — 지금 미리 설계하면 쓰이지 않을 추상이 생긴다.
