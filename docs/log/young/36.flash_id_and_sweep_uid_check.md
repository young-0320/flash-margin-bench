## 근거

### 2-1. 왜 새 앱이 필요했나

UID(4Bh)는 g2 비트스트림(PS SPI) 위에서만 읽힌다. PL 경로는 `flash_spi_ctrl.v:120`이
`0x0B` 40클럭 프레임에 고정돼 막혀 있다(로그 23 §0). 그런데 **g2 위에서 도는 앱이
`flash_prep` 하나뿐이고 걔는 반드시 소거·쓰기를 한다.**

| | `--mode newchip` | `--mode sweep` (전) | `--mode sweep` (후) |
| --- | --- | --- | --- |
| 세션1 | `flash_prep` — UID 읽기 O, **P/E +1** | **없음** | `flash_id` — UID 읽기 O, **P/E 불변** |
| 신원 | 기계가 읽는다 | 사람 선언 | 기계가 읽어 **대조한다** |

앵커 재측정에서 P/E를 태우지 않으려고 세션 1을 통째로 뺀 것이 신원 확인까지 같이
없앤 것이었다. **읽기만 하는 앱**을 만들어 그 둘을 분리했다.

### 2-2. `flash_io` — 사본이 아니라 이전

`flash_id`가 필요로 하는 배관(UART 보 레이트·SPI0 초기화·전송·JEDEC·UID)은 전부
`flash_prep.c`에 이미 있었다. 복사하면 다섯 번째 사본이 된다.

**처음에는 새 코드만 부품으로 만들고 `flash_prep`은 두려고 했다** — 그것이 chip05~10을
측정할 바로 그 앱이라, 빌드가 바뀐 사실을 측정 도중에 알게 될까 봐. 그러나 그러면 같은
배관이 두 벌 남는다. **§2-7에서 `flash_prep`도 부품 위로 옮겼고, 값이 안 바뀌었다는
증거를 빌드 전후 비교로 확보했다.** 사본이 아니라 이전이다.

9/15 보 레이트 변경 때 네 파일을 다 고친 것이 이 중복의 비용이었다.

| 배관 | 작업 전 | 작업 후 |
| ---- | ------- | ------- |
| `uart_set_baud` | 4 (전 앱) | 3 (`flash_io` + `flash_jedec`·`core_smoke`·`g0_sweep`) |
| SPI0 초기화 | 2 | 2 (`flash_io` + `flash_jedec`) |
| JEDEC 읽기 | 2 | 2 (`flash_io` + `flash_jedec`) |
| UID 읽기 | 1 | 1 (`flash_io`) |

`flash_jedec`이 남은 이유는 기술적인 것이 아니고, **미룬 것도 아니라 두기로 한 것이다** —
근거는 §4 ③. `core_smoke`(세은)·`g0_sweep`은 SPI를 안 쓰고 `uart_set_baud`만 겹친다.

구현은 `flash_prep.c`에서 **그대로 옮겼다.** 프리스케일러(`PRESCALE_64`)·보 레이트
(921600)·`UID_LEN=8`·4Bh 3회 읽기 — 값을 하나도 바꾸지 않았다. 읽기 경로가 같아야
"`flash_id`가 읽은 UID = `flash_prep`이 읽은 UID"를 주장할 수 있다.

**유일한 차이: `flash_io`는 아무것도 출력하지 않는다.** 실패 문구의 접두(`#PREP`/`#G2`)가
앱마다 다르고 호스트 파서가 그 접두로 종료를 판정하기 때문이다(로그 24 §8 「중요 1」). 판정과
출력은 앱이 한다. UID 실패만 원인별로 갈라 돌려준다 — `-1` 전송 3회 실패 / `-2` 3회 읽기
불일치. 원본의 두 FAIL 문구를 앱이 그대로 낼 수 있게 하려는 것이다.

### 2-3. `flash_id` — 쓰기 명령을 한 바이트도 내보내지 않는다

소거·프로그램·WREN 없음. **그것이 이 앱의 존재 이유다.**

    #G2 ID — 읽기 전용 신원 확인 (소거·쓰기 없음)
    #G2 JEDEC ef 40 17 [OK] W25Q64 확인 — 보드-모듈 통신 정상
    #G2 UID D1642C74E7134527

**JEDEC을 같이 읽는 이유.** UID가 읽히면 통신은 이미 증명된다. JEDEC의 값어치는
**실패했을 때 원인을 가르는 것뿐**이다.

| 응답 | 뜻 |
| ---- | --- |
| `FF FF FF` | 무칩·오배선 — D0 배선표 + /WP·/HOLD 3V3 |
| `00 00 00` | 무칩·오배선·전원 — VCC·GND·CS |
| 그 외 ID | 다른 칩이거나 간헐 접촉 |

코드 3줄에 그 진단이 붙으므로 넣었다. 문구는 `flash_jedec.c`의 분기를 그대로 따랐다.
**이름이 `flash_uid`가 아니라 `flash_id`인 이유이기도 하다** — 신원(identity)에는 품종과
개체가 같이 들어간다.

### 2-4. 래퍼 통합 — `--chip`이 선언에서 검증으로

`run_id()`는 `run_prep()`과 같은 꼴이다. `program_g2 + flash_id`를 굽고 `#G2 UID`를 파싱해
등록부에서 역조회한 기대 UID와 대조한다. 어긋나면 **스윕을 시작하기 전에** 중단한다.

    칩 대조 실패 — 소켓의 칩이 chip04 가 아니다. 스윕을 시작하지 않는다
        읽은 UID : D1642C74E7134527 (chip02)
        기대 UID : D16484578B525622 (chip04)

읽은 UID의 라벨까지 찍는 것이 요점이다. "틀렸다"만으로는 사람이 다음 행동을 모른다 —
**무슨 칩을 꽂았는지**까지 답해야 소켓 앞에서 바로 고친다.

두 가지를 원본에서 그대로 지켰다.

- **드레인 스레드**(`run_xsct(..., ser=ser)`). 보드는 ELF가 뜨는 순간부터 뿜는데 xsct
  종료를 기다리며 안 읽으면 커널·FTDI 버퍼가 넘친다 — 2026-09-15 chip02에서 19스텝
  결측(무효 ⑤)으로 실현된 적이 있다
- **세션 로그 개명은 대조 통과 후.** 실패는 `session_idfail_*`로 남긴다. 확인되지 않은
  칩의 로그에 라벨을 박으면 그 파일이 나중에 증거로 읽힌다

### 2-5. `reproduce.py`의 선택 단계 `id`

`jedec`·`smoke`와 같은 꼴(`default=False`). 편의만이 아니다 — `run_step()`이
`PYTHONUTF8=1`을 자식에 강제하므로([로그 33](33.reproduce_windows_support.md) §2-5) **Windows에서는 이 경로로 빌드해야 한다.**
`flash_io.c`·`flash_id.c`도 한글 주석·문자열을 담고 있어 Vitis 내장 파이썬이 cp949로
읽으면 죽는 다섯·여섯 번째 파일이다.

    uv run python reproduce.py --only id

### 2-6. 검증 — `flash_id` 쪽

**⑥ 보드 실측 (`session_chip04_D16484578B525622_20260916T151941Z.log`)**

```
#G2 ID — 읽기 전용 신원 확인 (소거·쓰기 없음)
#G2 JEDEC EF 40 17 [OK] W25Q64 확인 — 보드-모듈 통신 정상
#G2 UID D16484578B525622
칩 대조 OK: 소켓의 칩 = chip04 (D16484578B525622)
[1/1] VALID sweep_…20260916T152000Z.csv (2520 rows) · 분석 OK width@1e-2=39689.78 ps
```

**설계대로 동작했다.** 읽은 UID가 등록부 값과 일치했고, 대조를 통과한 뒤에야 스윕으로
넘어갔다. width는 같은 칩 최초 측정(39,687.93) 대비 **+1.85ps** — 재측정 산포 안이다.
UART 선수신 163B가 로그에 찍혀 드레인 스레드도 제 일을 했다.

**⑦은 여전히 미실행이다 — §4 ②.** ⑥이 증명한 것은 "`flash_id`가 등록부와 같은 UID를
읽는다"까지고, **그 값이 `flash_prep`이 읽는 값과 같은지**는 두 앱을 연달아 돌려야 한다.
`flash_io`가 `flash_prep`의 코드를 그대로 옮겼다(§2-7)는 주장이 걸린 자리다.

**같은 날 드러난 것 — `idfail` 이름이 과했다.** 15:17 실행이
`session_idfail_20260916T151722Z.log`로 남았는데, 내용은 UID 불일치가 아니라 **ELF 누락**
이었다(`missing …/flash_id.elf`). 그 이름은 "꽂힌 칩이 다르다"를 뜻해야 하는데 빌드를
안 한 것까지 같은 이름으로 남으면 **나중에 그 로그를 칩을 잘못 집은 기록으로 읽는다.**
`ses.rename("idfail")`을 UID 불일치 지점으로만 옮겼다 — ELF 누락·`flash_id` FAIL·타임아웃은
기본 이름(`session_<batch_id>.log`)으로 남는다.

### 2-7. `flash_prep`을 부품 위로 — 그리고 값이 안 바뀌었다는 증거

같은 배관이 두 벌 남는 것이 이상해서 `flash_prep`도 옮겼다. 나간 것은 `uart_set_baud`·
SPI0 초기화·`XSpiPs_PolledTransfer`·JEDEC 읽기와 대조·UID 3회 읽기다. 순 **-20줄**이고
`XSpiPs`/`XUartPs` 참조가 **0**이 됐다.

남긴 것 하나: **`xfer()` 껍데기.** `flash_xfer`에 `#PREP ERROR`를 입히는 세 줄이다.
부품은 출력하지 않고 호스트 래퍼가 그 줄을 종료 신호로 읽으므로(로그 24 §8 「중요 1」)
접두는 앱에 남아야 한다.

문제는 이것이 **측정 중인 앱**이라는 것이다. "값을 안 바꿨다"를 주장이 아니라 증거로
만들어야 해서, **리팩터 전 ELF를 먼저 빌드해 두고 비교했다.**

| 항목 | 전 | 후 | 판정 |
| ---- | --- | --- | ---- |
| `#PREP` UART 출력 문구 | 19개 | 19개 | **완전 동일** (diff 0) |
| text | 38,773 | 39,221 | +448 — `-O0`이라 호출이 인라인되지 않는다 |
| data | 1,528 | 1,528 | 동일 |
| bss | 23,652 | 23,684 | +32 = `flash_io`의 13B 버퍼 2개(정렬 포함) |
| 우리 소스 경고 | 0 | 0 | BSP·FSBL 경고만 남는다 |

**문구 diff가 0인 것이 핵심이다.** 호스트 파서가 보는 것이 정확히 그 문구들이므로,
래퍼 입장에서 이 앱은 같은 앱이다. 크기 증가분도 정체가 설명된다 — 설명 안 되는
증가가 있었다면 뭔가 더 바뀐 것이다.

한 군데는 손을 봐야 했다. JEDEC **전송 실패** 경로는 `xfer()` 껍데기를 못 거쳐서 문구를
직접 찍는데, 처음에 `"…len=4"`를 리터럴로 박았더니 **문자열이 하나 늘었다.** 기존 포맷에
`4u`를 넘기도록 고쳐 문자열 테이블을 기준선과 같게 맞췄다. 사람 눈에는 같은 출력이지만
**"19개 동일"이라는 증거를 깨는 차이**였다.

**그래도 이것은 보드 검증을 대신하지 못한다.** 위 증거는 "같은 문구를 낸다"까지다.
SPI 타이밍·전송이 같다는 것은 칩이 대답해야 증명된다 — §4 ②.

### 2-10. 보드 검증 2 통과 — 그리고 폭이 70ps 움직였다 (2026-09-16 16:18)

chip02 를 `--mode newchip` 으로 돌려 `flash_prep` 이 부품 위에서 완주하는지 봤다.
**chip05~10 을 열기 전에 닫아야 했던 마지막 검증이다.**

```
#PREP JEDEC EF 40 17 · #PREP UID D1642C74E7134527
#PREP BLANK pre bits=2097152        ← 정답지가 이미 쓰여 있음 (정상)
#PREP erase done (128 sectors) · SUMMARY n=128 min=24014 max=32532 mean=27411 over400ms=0
#PREP BLANK post bits=0 · program done
#PREP PASS all 2048 pages verified
chip_pe.md: chip02 0~127 +1         ← P/E 5 → 6
```

**소거 시간 평균 27,411µs 는 chip02 의 기존값 27,151µs 와 사실상 같다.** §2-7 의 "문구 19개
동일" 이 호스트 파서에 대한 증거였다면, 이것은 **칩에 대한 증거**다 — SPI 타이밍이 리팩터
전후로 같다는 것은 칩이 대답해야 증명되고, 대답이 같았다.

#### 그런데 폭이 70ps 줄었다

| 측정 | width @ 1e-2 | G-a 기준(39,630.2 ± 14ps) |
| ---- | ------------ | ------------------------- |
| 2026-09-15 ① 3회 평균 | 39,630.2 | 기준값 |
| 오늘 16:10 `sweep` (prep 없음) | 39,633.7 (+3.5) | **안** |
| 오늘 16:18 `newchip` (prep 직후) | **39,563.1 (−67.1)** | **밖 — 허용치의 4.8배** |

**장비 드리프트가 아니다.** 8분 전 같은 칩이 기준 안에 들었다. 두 측정 사이에 있었던 일은
둘이다 — **재장착(칩을 뺐다 다시 꽂음)** 과 **prep(소거 + 정답지 재작성 + P/E +1)**.

해석 후보, 유력한 순서대로:

1. **재장착 그 자체 — 가장 유력하다.** 측정자가 칩을 빼고 다시 꽂았고, PMOD 결합이 덜
   물렸거나 손의 습기·피지가 핀에 닿았을 수 있다. 접촉 저항이 바뀌면 SPI 가장자리가
   흐려져 폭이 준다. **이것이 바로 §8 이 재장착 σ 로 재려는 성분**이다
2. **프로그램 직후 전하 안정화 전**(post-program relaxation). 그렇다면 "쓰고 나서 얼마나
   기다렸다 재느냐" 가 측정 조건이 된다 — 지금 절차에는 그 대기가 없다
3. **P/E 1회의 마모 효과.** S-1 의 조밀화 트리거가 1.83ps(3σ)인데 1사이클에 70ps 면 마모
   실험 설계 자체가 성립하지 않는다. 가장 약한 해석이다

#### 이것이 왜 급한가 — 재장착 노이즈가 개체차보다 크다

| | 크기 |
| --- | --- |
| 칩 개체차 (chip02 39,630 · chip03 39,653 · chip04 39,688) | **58 ps** |
| 오늘 재장착 1회의 변화 | **70 ps** |

**재장착 노이즈가 개체차보다 크면 측정 시스템이 개체를 분해하지 못한다.** 전수 조사는
개체 산포를 보려는 것인데, 소켓에 다시 꽂는 것만으로 그보다 큰 변동이 생기면 10개
데이터의 §6.3 판정이 통째로 흔들린다 — MSA 에서 말하는 계측 시스템 부적합이다.

다만 **n=1 이다.** 이것은 σ 가 아니라 차이 하나이고, 위 셋 중 무엇인지도 아직 안 갈린다.
**앵커 ②③④(재장착 3회)가 정확히 이 값을 재는 절차**이므로, 전수 측정에서 그것을 빠뜨리면
안 된다는 것이 이 관측의 결론이다.

**가리는 방법.** ①과 ②③은 재장착 없이 연속 2회를 재면 갈린다 — 값이 돌아오면 재장착이
원인이고, 안 돌아오면 prep 쪽이다. 30분 뒤 한 번 더 재면 relaxation 과 마모도 갈린다.

**실무적 함의 — 앵커(②③④)는 prep 없이 재야 한다.** 재장착 성분만 보려는 절차인데 prep 을
끼우면 재장착·쓰기·마모가 한 값에 섞여 σ_repeat 가 무엇의 산포인지 알 수 없게 된다.
P/E 도 매번 오른다. `--mode sweep --chip 2` 로 재면 된다 (S-2 §8 에 추기).

**가리는 방법도 싸다** — prep 직후 1회, 30분 뒤 1회를 같은 칩에서 재면 ①(relaxation)과
②(마모)가 갈린다. 마모라면 안 돌아오고, relaxation 이면 돌아온다. **chip05 측정 전에
할 필요는 없다** — 전수 측정은 모두 prep 직후 조건으로 일관돼 있어(chip02·03·04 도 그랬다)
개체 산포 비교에는 영향이 없다.

### 3. 남는 한계 (새로 생긴 것이 아니다)

**UID 대조는 "다른 칩을 꽂았다"만 잡는다. "재장착을 안 했다"는 못 잡는다.** 사람이 칩을
빼지 않고 엔터만 쳐도 UID는 당연히 일치한다. **재장착 σ의 신뢰는 여전히 사람 손에 있다.**

로그 23 부록 A가 이미 지적한 한계이며, 이번 작업이 좁힌 것이 아니다. 여기 다시 적는
이유는 "이제 기계가 확인한다"가 그 한계까지 덮는 것으로 읽힐 수 있어서다.

배치 중 칩이 바뀌지 않는다는 가정(UID를 배치 시작 시 한 번만 읽는다)도 그대로다.

이미 달성했고 뒤에 할 일이 없다. **회수할 미래 비용이 없는 곳의 중복은 비용이 아니다.**

**둘째, 게재물의 출처 코드라 "찍을 때 코드 = 지금 코드"가 유지되는 편이 낫다.**

그 앱의 출력이다. `flash_prep`은 산출이 CSV라 코드가 바뀌어도 **출력 문구 19개 diff 0**
으로 동등성을 보일 수 있었지만(§2-7), **캡처는 그림이라 그 논증이 통하지 않는다.**
리팩터해두면 게재물 재현을 물을 때마다 "코드가 달라진 경위"를 설명해야 한다.

**셋째, 소유자가 다른데 얻는 것이 25줄이다.** 81줄 중 배관이 25줄쯤이다. 남의 파일을

반복이고 `flash_jedec_check()`는 1회 읽고 판정을 반환하는 모양이라, 끼우면 그 앱 고유의
"실패해도 계속 재시도" 흐름이 한 겹 어색해진다.

남는 비용은 하나다. **보 레이트를 또 바꾸면 여전히 3곳**(`flash_jedec`·`core_smoke`·

#### 5-2. 무엇이 문제인가

`--mode sweep`(등록된 칩 재측정, P/E 불변)은 `flash_prep` 을 돌리지 않는다. 그런데 칩을
확인하는 일이 전부 그 앱 안에 있었다.

| | `--mode newchip` | `--mode sweep` |
| --- | --- | --- |
| 세션1 | `flash_prep` | **없음** |
| JEDEC(접촉·배선) | O | **×** |
| UID(신원) | O — 기계가 4Bh 를 3회 읽음 | **×** — 사람이 `--chip` 으로 선언 |
| P/E | +1 | 0 |

**P/E 를 아낀 대가로 확인을 통째로 잃은 상태**다. 설계 의도가 아니라, "UID 를 읽으려면
반드시 지워야 한다"는 제약에서 나온 부작용이다.

위험이 비대칭이다. 잘못 집은 칩으로 측정하면 **CSV 에 남의 UID 가 박히고**, 사후에
판별할 방법이 없다. 앵커(chip02)를 사이사이 끼우는 W10-M 에서 특히 실현 가능성이 높다 —
책상에 육안 구분이 안 되는 칩이 10개 널려 있다.

**로그 23 부록 A 가 이 상황을 예고했다**: W5-D(책상에 chip01 한 개)에서는 오배치가 물리적으로
불가능해 UID 전용 앱을 만들지 않기로 했고, **"W5-M(10칩 배치)에서는 다르다 … `flash_uid.c` 가
필요하다"** 고 적어 두었다. 과거 판단을 뒤집는 게 아니라 **그 조건이 도래했다.**

#### 5-3. 결정과 근거

#### D1. `flash_jedec.c` 를 확장하지 않고 새 앱을 만든다

`flash_jedec` 은 이미 UART 설정·SPI 초기화·JEDEC 읽기를 갖고 있어 **UID 읽기 25줄이면**
끝난다. 그럼에도 새 앱으로 간다.

- 그 파일은 **장세은 소유**다 (헤더: "스펙·검토·게재물 캡처 소유: 장세은", [로그 9](9.g2_jedec_bringup_prep.md) ③).
  게재 2번(성공 캡처 + 모듈 분리 대조군)의 산출 경로다
- **앱 하나 = 목적 하나**가 지금 4개 앱이 지켜온 규칙이다. 진단·게재용 앱이 측정 전
  신원 확인까지 겸하면 둘 중 하나를 바꿀 때 다른 하나가 딸려 온다
- `flash_jedec` 은 1초 주기 무한 루프다. 측정 직전에 쓰기엔 성격이 다르다

25줄을 아끼자고 소유가 갈린 게재물 파일을 건드릴 이유가 없다.

#### D2. 공용 부품은 신설하되, **기존 앱은 옮기지 않는다**

> **2026-09-16 — 같은 날 뒤집혔다 (§2-7).** `flash_prep` 을 부품 위로 옮겼다. "측정 중인
> 앱이라 못 건드린다"가 여기서 미룬 이유였는데, 리팩터 전 ELF 를 먼저 빌드해 두고 비교해
> **출력 문구 19개 diff 0** 을 확보하는 것으로 그 위험을 없앴다. 남은 `flash_jedec` 은
> 옮기지 않기로 확정 — §4 ③.

중복 실측 (2026-09-16):

| | `core_smoke` | `flash_jedec` | `flash_prep` | `g0_sweep` |
| --- | --- | --- | --- | --- |
| `uart_set_baud()` | ✓ | ✓ | ✓ | ✓ |
| SPI 초기화 | | ✓ | ✓ | |
| `xfer()` | | | ✓ | |
| JEDEC 확인 | | ✓ | ✓ | |

**UART 보 레이트는 네 앱 전부에 같은 코드로 있다.** 9/15 에 115200 → 921600 으로 바꿀 때
네 파일을 다 고친 것이 이미 치른 비용이다(로그 30 §10.3). 통합할 이유는 충분하다.

그런데 **지금은 아니다**:

- `flash_prep` 은 **chip05~10 을 측정할 바로 그 앱**이다. 리팩터하면 chip04 와 다른 빌드가
  되고, 프리스케일러·보 레이트가 미묘하게 달라지면 측정 도중에 알게 된다
- `flash_jedec` 은 장세은 소유다 (D1)
- 마모 엔진(`flash_wear`)이 무엇을 필요로 할지 아직 모른다. 지금 인터페이스를 고정하면
  그때 또 고친다

그래서 **새 코드만 부품으로 만든다.** 늘어나는 중복은 `flash_id` 를 독립 파일로 만들든
부품으로 만들든 같고, 부품으로 두면 **미래 통합 지점이 생긴다**. `flash_wear` 를 만들 때
`flash_prep`·`flash_jedec` 을 여기로 옮긴다 — 그때는 캠페인도 끝나 있고 사용처도 확정된다.

#### D3. JEDEC 까지 읽는다 → 이름은 `flash_id`

UID 가 3회 일관되게 읽히면 통신은 이미 증명된다. JEDEC 은 **중복**이다. 그럼에도 넣는다 —
값어치가 **실패했을 때 원인을 가르는 것**에 있기 때문이다.

| UID 만 읽을 때 | JEDEC 도 읽을 때 |
| --- | --- |
| "UID 안 읽힘" | `FF FF FF` → 무칩·오배선 |
| | `00 00 00` → 전원·CS |
| | `EF 40 17` 인데 UID 실패 → SPI 경로 간헐 |

코드 3줄에 이 진단이 붙는다. 밤에 칩을 갈아 끼우다 안 될 때 원인을 바로 짚어준다.

그래서 이 앱은 "UID 를 뽑는 앱"이 아니라 **"신원을 확인하는 앱"**이고, 로그 23·워크플로 9 가
예고한 이름 `flash_uid` 는 절반만 말한다. **`flash_id`** 로 간다 — 앱 이름이 하는 일을 말하는
이 저장소의 규칙(`flash_jedec`·`flash_prep`·`g0_sweep`)과 같은 축이다.

#### D4. 출력 접두는 `#G2`, 형식은 기존 파서와 맞춘다

`flash_jedec` 이 `#G2`, `flash_prep` 이 `#PREP` 를 쓴다. 새 앱은 G2 비트스트림 위에서 도는
진단 계열이므로 `#G2 JEDEC …` · `#G2 UID <16hex 대문자>`. 래퍼 파서는 두 접두를 다 받게 한다.

#### D5. 대조 실패는 **스윕 전에** 중단한다

읽은 UID 와 `--chip` 의 등록부 UID 가 다르면 즉시 `Abort`. 메시지에 읽은 UID·기대 UID·기대
라벨을 모두 찍고, 읽은 UID 가 등록부에 있으면 그 라벨도 같이 보여준다 — "무슨 칩을 꽂았는지"를
사람이 바로 알아야 한다.

세션1 은 약 10초, **P/E 는 0**이다. 이 비용으로 sweep 모드가 newchip 과 같은 수준의 사전
확인을 갖는다.

#### 5-5. 설계 시점의 미결

1. **역할 배분.** 워크플로 9 는 `flash_uid.c` 를 **장세은** 담당으로 둔다. 세은이 Windows
   빌드에 묶여 있어 한영웅이 직접 하기로 했는데, **이 변경은 회의에서 확정할 사안**이다.
   확정 전에는 워크플로 9 를 고치지 않는다

   > **닫혔다 — §4 ①.** 워크플로 9 §2-3 의 `flash_uid.c` 행을 한영웅 확정으로 닫았다.

2. **`flash_prep`·`flash_jedec` 을 언제 `flash_io` 로 옮길 것인가.** D2 는 "마모 엔진을 만들
   때"로 미뤘다. 그 시점에 `flash_wear` 가 요구하는 인터페이스를 보고 한 번에 정한다

   > **닫혔다 — §4 ③.** `flash_prep` 은 같은 날 옮겼고(§2-7), `flash_jedec` 은 **두기로**
   > 확정했다(2026-09-17). 미룬 것이 아니라 닫힌 결정이다.

3. 재장착 미검출은 그대로 남는다 → 아직 열려 있어 `## 미결` 로 옮겼다
4. **`reproduce.py` 에서 선택 단계인가 기본 단계인가.** `jedec`·`smoke` 처럼 `default=False`
   로 두면 필요한 사람만 굽는다. 그런데 `--mode sweep` 에 이 ELF 가 **반드시** 필요하고
   앵커 측정(chip02 ②③④)이 W10-M 일정에 들어 있어, 측정하는 사람은 전부 필요해진다.
   추가 비용은 약 17초. **FULL 에 넣는 쪽으로 기운다** — "빌드는 통과했는데 측정을 못 하는"
   상태를 만들지 않는 것이 `reproduce.py` 의 목적이다. 다만 구현물을 보고 확정한다
   → **확정: `FULL` 에 넣었다** (2026-09-16, 로그 36 §2-8). 구현은 선택 단계로 왔으나,
   `--mode sweep` 이 ELF 없이는 시작도 못 하는 것을 실제로 확인하고 뒤집었다
5. `--mode sweep` 의 세션1 을 선택으로 둘 것인가 → 아직 열려 있어 `## 미결` 로 옮겼다
