## 1. 이 실험을 왜 하는가

SPI NOR Flash는 데이터를 계속 쓰고 지우면 내부 셀이 조금씩 마모된다. 하지만 어느
순간 갑자기 고장 나는 것만 확인하면, 고장 전에 어떤 변화가 있었는지 알 수 없다.

우리 프로젝트는 Flash가 아직 데이터를 정상적으로 읽을 수 있을 때도 다음 값들이
조금씩 변하는지 확인하려는 것이다.

1. 데이터를 안정적으로 읽을 수 있는 **타이밍 window의 폭**
2. 데이터를 쓰는 데 걸리는 **Program 시간**
3. 데이터를 지우는 데 걸리는 **Erase 시간**
4. Program 또는 Erase가 제대로 되지 않은 **오류 비트 수**

즉, 단순히 `정상/불량`만 판정하는 것이 아니라 정상과 불량 사이에 남아 있는 여유인
**마진**을 측정한다.

> 핵심 질문: P/E 횟수가 증가할수록 Flash의 타이밍 마진이나 Program/Erase 특성이
> 달라지는가?

## 2. P/E는 무엇인가

P/E는 **Program/Erase**의 줄임말이다.

- Erase가 끝난 Flash는 모든 비트가 `1`, 즉 `0xFF`인 상태다.
- Program으로 `0x00`을 쓰면 모든 비트가 `1 → 0`으로 바뀐다.
- `0`을 다시 `1`로 만들려면 섹터 전체를 Erase해야 한다.

이번 실험에서 P/E 1사이클은 다음과 같다.

```text
7개 섹터가 모두 0xFF인 상태
        ↓
112페이지 전체에 0x00 Program
        ↓
Program이 제대로 됐는지 확인
        ↓
7개 섹터 Erase
        ↓
모두 0xFF가 됐는지 확인
        ↓
P/E 1사이클 완료
```

현재 사양에서는 1섹터를 16페이지로 계산하므로 다음과 같이 112페이지가 된다.

```text
7 sectors × 16 pages = 112 pages
```

`0x00`을 사용하는 이유는 선택한 영역의 모든 비트를 `1 → 0`으로 바꿔 전체에
Program 스트레스를 주기 위해서다.

## 3. 칩 내부 영역을 어떻게 나누는가

P/E를 반복한 영역만 측정하면 변화가 마모 때문인지, 온도나 장비 때문인지 구분하기
어렵다. 그래서 같은 칩 안에 마모 영역과 비교 영역을 함께 둔다.

### 파일럿 실험의 영역 배치

| 영역 | 섹터 | 시작 섹터 | 역할 |
|---|---:|---:|---|
| wear | 0–6 | 0 | P/E를 계속 반복하여 마모시킴 |
| near control | 7–13 | 7 | wear 바로 옆에서 주변 영향 확인 |
| far control | 2041–2047 | 2041 | 멀리 떨어진 곳에서 공통 변화 확인 |
| tally A | 512 | - | P/E 진행 횟수 보존 |
| tally B | 1536 | - | P/E 진행 횟수의 두 번째 사본 |

```text
Flash 앞쪽                                      Flash 뒤쪽

[0 ... 6] [7 ... 13] .... [512] .... [1536] .... [2041 ... 2047]
  wear       near         tally A    tally B           far
  반복 P/E   비교 영역                                비교 영역
```

### 결과를 비교하는 방법

- wear만 변하면 P/E 마모의 영향일 가능성이 크다.
- wear와 near가 함께 변하면 주변 섹터까지 영향을 받았을 수 있다.
- wear, near, far가 모두 변하면 온도나 측정 환경이 변했을 수 있다.
- FPGA 내부 loopback도 함께 변하면 Flash보다 측정 경로나 접촉 상태를 먼저 확인한다.

near와 far는 wear loop 동안에는 반복해서 지우지 않는다. 하지만 체크포인트 측정을 위해
PRBS를 새로 기록할 때는 Erase와 Program을 한 번 수행한다. 따라서 대조 영역도
체크포인트 수만큼 P/E가 조금씩 증가한다. 로그에는 **영역별 실제 누적 P/E 횟수**를
따로 적어야 한다.

## 4. 전체 실험 흐름

### 1단계. 새 칩 baseline 측정

마모시키기 전의 칩 상태를 먼저 측정한다. 저장소의 S2 문서는 새 칩 10개를 모두 같은
조건에서 측정한 뒤 역할을 나누도록 정하고 있다.

```text
칩 장착
→ JEDEC ID와 UID 확인
→ 초기 상태 및 Erase 상태 확인
→ PRBS 기록과 verify
→ 25 MHz 타이밍 sweep
→ 결과와 UID 기록
→ 모든 칩 측정 후 역할 배정
```

제안된 칩 배정은 다음과 같다.

| 역할 | 수량 |
|---|---:|
| pilot wear | 1개 |
| terminal wear | 3개 |
| blind chip | 2개 |
| unworn control | 2개 |
| spare | 2개 |

baseline 전에 특정 칩을 wear용으로 확정하면 원래부터 특성이 다른 칩을 마모 효과로
오해할 수 있다. 그래서 먼저 10개를 측정한 다음 역할을 배정한다.

### 2단계. P/E 0 체크포인트

파일럿 칩의 UID와 초기 상태를 다시 확인하고, wear·near·far 영역을 같은 PRBS 패턴으로
측정한다. 이것이 마모 전 기준값인 P/E 0 결과가 된다.

### 3단계. 100사이클 시험

바로 수십만 회를 돌리지 않고 wear 영역에만 P/E를 100회 실행한다.

```text
112페이지에 0x00 Program
→ Program 결과 확인
→ 7개 섹터 Erase
→ Erase 결과 확인
→ 횟수 기록
→ 총 100회 반복
```

이 시험에서 주소, 횟수, 로그, 전원 복구가 맞는지 확인한다. 정상일 때만 장기 실험으로
넘어간다.

### 4단계. 장기 P/E와 체크포인트 측정

```text
P/E 반복
→ 정해진 횟수에서 멈춤
→ wear, near, far 측정
→ 결과 저장
→ 다시 P/E 반복
```

중간에 멈추어 측정하는 시점을 **체크포인트**라고 한다.

## 5. 체크포인트에서 무엇을 측정하는가

### 5-1. 타이밍 욕조곡선과 window

FPGA가 Flash의 MISO 데이터를 여러 샘플링 지점에서 반복해서 읽는다. 각 지점에서
발생한 비트 오류율을 그리면 욕조 모양의 그래프가 만들어진다.

오류가 기준보다 낮은 연속 구간이 타이밍 window다.

- window가 넓음: 샘플링 위치가 조금 흔들려도 안정적
- window가 좁음: 작은 타이밍 변화에도 오류가 생길 수 있음

현재 사양은 다음 세 BER 기준의 window 폭을 비교한다.

- `theta = 1e-2`
- `theta = 1e-3`
- `theta = 1e-4`

### 5-2. Program/Erase 시간

각 섹터를 쓰고 지우는 데 걸린 시간도 측정한다. 타이밍 window가 변하지 않더라도
Program 또는 Erase 시간이 변한다면 내부 셀의 상태 변화가 먼저 나타난 것일 수 있다.

### 5-3. 오류 비트

- `program_fail_bits`: `0x00`을 쓴 뒤에도 `1`로 남은 비트
- `erase_residual_bits`: Erase 후에도 `0`으로 남은 비트

오류가 생기면 전체 개수, 처음 발견된 주소들, 오류가 가장 많은 페이지를 기록한다.

### 현재 측정 조건

| 항목 | 사양 값 |
|---|---|
| SPI 속도 | 25 MHz |
| 페이지당 읽기 횟수 | 112회 |
| 페이지당 비교 비트 | 2048 bits |
| 데이터 패턴 | PRBS15 |
| BER 기준 | `1e-2`, `1e-3`, `1e-4` |
| 일반 체크포인트 반복 | 1회 |
| 시작·중간·마지막 반복 | 3회 |

## 6. 체크포인트는 언제 둘 것인가

현재 S1은 변화가 없을 때는 측정 간격을 넓히고, 변화가 보이면 간격을 좁히는 방식을
제안한다.

1. P/E 0에서 첫 측정을 한다.
2. P/E 300에서 두 번째 측정을 한다.
3. 변화가 작으면 다음 체크포인트를 약 2.15배 뒤로 잡는다.
4. 직전 window 폭 변화가 약 1.83 ps보다 크면 다음 간격은 약 1.47배만 늘린다.
5. 변화가 다시 작아지면 2.15배 간격으로 돌아간다.
6. 현재 최대 목표는 P/E 300,000이다.

1.83 ps는 현재 제안된 노이즈 기준이다. 실제로 같은 칩을 다시 꽂았을 때 생기는 차이를
충분히 측정한 뒤 이 값을 확정해야 한다.

## 7. 어떤 로그를 남겨야 하는가

### A. 매 사이클의 작업 시간

7개 wear 섹터 각각에 대해 다음을 남긴다.

- P/E cycle 번호
- sector 번호
- Program에 걸린 시간
- Erase에 걸린 시간
- 측정 시각

100사이클 시험에서는 `100 cycles × 7 sectors = 700행`이 나와야 한다.

### B. 무결성 검사

기본적으로 100사이클마다 다음을 기록한다.

- Program 실패 비트 수
- Erase 후 남은 비트 수
- 오류 주소와 전체 오류 수
- 오류가 가장 많은 페이지
- 칩 UID가 처음과 같은지
- FPGA die temperature
- 측정 시각

첫 오류가 나타난 이후에는 검사 간격을 100사이클에서 10사이클로 줄이는 것이 현재
사양의 제안이다.

### C. 체크포인트 측정

체크포인트마다 다음을 남긴다.

- wear loop의 P/E 횟수
- 측정 영역: wear, near 또는 far
- 해당 영역의 실제 누적 P/E
- 칩 UID
- 시작 섹터와 섹터 수
- 읽기 반복 수와 PRBS 패턴
- 반복 측정 번호
- 실제 sweep CSV 경로
- 사용한 코드의 Git revision
- 온도와 측정 시각

이 정보가 있어야 나중에 그래프의 한 점이 어떤 칩, 코드, 영역에서 나온 것인지 다시
확인할 수 있다.

## 8. 전원이 꺼졌을 때 P/E 횟수 복구

300,000사이클은 순수 cycling만 약 34시간이 걸릴 수 있다. PC나 보드 전원이 꺼지면
RAM에 있던 횟수는 사라지므로 Flash의 별도 tally 영역에도 진행 상황을 남긴다.

- sector 512와 sector 1536에 같은 내용을 두 벌로 기록
- 100사이클마다 다음 빈 바이트를 `0xFF → 0x00`으로 변경
- `0x00` 개수에 100을 곱해 완료한 횟수를 계산
- 두 사본이 다르면 더 큰 값을 사용하고 불일치 사실도 기록
- `0x00`이나 `0xFF`가 아닌 값은 기록 도중 전원이 꺼진 상태로 판단

재시작할 때는 칩 UID, tally 두 사본, PC의 마지막 로그, wear 영역의 Erase 상태를 함께
확인해야 한다.

## 9. 경고 또는 중단 조건

현재 S1 사양의 중요한 보호 조건은 다음과 같다.

| 조건 | 처리 |
|---|---|
| 오류 비트 46개 초과 | `1e-4` window 해석 경고, 실험 계속 |
| 오류 비트 459개 초과 | `1e-3` window 해석 경고, 실험 계속 |
| 오류 비트 4588개 초과 | `1e-2`도 해석하기 어려우므로 중단 |
| Erase 시간 400 ms 초과 | 경고하고 계속 |
| WIP 상태가 2초 초과 | 중단하고 자동 재시도하지 않음 |
| UID 불일치 | 즉시 중단 |

이 조건은 칩을 보호하기 위한 것뿐 아니라, 잘못된 상태로 측정을 계속하여 의미 없는
데이터를 쌓는 일을 막기 위한 것이다.

## 10. 100사이클 시험에서 확인할 것

장기 P/E를 시작하기 전에 다음이 모두 맞아야 한다.

1. 프로그램의 cycle 값이 100이다.
2. PC 로그도 100사이클까지 존재한다.
3. tally 두 사본도 100을 나타낸다.
4. 섹터별 시간 로그가 700행이다.
5. Program 후 `0x00`, Erase 후 `0xFF`가 확인된다.
6. 시작과 종료 시점의 UID가 같다.
7. wear 섹터 0–6만 작업했다.
8. near, far, tally 영역을 잘못 지우지 않았다.
9. 체크포인트 sweep이 정상 완료됐다.
10. wear, near, far의 시작 섹터가 각각 0, 7, 2041로 기록됐다.

전원 차단 복구 시험도 별도로 해보며, 복구한 P/E 횟수의 오차는 최대 100사이클 이하여야
한다.

## 12. 아직 준비되지 않은 것

### 현재 `flash_prep.c`를 반복 사용하면 안 됨

현재 코드는 페이지 0–2047, 즉 섹터 0–127을 Erase/Program한다. 이것을 wear 코드처럼
반복하면 wear 섹터 0–6뿐 아니라 비교 영역인 near 7–13도 함께 마모된다.

따라서 wear 섹터 0–6만 처리하는 전용 반복 코드가 필요하다.

### 전용 wear 실행 코드가 없음

현재 확인한 저장소에는 반복 P/E 전체를 담당할 다음 파일이 아직 없다.

- `ps/src/flash_wear.c`
- `host/run/run_wear.py`

반복 P/E, 시간 측정, 오류 검사, tally 기록과 재시작 기능을 새로 준비해야 한다.

### `BASE_SECTOR` 기능 확인 필요

wear, near, far를 같은 방식으로 측정하려면 측정 시작 섹터를 바꿀 수 있어야 한다.
그러나 현재 호스트 코드는 시작 섹터가 0이 아니면 거부하고, RTL 변경안도 아직 구현 및
승인 상태를 확인해야 한다.

### 읽기 횟수 112회 반영 확인 필요

최신 S1은 112회를 사용하지만 현재 일부 PS 코드는 100회로 고정되어 있다. 기존 결과와
비교할 수 있도록 100회와 112회 사이의 차이를 확인하고 코드를 통일해야 한다.

### 칩 배정과 baseline이 아직 필요함

`docs/chip_registry.md`에는 아직 채워야 할 UID가 있고, chip01은 과거 Flash 준비 과정에서
P/E 노출이 있었다. chip01을 완전한 새 칩으로 가정하면 안 된다.

### 온도값의 한계

현재 XADC로 읽는 값은 FPGA die temperature이며 Flash 칩 자체의 온도가 아니다. 온도와
P/E의 인과관계를 증명하는 값이 아니라 측정 환경이 달라졌는지 확인하는 보조 정보다.

## 13. 기존 GitHub 문서의 숫자가 다를 때

workflow와 과거 로그에는 초기 계획의 값이 일부 남아 있다.

- 읽기 반복 `N=100`
- far sector `249–255` 또는 `121–127`
- tally sector `128`
- 고정된 체크포인트 예시

현재 실험 숫자는 다음 순서로 판단한다.

1. P/E 주소와 측정 수치: `docs/spec/s1.wear_bench_spec.md`
2. 새 칩 절차와 배정: `docs/spec/s2.newchip_protocol.md`
3. 전체 작업 순서: `docs/workflow/5.newchip_baseline_and_wear_bench.md`
4. 실제 과거 실행 내용: `docs/chip_pe.md`와 각 log

따라서 현재 아이디어에서는 wear `0–6`, near `7–13`, far `2041–2047`, tally `512/1536`,
읽기 반복 `112회`를 기준으로 한다. 아직 코드나 승인 상태가 이 값과 맞지 않는 부분은
실행 전에 팀에서 확인한다.

## 14. 결과를 어떻게 해석할 것인가

### wear의 window만 좁아짐

P/E 마모가 외부 SPI 읽기 타이밍에 영향을 주었을 가능성이 있다.

### wear와 near가 함께 변함

마모 영역 주변의 섹터도 영향을 받았을 가능성이 있다.

### wear, near, far가 모두 변함

P/E보다 온도, 소켓 접촉, 케이블 또는 공통 측정 경로가 달라졌을 가능성이 있다.

### window는 같고 Program/Erase 시간만 변함

Flash 내부는 마모되고 있지만 MISO 타이밍에는 아직 영향이 나타나지 않았을 수 있다.
Program/Erase 시간이 더 민감한 노화 지표일 수 있다.

### 오류 비트만 증가함

외부 인터페이스 타이밍보다 셀의 저장 능력이 먼저 나빠졌을 가능성이 있다.

### 아무 변화도 없음

현재 P/E 범위와 측정 방법으로는 변화를 관측하지 못했다는 결과다. 실험 실패로 단정하지
말고 P/E 횟수나 측정 민감도가 충분했는지 검토한다.

중요한 점은 `P/E를 하면 반드시 MISO window가 좁아진다`고 미리 결론 내리지 않는 것이다.
셀 내부 마모가 외부 SPI 타이밍으로 바로 나타난다는 보장은 없다. 반드시 대조 영역과
Program/Erase 시간, 오류 비트를 함께 보고 판단한다.

## 15. 내일 제안할 현실적인 내용

내일 바로 300,000회 장기 P/E를 실행하자는 것이 아니다. 다음 순서로 제안한다.

1. 최신 S1의 주소와 조건을 팀에서 확인한다.
2. 새 칩의 UID와 마모 전 baseline을 먼저 확보한다.
3. wear 섹터 0–6만 건드리는 P/E 코드를 준비한다.
4. near, far, tally가 보호되는지 실제 칩 없이 먼저 확인한다.
5. Program/Erase 시간과 오류 로그가 남는지 확인한다.
6. 전원 차단 후 횟수 복구 방법을 확인한다.
7. 실제 파일럿 칩에는 우선 100사이클만 수행한다.
8. 100사이클 결과가 모두 맞으면 장기 체크포인트 실험을 진행한다.

팀에 전달할 아이디어를 한 문단으로 줄이면 다음과 같다.

> 파일럿 칩의 sector 0–6만 반복 P/E하여 마모시키고, sector 7–13과 2041–2047은 비교
> 영역으로 유지한다. 먼저 100사이클 시험을 통해 주소, P/E 횟수, Program/Erase 시간,
> 오류 및 복구 로그가 정확한지 검증한다. 이후 체크포인트마다 세 영역의 타이밍 window를
> 측정하여 P/E 횟수에 따른 변화를 비교한다.

## 16. 핵심 결론

```text
일부 영역만 의도적으로 P/E 마모
              ↓
마모 영역과 대조 영역을 같은 조건에서 측정
              ↓
타이밍 window + Program/Erase 시간 + 오류 비트 비교
              ↓
완전 고장 전에 나타나는 노화 징후 탐색
```

현재 GitHub에는 Flash 준비와 sweep 측정 기반은 있지만, 안전한 wear 반복, tally 복구,
여러 시작 섹터 측정, 읽기 112회 통일은 아직 확인 또는 구현이 필요하다.

따라서 내일의 목표는 장기 P/E를 바로 실행하는 것이 아니라, **실험 구조를 팀에 제안하고
주소 보호가 확인된 100사이클 파일럿을 준비하는 것**이다.
