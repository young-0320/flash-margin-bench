## 결정

- [D45-1] 응답(`OK`/`REJECT`)의 체크섬은 첫 글자부터다 — 접두가 없다 (2026-09-21, 한영웅의 AI) — §1 · `host/tests/host_side.py`
- [D45-2] 명령 채널의 tally 값(`TALLY`·`RESUME`)은 바이트 수이고 사이클(×100)로 바꾸는 것은 어댑터다. 경계 3·5 의 반환은 mock 과 같이 사이클이다 — §2 · `host/run/wear_link.py`
- [D45-3] `REERASE` 는 `recovering` 이고 **같은 범위의 마지막 `blank_check` 가 잔류를 봤을 때만** 받으며, 잔류가 있는 섹터만 지운다. 아니면 `E_STATE` — §3 · `ps/src/flash_wear.c` · `host/tests/mock_engine.py`
- [D45-4] `write_ok` 는 비파괴 시험이다 — WREN 뒤 WEL 이 서고 BP 가 0 이면 참, WRDI 로 되돌린다 — §4 · `ps/src/flash_wear.c`
- [D45-5] `BLANK` 는 `E_NSECT0`·`E_RANGE` 만 검사한다(읽기라 tally·대조군을 막지 않는다). 부팅 시 `pattern` 은 `0x00` 이라 START 전 `BLANK` 의 `program_fail` 대조값도 `0x00` 이다 — §5
- [D45-6] 정본에 자리가 없는 세 경우의 코드 — 전송 3회 실패는 그 op 의 `program_fail`/`erase_fail` R 행 + `error`, 인자 누락·비숫자는 `E_RANGE`, 모르는 동사는 `E_STATE` — §6
- [D45-7] B(전원 장애 복구)의 「정상 진행」은 재개 뒤 `wear_start(cycle=채택값)` 이 받아들여져 5사이클을 완주하는 것까지 잰다 — §7 · `host/tests/harness.py`
- [D45-8] 재소거의 `chip_pe.md` 증분 행은 섹터 범위=재소거한 섹터, 증분 `±1`, 비고 「reerase · ±1」 — §8 · `host/run/run_wear.py`
- [D45-9] C 엔진의 채점은 호스트 시뮬레이션(fake NOR + 파이프)이 한다. 프로세스 재시작이 보드 리셋이고 칩만 상태 파일로 남는다 — §9 · `ps/sim/` · `host/tests/test_sim.py`
- [D45-10] `git_rev` 는 빌드 스크립트가 생성하는 `wear_build.h` 로 들어간다. `-D` 로 문자열을 넘기지 않는다 — §10 · `ps/scripts/build_flash_wear.py` · `ps/sim/build_sim.sh`
- [D45-11] 실칩 P/E 는 내지 않았다. 인수 시험은 사람이 `run_wear.py accept --i-approve-real-pe` 로 연다. SPI 프리스케일러는 64 그대로다 ([U44-7] 은 열려 있다) — §11

## 근거

### 1. 응답 체크섬의 시작점 — 동사가 본문이다

S-4 §5.2 는 「접두 다음부터 ` sum=` 앞까지」라 하고 행은 `#WEAR `, 명령은 `WEAR ` 라 적었지만
응답의 접두는 적지 않았다. 후보는 둘 — ⓐ `OK `/`REJECT ` 를 접두로 보고 그 뒤부터, ⓑ 접두가
없으니 첫 글자부터. 행에서 종류 글자(`A`)가, 명령에서 동사(`START`)가 본문에 들어가므로 응답의
`OK` 도 같은 자리다 — ⓑ. 실익도 있다: `OK`↔`REJECT` 가 뒤집혀도 체크섬이 잡는다. 이 결정은
`host_side.py` 한 곳에만 있고 C 엔진은 그 함수가 만든 문자열로 시험된다.

### 2. tally 는 바이트로 싣고 어댑터가 곱한다

경계 5 는 `(count_a, count_b, mismatch)` 라 「count」인데 mock 은 처음부터 사이클(×100)을
돌려줬고 `decide_resume` 의 `|a−b| > 100`·`d` 규칙도 그 단위 위에 있다. S-1 §8.3 은 「tally × 100」
이라 tally 자체는 바이트다. 명령 채널을 S-1 의 단위(바이트)로 두고 어댑터가 ×100 을 하면 mock 과
어댑터의 반환 모양이 같아 같은 채점표가 둘 다 잰다. 엔진 쪽에서 곱하는 안은 `DUMP` 의 바이트와
`TALLY` 의 값이 다른 단위가 돼 탈락.

### 3. 잔류 없는 섹터를 지우는 것은 마모다

`pe_engine.md` §2.1 의 REERASE 조건 「가장 최근 blank_check 에서 그 섹터의 부분 소거 확인 ·
요청 섹터가 검출 주소로 계산한 섹터와 일치」를 엔진이 판정하려면 `recovering` 이 마지막
blank_check 의 범위와 잔류를 들고 있어야 한다. 요청 범위가 다르거나 잔류가 0 이면 지울 이유가
없으므로 `E_STATE`. 범위 7섹터 안에서도 섹터마다 다시 읽어 잔류가 있는 것만 지운다 — 재소거는
카운터에 안 들어가는 ±1 이라(§8.2) 불필요한 섹터까지 지우면 그 불확실을 7배로 늘린다.
사건 행은 섹터마다 1행이다.

### 4. 쓸 수 있는지를 쓰지 않고 본다

`write_ok` 의 「write 시험」을 실제 프로그램으로 하면 그것이 곧 마모이고 어느 주소를 쓸지도
없다. WREN 뒤 상태 레지스터의 WEL 이 서는지는 칩이 쓰기 명령을 받아들이는지를, BP 비트는
블록 보호로 막혀 있지 않은지를 비파괴로 보인다. SPI 무응답이면 WEL 이 안 서서 거짓이 된다 —
S-4 §3.1 「SPI 무응답」이 `write_ok=0` 으로 호스트에 닿는다. 셀이 실제로 프로그램되는지는
못 본다 — 그것은 다음 tally 쓰기가 답한다.

### 5. BLANK 는 읽기다

`check_range` 를 START·REERASE 와 같이 걸면 호스트가 대조군을 blank check 할 수 없다.
읽기는 마모가 아니므로 범위만 본다. `pattern` 은 START 인자라 START 전에는 정의가 없는데
`resume` 절차가 START 전에 `BLANK` 를 부르므로 기본값이 있어야 한다 — 파일럿 고정값 `0x00`
(S-1 §1). 인수 시험의 `probe` 기대값(전량 229,376)이 이 값 위에 선다.

### 6. 정본에 자리가 없는 코드

R 행의 `kind` 집합과 거부 11종은 잠겨 있어 새 이름을 만들 수 없다. `flash_xfer` 3회 실패는
폴링 전송에서 사실상 안 나지만(XSpiPs 가 busy 일 때뿐) 자리를 비워 둘 수 없어 그 op 의
`*_fail` 로 적고 `t_us=0` 으로 가른다. 인자가 빠지거나 숫자가 아닌 것은 「인자 범위」 단계의
실패라 `E_RANGE`. 모르는 동사는 「상태에 맞지 않는 명령」에 가장 가까워 `E_STATE`. 셋 다
호스트가 만드는 정상 명령에서는 나지 않는다.

### 7. 「재소거 후 정상 진행」을 잰다

종전 `check_B` 는 잔류가 0 이 됐는지까지만 봤다. `pe_engine.md` §5 가 B 의 경계를
「3 + 4 + 8 + 1(`cycle=채택값`)」로 적으므로 경계 1 까지 밟아야 B 다. `resume_after` 가 §8.3
1~5 뒤에 6 을 짧게(5사이클) 돌리고 `checkpoint_due` 와 `cycle=채택값+5` 를 확인한다.
Hypothesis 의 임의 시점 200례가 전부 이 길을 지난다 — 차단 시점에 따라 채택값이 tally 앞·뒤
어디에 떨어져도 `E_CYCLE` 에 걸리지 않는 것을 여기서 봤다.

### 8. 재소거 행의 증분 칸

S-1 §9 와 `pe_engine.md` 는 「증분 행을 비고 「reerase · ±1」로」라고만 한다. 증분 칸에 `+1`
을 적으면 카운터에 안 들어가는 것을 들어간 것처럼 읽히고, `+0` 이면 마모가 없었던 것처럼
읽힌다. `±1` 이 S-1 §8.3 의 「복원 불확실성 ±1」 그 자체라 그대로 적는다. 섹터 범위는 지운
섹터 하나다 — 7섹터 전부로 적으면 안 지운 섹터에 불확실이 붙는다.

### 9. 실칩 없이 C 엔진을 같은 TB 로

mock 만 통과하면 「엔진은 이렇게 동작한다」를 증명하지 못한다. 엔진을 `flash_io.h` 와
`wear_plat.h` 만 부르게 갈라, 같은 소스를 fake NOR(8MB 배열 · 06/04/05/20/02/03/9F/4B) 와
stdin/stdout 위에 올리면 어댑터 경유로 mock 과 같은 `check_*` 가 잰다. 리셋은 프로세스 재시작
이고 칩은 `WEAR_FAKE_STATE` 파일로만 남아 무상태가 강제된다. 못 보는 것 — WIP 시간·부분 소거의
물리·UART 의 실제 손실. 보는 것 — 문법·상태기계·tally 슬롯·주소 범위(fake 의 P/E 자취가
`[1000, 1007)` + tally 512·1,536 뿐인 것을 TB 가 확인한다).

### 10. git_rev 는 생성 헤더로

`-DWEAR_GIT_REV="\"abc\""` 는 Vitis → CMake → 셸을 지나며 따옴표가 깎일 수 있다. 빌드
스크립트가 `wear_build.h` 한 줄을 생성해 소스 옆에 두면 두 빌드(Vitis·gcc)가 같은 방식이고
소스에 값이 없다. `test_sim.py` 가 H 행의 `git_rev` 와 빌드 시점 HEAD 를 대조한다.

### 11. 실칩 앞에서 멈춘 자리

프롬프트 §0 대로 실칩 P/E 는 사람 승인 뒤다. 프리스케일러는 64(2.6MHz, JEDEC 검증치)로
빌드했고 16·8 은 `WEAR_SPI_PRESCALE` define 으로만 열어 두었다 — 실측 절차는 인수 100사이클을
64 로 먼저 돌려 A6 분포를 얻은 뒤 16 으로 다시 빌드해 같은 시험을 돌리고 `t_program_us` 는
WIP 만 재므로 값이 같아야 하며 사이클 시간(A 행 `ts` 간격)만 줄어야 한다. 남은 것은 [U44-7]·
[U44-8] 그대로다.

발견한 문서 간 어긋남 둘 — S-1 §6 ④ 는 tally 기록을 「검사 주기 도달 시」 안에 두어 조밀화(10)
가 tally 까지 10 단위로 만들지만 §8.1 은 100 단위다(프롬프트 §3 #8 대로 §8.1 을 따랐다).
S-1 §9 B 행의 `die_temp_c` 와 S-4 §5.2 의 `die_temp_mc` 는 이름이 다르다(S-4 를 따랐다 —
XADC 미구현이라 빈 값이다).

알고 넘긴 것 — PS UART RX FIFO 가 64B 라 `running` 중에는 사이클 경계에서만 비운다. START 행은
약 110B 라 `running` 중에 보내면 넘쳐 `E_SUM` 이거나 유실된다. 설계상 `running` 중에 보낼
것은 `HALT`·`STATUS`(30B 안팎)뿐이라 문제가 되지 않지만, 호스트는 응답 없이 다음 명령을 보내지
않아야 한다(S-4 §5.2). `flash_prep` 의 PRBS 시드 `page & 0x3FFF` 는 페이지 16,384 이상(원격
2,041 = 페이지 32,656~)에서 페이지 272~383 과 겹친다 — prep 의 verify 는 같은 시드로 읽어
통과하지만 스윕 쪽 규약(수정안 #1)이 미정이라 정하지 않았다.
