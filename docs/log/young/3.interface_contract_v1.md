## 근거

### 1. 확정문으로 쓰기 시작했다가 후보 문서로 다시 썼다

처음에는 계약서를 확정문 형태로 썼다. 그런데 7/8 아침에 3인이 그것을 읽고 결정해야 하는데,
확정문은 무엇을 고를 여지가 있는지를 보여주지 않는다. **결정 항목별 후보·장단점·추천**
문서로 재작성하고, 채택안만 남겨 확정안으로 갱신하는 흐름으로 바꿨다.

결정 간 의존성부터 정리했다. 위상 아키텍처(계약 0)가 1·2·4 의 전제다. 반면 스윕 주체(2-1)는
어느 쪽이든 핸드셰이크·카운터·CSV 가 불변이라, v0 를 호스트 주도로 시작해도 자율 FSM 은
레지스터 추가로만 도입할 수 있다. 전제인 것과 아닌 것을 갈라 둬야 아침 세션에서 순서가 막히지
않는다.

CSV 후보는 문서가 아니라 `bathtub_analysis.py` 로더 실코드 기준으로 평가했다 — `#` 주석
헤더는 DictReader 가 깨지고(4-2(b) 단점), `bit_err_sq_sum` 열을 생략하면 SKIP 경로가 그대로
동작하며(4-3(a) 근거), 메타데이터 행 반복은 몬테카를로 CSV 의 기존 관례다. 소비자 코드를
열어 보면 후보의 장단점이 취향이 아니라 사실이 된다.

### 2. 위상 아키텍처 — 무엇을 시프트하나 (계약 0)

| 안 | 무엇을 시프트하나 | 판정 |
| --- | --- | --- |
| **A. 샘플 클럭 시프트** | SPI 마스터(SCLK·CS·MOSI)는 고정 클럭 `clk_core`. MISO **캡처 플롭만** MMCM 동적 위상 시프트 출력 `clk_sample` 로 구동 | **채택** |
| B1. SCLK 출력만 시프트 | SCLK 핀만 시프트, 마스터 로직·MOSI·CS 는 고정 | **기각** — 시프트가 커지면 MOSI·CS ↔ SCLK 상대 타이밍이 함께 틀어져 명령 자체가 깨질 수 있음. 에러가 읽기 마진인지 명령 오염인지 구분 불가 (교란 변수) |
| B2. SPI 마스터 전체 시프트 | SCLK·CS·MOSI 를 전부 시프트 도메인에서 생성, MISO 캡처는 고정 도메인 | 물리적으로 A 와 등가 측정. 단 시프트 클럭이 SPI 마스터 전체 + 출력 핀을 구동해 CDC 표면·타이밍 제약이 A 보다 큼 |

A안 권고 근거는 넷이었다.

1. **DUT 자극 완전 불변** — 칩이 보는 SCLK·CS·MOSI 가 모든 위상 스텝에서 동일하다. 곡선의
   변화를 캡처 타이밍 하나에만 귀속시킬 수 있다 (계측의 통제 변인).
2. **시프트 도메인 최소화** — 시프트 클럭이 구동하는 것은 캡처 플롭 + 비교기·카운터 경로뿐.
   SPI 마스터는 단일 고정 도메인이라 flash 서브시스템 설계가 단순해진다.
3. **루프백 G0 와 실칩 경로가 동일 구조** — 출력 핀(고정 도메인 패턴) → 입력 핀(시프트 캡처).
   엔진을 그대로 재사용한다.
4. 프로젝트 서사와 일치한다 — "칩이 아니라 측정기가 경계까지 다가간다"
   (`project_context.md` §3.2).

B1 을 기각한 논거가 이 결정의 핵심이다. 시프트가 커지면 MOSI·CS ↔ SCLK 상대 타이밍이 위상에
따라 틀어져 **명령 오염이 읽기 마진과 뒤섞인다.** 계측에서 교란 변수를 하나 들여놓는 셈이라,
자원이 덜 들어도 살 수 없는 안이었다.

### 3. core ↔ flash 핸드셰이크 (계약 1)

경계는 core(MMCM 위상 제어·AXI-Lite) ↔ flash 서브시스템(SPI 마스터·패턴 비교기·에러
카운터)이고, 이 절 전체가 계약 0 에 종속이다.

**1-1. 시프트 도메인(CDC) 소유권 — 캡처·비교·집계를 누가 갖나**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **flash 측이 캡처~집계+CDC 전부 소유.** 계약 경계는 clk_core 단일 도메인 | 계약이 가장 단순(전 신호 한 도메인). 캡처·비교·카운터가 한 소유자라 프레이밍 재정렬을 내부에서 해결 | 장세은이 mesochronous CDC 를 설계해야 함 (부담 이동) |
| (b) core 가 캡처 플롭+CDC 까지 소유, flash 에 clk_core 동기 비트스트림 전달 | 위상·CDC 지식이 MMCM 소유자(core)에 집중. flash 는 순수 비교기 | 인터페이스에 스트림 신호(데이터+유효+프레임) 추가. 캡처와 비교가 갈라져 버스트 프레이밍 책임 경계가 애매 |
| (c) 결과 카운터를 시프트 도메인 그대로 넘기고 core 가 동기화 | flash 내부에서 CDC 없음 | 계약 신호가 두 도메인 혼재 — 계약 문서가 클럭 주석 범벅이 되고 실수 여지 최대 |

**추천은 (a).** 계약 경계가 단일 도메인인 것이 3인 병렬 개발에서 가장 사고가 적다. CDC 자체는
"done 시점에 결과가 clk_core 에서 유효"라는 한 문장으로 요구사항이 닫힌다. (b)는 장세은
부담을 덜고 싶을 때의 차선이다. CDC 템플릿(2단 동기화 + done 핸드셰이크)은 한영웅이 제공한다.

**1-2. 트랜잭션 프로토콜 형태**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **start 펄스 + busy 레벨 + done 펄스** (결과는 다음 start 까지 유지) | 가장 단순. 스텝당 트랜잭션 1개인 이 용도에 정확히 맞음. 호스트 폴링(STATUS)과 자연스럽게 연결 | 펄스 유실에 민감 — 단 1-1(a)면 동일 도메인이라 해당 없음 |
| (b) 4-phase req/ack | 도메인 경계에 강건 (1-1(c) 선택 시엔 이게 필수) | 동일 도메인에선 과잉. FSM 상태 증가 |
| (c) valid/ready 스트림 | 표준 관례, IP 재사용 용이 | 배압(backpressure) 개념이 불필요한 곳에 도입 — 결과는 스텝당 1개 |

**추천은 (a).** 1-1 을 (a)로 정하면 (b)(c)의 존재 이유가 사라진다.

**1-3. 측정 파라미터(N, B) 전달 방식**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **사이드밴드 `cfg_*` 신호, start 시점 래치** | flash 가 AXI 를 몰라도 됨. "언제 값이 바뀌어도 되는가"가 래치 규약으로 명확 | 신호 2개 추가 |
| (b) flash 가 AXI 레지스터 파일 직접 참조 | 신호 수 최소 | 레지스터 파일이 두 블록에 걸침 — 소유 경계 붕괴. 측정 중 값 변경 시 거동 미정의 |
| (c) 합성 시 파라미터 고정 (N=100, B=2048) | RTL 최소 | 실측 σⱼ 로 N 재확정(G0 체크리스트 3항) 시 재합성 필요 — 실험 반복에 불리 |

**추천은 (a).** (c)는 7/10 까지의 최소품으로는 성립하지만, G0 직후 N 재확인이 예정돼 있어
결국 레지스터화가 필요하다.

### 4. AXI-Lite 레지스터 맵 v0 (계약 2)

**2-1. 스윕 루프의 주체**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **호스트(PS) 주도** — 스텝당 {PHASE_INC → 폴 → MEAS_START → 폴 → 카운터 리드} | RTL 최소(자율 FSM·결과 버퍼 불요) → 7/10 크리티컬 패스 단축. 스텝 단위 관찰 가능해 디버깅 쉬움. 속도 손실 무시 가능 — 스텝당 측정 8.4ms 가 지배적, AXI 폴링은 µs 단위 | 스윕 시퀀싱 책임이 PS 소프트웨어로 이동. 스텝 간 간격이 소프트웨어 지터에 노출 (측정 자체는 HW 라 데이터 오염은 없음) |
| (b) 자율 스윕 FSM + 결과 BRAM — SWEEP_START 한 번에 전 스텝 | 스윕 원자성(호스트 개입 없이 일정한 스텝 간격). 향후 고속 반복 측정에 유리 | FSM + BRAM 리드 인터페이스 RTL 추가 — 마감 전 최대 리스크 구간. 디버깅 시 중간 상태 관찰 어려움 |

**추천은 (a)를 v0 으로, (b)는 v1 확장.** (a)로 시작해도 계약 1·3·4 는 불변이고, (b)는
레지스터 추가만으로 도입할 수 있다(맵 비파괴). G4 반복 측정에서 스텝 간격 일관성이 문제로
드러나면 그때 (b)로 간다.

**2-2. 위상 제어 명령 형태**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **상대 이동: PHASE_INC / PHASE_DEC 펄스** + PHASE_POS(RO) 카운터 | MMCM PS 포트(PSEN/PSINCDEC)와 1:1 — RTL 최소 | 호스트가 위치를 추적해야 함. 호스트-HW 불일치 리스크는 PHASE_POS 대조로 완화 |
| (b) 절대 목표: PHASE_TARGET 쓰고 GO — HW 가 다중 스텝 자동 이동 | 명령 의미 명확, 재시도·재시작 안전 | 위치 비교 + 다중 스텝 FSM 필요. v0 스윕(단조 증가 1스텝씩)에는 과잉 |

**추천은 (a).** 스윕은 어차피 1스텝씩 단조 이동이라 절대 지정의 이점이 없다. PHASE_POS 는
(a)에서도 두어 검증 수단으로 쓴다.

**2-3. DONE / OVF 플래그 클리어 방식**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **다음 MEAS_START 에 자동 클리어** | 호스트 코드 단순(클리어 쓰기 불요). "플래그 = 마지막 측정의 속성"으로 의미 명확 | 측정 사이에 플래그를 읽고 지우는 세밀 제어 불가 (필요 시나리오 없음) |
| (b) W1C (write-1-to-clear) | 표준 관례, 플래그별 독립 제어 | 호스트가 클리어를 빼먹으면 stale DONE 을 새 DONE 으로 오독 — 폴링 루프 버그 단골 |

**추천은 (a).** 폴링 시퀀스가 {START → DONE 대기 → 리드} 하나뿐이라 자동 클리어가 오독
여지를 없앤다.

### 5. 카운터 폭·B_BITS·버스트성 (계약 3)

기준 수치는 위상 스텝당 최대 비트 에러 = N×B = 100 × 2,048 = 204,800, 최소 18비트다.

**3-1. `err_bits` 카운터 폭 — 추천이 뒤집힌 자리**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| 18비트 (최소) | 자원 최소 (미미한 차이) | 여유 0 — N 이나 B 를 조금만 올려도 재계약. 실측 σⱼ 로 N 재확정(G0 체크 3항) 예정이라 위험 |
| **24비트** | N×B 대비 ×81.9 여유 (B=2,048 이면 N ≤ 8,191 까지 무재계약). 상한이 계약에 명시적으로 드러남 | 32비트 대비 특별한 자원 이득은 없음 |
| 32비트 (레지스터 전폭) | 폭 고민 자체를 제거 | "얼마까지 유효한가"가 계약에서 사라짐 — 상한 인식 없이 N·B 를 키우다 스텝당 시간 폭증을 늦게 발견하는 류의 실수 여지 |

추천은 24비트였다. 자원 차이는 셋 다 무의미하고 실질 쟁점은 "상한을 계약에 남기느냐"인데,
24비트가 충분한 여유와 명시적 상한을 동시에 주기 때문이다.

**그 추천을 철회했다.** 설정 필드가 16비트(N, B ≤ 65,535)이므로 err_bits 최대는
65,535² < 2³² 이고, 그러면 **구조적으로 오버플로가 불가능** 해 포화 로직도 필요 없어진다 —
RTL 이 오히려 단순해진다. err_reads 도 같다. "상한 의식"은 설정 필드 폭과 스윕 시간이 이미
담당한다. 추천의 전제였던 "상한을 어디에 남기나"가 다른 곳에서 이미 답이 있었던 셈이다.

**3-2. 오버플로 거동**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| **포화(saturate) + STATUS.CNT_OVF sticky** | 오염이 눈에 보이고(값이 천장에 붙음) 플래그로 해당 스텝 무효 판정 가능 | 포화 로직 약간 추가 (비교기 1개) |
| 랩어라운드 (자연 오버플로) | RTL 추가 없음 | **욕조 곡선 어깨를 조용히 왜곡** — 에러 많은 스텝이 에러 적은 값으로 둔갑. PASS/FAIL 이 아니라 값 오염이라 검증에서도 안 잡힘 (MC 스크립트 `!!` 플래그가 경고한 바로 그 실패 모드) |
| 오버플로 시 측정 즉시 중단(abort) | 오염 데이터 원천 차단 | 중단 상태·재시작 경로가 FSM 에 추가. 곡선 극단(BER~0.5)에서는 포화가 정상 상황이라 중단이 오히려 스윕을 막음 |

랩만은 반드시 배제한다. 극단 위상에서는 포화가 일어나도 되므로(그 스텝 BER 은 어차피 0.5
포화 해석) abort 는 부적합하고, 플래그를 보고 호스트가 판단한다. 3-1 이 32비트로 확정되면서
err_bits·err_reads 는 구조적으로 오버플로 불가가 되어 이 규약은 err_sq_sum 에만 남았고,
3-4 가 (A)로 확정되며 sq_sum 도 하드웨어에서 사라져 **현재 적용 대상이 없다.** 오버플로
가능한 카운터가 새로 생기면 이 규약을 적용하는 원칙으로 유지한다.

**3-3. B_BITS (읽기 1회 버스트 길이)**

제약은 최저 병행 θ=10⁻⁴ 의 유효 조건 N×B×θ ≥ ~20 이다.

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| 512비트 (64B) | 스텝당 시간 1/4 | 조건 충족에 N=400 필요 → 총 비트 수는 동일한데 읽기 오버헤드(40비트/회) 비중만 4배 — 순손해 |
| **2,048비트 (256B, 1페이지)** | MC 의 N=100 권고와 정합 (N×B×θ=20.5). 페이지 단위라 주소 관리 자연스러움. 스텝당 8.4ms·스윕 ~23초(25MHz)로 실용적 | — |
| 4,096비트 (2페이지) | 읽기당 오버헤드 비중 절반, 같은 총 비트에 N=50 | MC 재실행 필요 (N 권고 연쇄 변경). 통계 이득은 총 비트 수가 같으면 없음 |

이미 모든 분석이 2,048 위에 서 있고 대안들의 이득이 미미하거나 음수다. 확정 근거에는 페이지
프로그램 단위(256B)와의 1:1 대응을 넣었고, `monte_carlo_sweep_params.py` 의 `!!` 플래그는
이것으로 해소됐다.

**3-4. 버스트성을 무엇으로 재나 — 논의 중에 후보가 하나 늘었다**

용도는 에러 버스트성 점검, 곧 θ 확정 체크리스트 4항(비트 독립 가정 검증)이고 소비자는
`bathtub_analysis.py` 다.

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| 채택 — error logger 에 제곱 누적기 추가 | 체크 4 를 계획대로 정량 판정 (과분산 F 통계) | logger 에 곱셈기(11×11비트)+32비트 누적기 추가 — 박지민 작업량 증가 |
| 미채택 — `reads_with_error` 로 근사 | RTL 추가 최소 (비교기 1개) | 버스트성 검정력이 낮음 — "에러 있는 읽기 수 vs 이항 기대치" 비교는 약한 버스트만 있으면 못 잡음 |
| 보류 — 신호·레지스터만 예약, 구현은 G0 이후 | 7/10 크리티컬 패스에서 제외하면서 계약 재협상 없음 | G0 데이터로 체크 4 를 못 돌림 → θ 확정이 그만큼 지연 |

여기까지의 추천은 "채택, 단 박지민 부담이 크면 보류(예약)로"였다. 곱셈기라 해도 DSP 슬라이스
1개 수준이고, θ 확정 체크리스트가 G0 직후 예정이라 G0 데이터에 제곱합이 없으면 체크 4 만
뒤로 밀리기 때문이다.

논의 중에 **추가 후보 (A) — 읽기별 에러 수 버퍼** 가 나왔다. 제곱합을 누적하는 대신 읽기별
에러 수 e_i (≤ B=2,048)를 그대로 작은 RAM 에 기록하고, 스텝 종료 후 호스트가 레지스터 창으로
회수한다. 제곱합은 호스트가 파생 계산하므로 CSV 열도 분석기도 불변이다.

(A)를 택한 기준은 구현 난이도가 아니라 **결과의 품질** 이다. 정보 포함 관계가 일방향이라
(A→제곱합은 가능, 역은 불가) 원시값이 보존되고, 사후 재분석과 이상 스텝 원인 추적이 가능해지며,
각 항목이 2,048 이하라 포화 규약 자체가 불필요해진다. 비용은 레지스터 맵 읽기 창 추가(계약 2
개정)와 호스트 회수 코드(주로 한영웅 몫)이고 스텝당 시간은 1% 미만 늘어난다. 박지민 몫 RTL 은
곱셈기에서 RAM 기록으로 **오히려 단순해진다** — 인계 사양이 "읽기 종료마다 e_i 를 RAM 에
기록"이 된다.

파급은 세 군데다. 계약 1 의 `err_sq_sum`·`cnt_ovf` 가 `log_rd_addr`/`log_rd_data` 로 교체되고
(BRAM 2,048×16b, flash 소유, 버퍼 로깅 시 N ≤ 2,048), 계약 2 에 LOG_ADDR/LOG_DATA 창이 생기며
ERR_SQ_SUM·CNT_OVF 가 삭제되고, CSV 의 `bit_err_sq_sum` 열은 호스트 파생으로 재정의된다.

### 6. 스윕 로그 CSV 스키마 (계약 4)

생산자는 PS 스윕 루프, 소비자는 `bathtub_analysis.py` 다.

**4-1. 위상축 표현**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **`phase_step`(원시) + `phase_ps`(파생) 병기** | 클럭 플랜(E) 미확정이 수집을 안 막음 — Δφ 실값 확정 시 step 에서 ps 재계산 가능. 현 분석기(phase_ps 소비)와 즉시 호환 | 컬럼 1개 중복 (파생값 저장 — 원시 물리량 원칙의 예외) |
| (b) `phase_ps` 만 | 컬럼 최소, 분석기 호환 | Δφ 자리표시자로 수집한 데이터는 E 확정 후 **재측정 외엔 복구 불가** (원시값 소실) |
| (c) `phase_step` 만 + 변환은 메타데이터 | 원시 물리량 원칙에 가장 충실 | 분석기 로더 수정 필요. 사람이 CSV 를 직접 볼 때 ps 감각 상실 |

**추천은 (a).** E 결정이 내일 낮으로 밀려 있는 상황에서 (b)는 도박이고, (c)는 분석기 수정을
크리티컬 패스에 추가한다. 파생 컬럼 1개는 실용적 타협이다.

**4-2. 런 메타데이터 기록 위치**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **행마다 컬럼으로 반복** | 리포 기존 관례(몬테카를로 CSV 동일). 행 단위 자기완결 — 분할·병합·이상 런 감지에 강함. DictReader 무수정 | 파일 크기 소폭 증가 (수천 행 × 짧은 문자열 — 무시 가능) |
| (b) `#` 주석 헤더 | 사람이 읽기 좋음 | **현 `bathtub_analysis.py` DictReader 가 그대로 깨짐** (첫 `#` 줄을 헤더로 오인) — 로더 수정 필요 |
| (c) 사이드카 JSON (`.csv` + `.meta.json`) | CSV 순수성 유지 | 파일 2개 동기 관리 — 승격 시 누락 사고 단골 |

**추천은 (a).** 관례 유지 + 파서 무수정이고, 반대 이유가 파일 크기뿐인데 무시 가능한 수준이다.

**4-3. 미구현 컬럼 표기**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **컬럼 자체 생략** | 현 분석기의 SKIP 경로가 이미 동작 ("컬럼 없음 → 체크 4 SKIP" 메시지) | 스키마가 런마다 다름 (컬럼 유무로 구현 여부 판별하는 게 곧 의도) |
| (b) 빈 값 | 컬럼 집합 고정 | 현 로더는 첫 행만 검사 — 중간 행만 비면 int() 크래시. 규약을 "전부 비거나 전부 채움"으로 추가해야 함 |
| (c) -1 등 센티널 | 컬럼 집합 고정, 파싱 균일 | 로더에 센티널 분기 추가 필요. 센티널이 실수로 통계에 섞이는 고전적 사고 |

**추천은 (a).** 분석기가 이미 이 규약으로 짜여 있어 코드 수정이 0 이다.

**4-4. 무효 런 처리**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) **파일명에 `_invalid` 접미** | 디렉토리 목록만으로 식별. 분석 배치가 glob 에서 자연 제외 | 파일명 규약 의존 (이름 바꾸면 정보 소실) |
| (b) `valid` 컬럼 추가 | 정보가 파일 내부에 | 모든 소비자가 필터를 구현해야 — 하나라도 빼먹으면 오염 데이터가 조용히 섞임 |
| (c) 저장 안 함 | 오염 원천 차단 | 디버깅 증거 소실 — 왜 포화했는지 추적 불가 |

**추천은 (a).** "기본 동작이 안전"한 유일한 후보다 — 필터를 안 짜도 무효 데이터가 안 섞인다.

### 7. 클럭 플랜 — 출력 분주비 O 선택 (E)

VCO 는 D=1·정수 M 제약(지터 최소화)으로 이미 1,125MHz 다. MMCM 의 O 는 정수 손잡이라 출력
주파수 f = 1,125 ÷ O 는 **1,125 의 약수만 가능** 하다 (1,125 = 3²×5³ → 1, 3, 5, 9, 15, 25,
45, 75, 125, 225, 375, 1125 MHz). 애초 몬테카를로 비교에 쓴 25/50/100MHz 중 **50·100 은 약수가
아니라 애초에 불가능한 값** 이었다 — 이번 결정으로 그 사실이 확정에 반영됐다.

스윕 시간은 스텝 수(56×O)와 스텝당 읽기 시간이 둘 다 f 에 반비례해 f² 꼴로 줄어든다. 이
관계로 역산한 후보다.

| O | f | 스윕 시간(N=100, 추정) | 판정 |
| --- | --- | --- | --- |
| 75 | 15MHz | ~63초 | 기각 — 불필요하게 느림 |
| **45** | **25MHz** | **~23초** | **채택 (v0, 브링업)** |
| 25 | 45MHz | ~7초 | 향후 후보 |
| 15 | 75MHz | ~2.5초 | 향후 후보 |
| 9 | 125MHz | ~0.9초 | 미검토 — flash 스펙 한계(fR) 근접·초과 여부 확인 필요 |

G0~G4 는 "실칩 저클럭 브링업"(G2)을 포함한 초기 검증 단계다. 이 단계의 목적은 스윕 속도가
아니라 **MMCM 위상 제어·핸드셰이크가 의도대로 도는지 확인** 이므로, 후보 중 가장 느리고
널널한 25MHz 로 시작해 타이밍 여유를 확보한다. 스윕 약 23초는 이 단계에서 감내 가능한
비용이다. Δφ(15.87ps)·2,520스텝은 O=45 기준이므로, O 를 바꾸면 UI 당 스텝 수(56×O)도 함께
바뀐다 — 예를 들어 O=25 면 1,400스텝이다.

확정된 Δφ=15.87ps 로 MC 를 재실행했다. 규칙 std ≤ 7.9ps 기준에서 채택 θ=10⁻²·최악 지터
200ps 일 때 std 가 1.91ps 라, **N=100 을 유지** 한다.

### 8. 밤·심야 6건 — RTL 착수 전 마지막 구멍 봉합

밤에 정한 셋은 하드웨어가 보장해야 할 성질들이다. 17 워치독+TIMEOUT(R10)은 "done 은 유한 시간
안에 보장된다"를 산문 약속이 아니라 하드웨어 성질로 만들었고(T_max=2×N×(B+64)), 18 시끄러운
거부(R11, CFG_ERR)는 R6 를 하드웨어 집행 규칙으로 승격시켰다. 함께 SCLK=clk_core
포워딩(R9)으로 커버리지 함정을 봉쇄하고, STATUS bit4/5 를 추가하고, 무효 런 정의를 5항으로
재작성하고, e_i 원본 저장을 필수로 올렸다(동반 `_reads.csv`).

R11 과 fault injection 의 관계도 이때 확인했다. 의도적 에러 주입은 "합법 설정 + 데이터
오염"이라 CFG_ERR 과 **직교** 하므로 충돌이 없다. CFG_ERR 자체의 검증은 N=0 을 일부러 쓰는
negative test 로 가능한데, 시끄러운 거부이기 때문에 테스트를 쓸 수 있다.

심야의 셋은 측정이 성립하는 조건이다. 19 PRBS-15(x¹⁵+x¹⁴+1, 시드 {1, index[13:0]}, 루프백
index 는 스텝 내 읽기 번호·실칩 index 는 페이지 주소 하위 14비트)는 저전이 패턴에서는 욕조
벽이 생기지 않는다는 문제를 닫았다 — **"밖 BER 0.5 포화"가 전 통계의 암묵 전제** 였다는 것을
명시 사양으로 만든 것이다. 20 은 G0 루프백 핀을 JE1(V12)↔JE2(W16), MMCM 입력을 K17 로
정했는데, JE 내장 200Ω 직렬 저항이 핀 충돌 보험으로 공짜라서다(실칩 G2 는 고속 PMOD JB).
21 호스트를 PS bare-metal C(Vitis standalone, CSV 는 UART→PC 파일화)로 둔 것도 같은 성격이다.

마지막으로 계약의 경계 표기를 사람에서 블록/폴더명 기준으로 바꿨다. `roles.md` 와의 불일치를
없애기 위해서인데, 총력전 중에는 배정이 유동이라 사람 이름으로 적은 경계가 곧 틀린 문서가
된다. 결과물이 기준이다 — `fpga/rtl/core/` 는 계측 제어, `fpga/rtl/flash/` 는 측정 대상
경로(루프백 프런트엔드 포함)다.
