  들어가니 계약이 말하지 않은 자리가 나왔다 — 호스트가 CTRL 에 명령 비트를 두 개 이상

## 근거

### 1. 스텁만 갈아끼우면 core 전체가 순수 Verilog 가 된다

프리미티브를 `core_mmcm.v` 한 파일에만 격리했다. 박지민의 iverilog+cocotb 사다리에서
MMCM 스텁만 바꿔 끼우면 나머지 core 는 손댈 것 없이 시뮬레이션에 올라간다. 시뮬 가능성을
나중에 확보하려면 이미 얽힌 것을 풀어야 하므로 처음부터 갈랐다.

### 2. 조합은 항상 호스트 버그다

호스트 시퀀스는 구조적으로 한 번에 한 명령이다. 그러니 CTRL 에 명령 비트가 둘 이상 서는
일은 정상 동작으로 도달할 수 없고, 언제나 호스트 쪽 버그다.

처음에는 조용한 무시로 구현했다가 7/7 리뷰에서 바꿨다 — R11 과 같은 "시끄러운 거부"
철학이어야 한다. 순차 실행안은 요청도 없는 기능(명령 큐 FSM)을 들이는 것이라 기각했다.

리셋으로만 클리어하는 이유는 이 비트의 성격이다. `CMD_ERR` 은 측정 상태가 아니라
**소프트웨어 버그 검출기** 이고, 스윕 종료 시 1회 확인해 무효 판정에 쓰는 증거물이다.
다음 START 가 지우면 증거가 사라진다.

R4 의 "busy 중 무시"는 계약 문언 그대로 조용히 두었다 — 그쪽은 호스트가 R4 대로 STATUS 를
보고 오면 안 밟는 자리다.

### 3. 거부된 START 가 이전 증거를 지우면 안 된다

DONE 은 R5 문언 그대로 START 수락 시 지운다. TIMEOUT·CFG_ERR 은 `meas_busy` 상승
(= "유효 START", R11 문언) 시 지운다.

둘을 같은 시점으로 묶으면 **거부된 START 가 이전 TIMEOUT 증거를 지운다.** 거부는 아무
일도 일으키지 않아야 하는데 증거만 날리는 셈이 된다.

### 4. 폴링 트래픽에 단일 미결로 충분하다

8.4ms 당 ~200회 폴링이다. outstanding 을 늘려 얻을 것이 없다. `LOG_DATA` 는 별도
트랜잭션이라 "주소 다음 사이클 유효"라는 계약이 자동으로 충족된다.

### 5. 판정 주체와 레지스터 소유자가 다르다

계약 수정 4건을 제안했다.

1. **§2 신호 2개** — `meas_timeout`(done 과 동시 1펄스, R10)·`cfg_err`(거부 1펄스, R11).
   `STATUS.TIMEOUT`/`CFG_ERR` 은 core 레지스터인데 판정 주체는 flash 다. 그 사이를 잇는
   전달 경로가 §2 에 없었다. 부결되면 core 가 R11 을 자체 검사하는 대안으로 재작업해야
   한다 (R10 은 어차피 신호가 필요하다)
2. **§3 CTRL "명령 비트는 한 번에 하나"** + `STATUS` bit6 `CMD_ERR` — §2 의 결론을 계약
   문언으로 올리는 것이다
3. **R11 "유효 START" 조작적 정의** = `meas_busy` 상승 에지 — §3 의 근거를 계약이 말하게
   한다
4. **§6 무효 런 ⑥** 스윕 종료 시 `CMD_ERR=1` — 호스트 스윕 코드가 종료 시 1회 확인한다

sticky 클리어 시점 중 DONE = START 수락 시는 R5 문언 그대로라 계약 수정이 아니다 — 추인
때 통보만 한다.

### 6. O=45 는 되돌리기 싼 보수값이다

브링업에서는 여유가 큰 쪽이 낫다. 안정화 후 `O=25/15` 상향 검토(계약 결정 16)는
`core_mmcm.v` 파라미터 2줄 수정으로 끝나므로, 지금 조여 둘 이유가 없다.

### 7. busy 가 늦으면 두 번째 START 가 들어올 창이 생긴다

core 의 명령 게이팅이 `meas_busy` 를 참조한다. flash 의 busy 상승이 2사이클 이상 늦으면
그 틈에 두 번째 START 가 수락될 수 있다.

R11 검증은 cfg 래치값의 조합 논리라 1사이클 판정이 가능하고, R11 의 "busy 발행 없음"과도
양립한다. 호스트가 R4 대로 STATUS 를 확인하고 명령하면 실제로는 안 밟는 창이지만,
하드웨어 성질로 닫아 두는 것이 계약 철학과 일치한다.
