## 근거

### 1. 순서를 ④→③으로 바꿨다

캡처가 UID→라벨 역조회에 등록부 파서를 import 한다. 파서가 먼저 있어야 캡처를 검증할 수
있어 순서를 바꿨다. 파서는 `host/capture/`에 뒀다 — 캡처가 의존하는 가장 낮은 층이고
"계약 §6이 바뀌면 바뀐다"는 캡처 폴더 기준과 어긋나지 않는다(라벨 규칙 `chip01~chip10`이
§6 것이다). `chip_pe.py`는 래퍼만 쓰므로 `host/run/`.

### 2. 포트를 비트스트림 굽기 **전에** 연다 — 프롬프트와 반대

프롬프트는 "굽는 동안 포트를 닫는다"였다. 구현하려다 보니 UID 줄을 잃는 경로였다.
`program_g2.tcl`은 `con` 직후 앱이 즉시 `#PREP JEDEC`·`#PREP UID`를 찍는데, xsct 종료 →
파이썬이 포트를 다시 여는 사이 1~2초 tty 가 닫혀 있으면 USB-시리얼 드라이버가 바이트를
버린다(FT2232 RX FIFO 는 수백 바이트라 운이 좋으면 남지만 보장이 없다). 세션 2도 같다 —
`#G0 SWEEP BEGIN`을 놓치면 캡처가 `began=False`로 전 행을 버려 무효 ⑤가 된다.

반면 `rst -system` 쓰레기는 런북 3이 이미 "캡처 먼저, xsct 나중" 순서로 겪어 온 상황이고
접두 필터(`#PREP`/`#G0`)로 무해하다. 남는 위험은 쓰레기 바이트가 줄바꿈 없이 첫 실제 줄
앞에 들러붙는 것인데, 래퍼는 시리얼 timeout=2s 를 써서 xsct 의 fpga 프로그래밍(수 초) 사이에
잔여물이 부분 줄로 먼저 빠지게 했고, `#PREP` 은 `find()`로 줄 중간에서도 잡는다.

**이 마지막 문단이 이튿날 반증됐다** — §8 「중요 3」. `run_xsct()`는 `subprocess.run`으로
블로킹하며 그동안 `readline()`을 아무도 호출하지 않으므로, 쓰레기와 `#G0 SWEEP BEGIN`은
커널 버퍼에 같이 쌓였다가 첫 `readline()`이 한 줄로 돌려준다. 그래도 **결정 자체는
바뀌지 않는다** — 첫 줄을 잃으면 전 행이 버려지므로 열어 두는 쪽이 맞고, 원문의 "닫는다"
지시가 틀렸다. 남는 근거는 경험뿐이다: 7/8·8/23 스윕이 같은 "캡처 먼저" 순서에
`startswith`로 성공했으므로 이 보드에서 쓰레기가 없거나 `\n`으로 끝날 가능성이 높다.

### 3. `--n-reads`는 검사만 한다 — 값을 바꿀 길이 없다

`N_READS_CFG`는 `g0_sweep.c` 컴파일 상수(100)이고 `build_g3_sweep.py`는 `SWEEP_STEPS`·
`F_SCLK_HZ`만 치환한다. 래퍼가 N 을 정할 수단이 리포에 없다. 그래서 `--n-reads`는 BEGIN 줄의
`n=`과 대조해 다르면 **그 회차 CSV 는 남기고** 중단한다(열의 `n_reads`가 진실이므로 파일은
틀리지 않았다 — 요청과 다를 뿐). 수정안 #2 §7 의 D 2단계(N=112 스윕)를 실제로 돌리려면
빌드 스크립트에 `N_READS_CFG` 치환을 넣어야 한다([U24-2]). `--base-sector`도 같은 이유로
0 만 받는다.

검토에서 비용이 하나 드러났다 — 지금은 N=100 만 존재하므로 이 검사가 실제로 잡는 것은
사용자의 `--n-reads` 오타뿐이고, 그 오타를 **스윕 완주(~6분) 뒤에** 알게 된다. 기대 n 을
`capture_sweep`에 넘겨 BEGIN 줄에서 즉시 끊으면 6분과 파일이 절약되나, [U24-2]가 풀리기
전까지는 현행 유지도 무방하다고 보고 두었다.

### 4. `--no-prep`은 `--uid`를 요구한다

prep 을 건너뛰면 UID 를 읽을 세션이 없다. 그런데 캡처는 UID 없이 chip CSV 를 만들지 않는다
(그게 ③의 요지다). 남는 길은 사람이 UID 를 주는 것뿐이라 `--no-prep --uid <16hex>`로 묶었고,
등록부에 **있는** UID 만 받는다 — 기계가 읽지 않은 UID 로 신규 등록을 하면 안 된다. 세션
로그에 "기계 확인 없음"을 남긴다. `flash_uid.c`(W5-M)가 생기면 이 약한 경로를 닫을 수 있다.

**최소 개구다.** 사람이 입력하는 것은 라벨이 아니라 UID 이고 라벨은 여전히 등록부가 답하므로
원문 정신("라벨을 사람이 입력하지 않는다")과 충돌하지 않는다. 남는 약점은 "소켓에 그 칩이
있다"는 검증이 없다는 것 — 로그 23 §3 ②의 문제가 이 경로에만 남는다. 그리고 **CSV 자체에는
기계 확인 여부가 없다**(세션 로그에만 있다). 수정안 #3 §2.2 에 "`--no-prep` 배치의 uid 는
세션 로그 근거"를 한 줄 적어 두면 사후 판독이 선다.

### 5. 캡처가 같은 경로를 덮어쓰지 않는다 — 프롬프트 밖 한 글자

가짜 시리얼 테스트에서 같은 초에 두 캡처가 돌자 valid 파일이 다음 캡처의 `_invalid` 개명에
덮여 사라졌다. `open(..., "x")`로 바꿨다. 실사용에선 스윕 간격이 분 단위라 안 일어나지만,
측정 원본이 조용히 사라지는 경로를 한 글자로 막을 수 있어 넣었다.

**목적은 정당하나 표면이 거칠다.** 같은 초 재시도에서 생 `FileExistsError` 트레이스백이
나가고(래퍼 안에서는 요약 줄 없이 죽는다), `rename()`은 여전히 덮어쓰므로 같은 초에 무효가
두 번 나면 첫 `_invalid`가 사라진다. 래퍼 경로에서는 회차 사이에 xsct(≥10초)가 끼므로
실사용 트리거는 사실상 없다.

### 6. 실패 두 종류를 가른다

회차 하나가 `valid=0`이면 그 회차만 `_invalid`로 남기고 다음 회차로 간다. xsct 실패는
즉시 중단이다. 배치가 끝나면 `"3/3 완료 (invalid 1)"`과 함께 **exit 1** 이 나간다 —
"그 회차만 무효로 남기고 계속"은 지키되, 종료 코드는 "전부 유효는 아님"을 알려야 한다.

### 8. 검토에서 뒤집힌 것 — 중요 4건과 그 수정 (2026-09-08)

이튿날 같은 커밋들을 원문 프롬프트·로그 23·수정안 #3과 대조했다. **치명 0건**, 원문 요구는
옵션 4종 금지·불변식 위치·append-only·등록부 정정·문서 정합까지 대부분 충족이었고,
미충족은 하나 — 원문 ④의 "전송 실패 3회 재시도"가 래퍼 경로에서 무효가 되는 것이었다.
영웅님 결정으로 중요 1·2 를 고치고 덤으로 3·4 까지 같이 갔다(브랜치
`worktree-fix-sweep-wrapper-review`).

**중요 1 — `#PREP ERROR`를 FAIL 과 같이 즉시 중단.** `flash_prep.c`의 `xfer()`는 실패마다
`#PREP ERROR spi transfer len=13`을 찍고 `-1`을 돌려주며 재시도 루프가 이어서 다시
시도하는데, 래퍼는 그 첫 줄에서 죽는다. 펌웨어는 계속 돌아 PASS 까지 갈 수 있고 **칩은
이미 prep 돼 P/E +1 이 실제로 발생**했는데 래퍼는 `chip_pe.md`에 기록하지 않고 등록부도
안 채운다. 아래 [U24-8]의 "동작엔 무관"은 사실이 아니었다.
→ **수정: 펌웨어 쪽을 고쳤다.** UID 재시도 루프에서 `xfer()` 대신
`XSpiPs_PolledTransfer()`를 직접 부른다(1줄). `#PREP ERROR`는 이 앱의 **다른 모든 경로에서
종료 신호**이고(JEDEC·지우기·쓰기 실패는 ERROR 뒤 FAIL 없이 `return 1`), 규칙을 깨는 곳이
UID 재시도 하나뿐이므로 그쪽을 고치는 것이 맞다. 래퍼에서 ERROR 를 무시하는 반대 방향을
택하면 JEDEC 전송 실패 때 FAIL 줄이 없어 15분 타임아웃을 기다리게 된다. 포기 시엔 기존
`#PREP FAIL uid transfer`가 나간다.

**중요 2 — `ses.open()` 전에 끝나는 경로에서 세션 로그가 어디에도 안 남는다.** 신규 UID
라벨 오타(`RegistryError`) · 라벨 프롬프트 Ctrl-C · prep 도중 Ctrl-C · 포트 열기 실패가
그렇다. 앞의 둘은 **`flash_prep`이 완주한 뒤**라 칩에 P/E +1 이 들어갔는데 `chip_pe.md`
에는 없고 `#PREP UID`는 화면에만 있다. 다시 돌리면 +1 이 또 들어가고 첫 +1 은 이력에서
영구히 사라진다 — 이력 파일의 존재 이유와 정면 충돌이다.
→ **수정: 메모리 버퍼를 없애고 시작 즉시 `session_<batch_id>.log` 에 매 줄 쓴다.** 라벨·
UID 를 알면 `rename()` 한다. `except` 를 하나씩 추가하는 방식은 강제 종료 같은 못 잡는
경우가 남는데, 처음부터 디스크에 쓰면 그 부류가 통째로 사라지고 코드도 줄어든다.
라벨 입력은 후보에 들 때까지 되묻게 했다 — 남는 구멍은 프롬프트에서 Ctrl-C 뿐이고, 그때도
세션 로그에 `#PREP UID`·`PASS`가 있어 사람이 소급 행을 넣을 수 있다.

**중요 3 — 세션 2 첫 줄 앞 쓰레기 방어가 실제로는 없다.** §2 의 근거 문단이 성립하지
않는다는 것이 여기서 나왔다. 재현: 쓰레기가 줄바꿈 없이 BEGIN 앞에 붙으면
`startswith("#G0")`가 실패해 **INVALID 0/0**. `run_prep()`만 `find()`를 써서 세션 1 은
방어되고 세션 2 는 방어가 없었다.
→ **수정: `capture_sweep()`도 `find("#G0")` 후 절단.** `run_prep()`과 같은 방어다.

**중요 4 — `Abort`·`KeyboardInterrupt` 외 예외에서 `k/N 완료` 요약이 안 찍힌다.**
`FileExistsError`(캡처) · `serial.SerialException`(스윕 중 케이블 뽑힘) ·
`subprocess.TimeoutExpired`(xsct 10분)가 해당한다.
→ **수정: `except Exception` 에서 예외와 요약을 로그에 남기고 재전파.**

수정 후 하드웨어 없이 재검증했고(쓰레기+BEGIN 한 줄이 VALID 로, 라벨 오타가 재입력으로,
포트 실패·Ctrl-C·스윕 중 예외에서 세션 로그와 요약이 남는 것, `--selftest` 4개 전부 PASS),
`flash_prep.c` 는 경고 0 으로 다시 빌드됐다. **`#PREP ERROR` 를 펌웨어가 찍는 경우 래퍼가
중단하는 것은 그대로 두었다 — 이제는 의도다.**

### 9. 고치지 않고 남긴 것

검토가 경미 7건·지적 10건을 같이 냈고 중요 4건만 고쳤다. 남긴 것은 **지금 닿지 않는
경로이거나 관례 차이**다.

- `_invalid` 개명(`rename()`)은 여전히 덮어쓴다 — 같은 초에 무효 두 번이면 첫 것이 사라진다
- 등록부 파서는 표가 파일 끝이고 마지막 줄에 `\n`이 없으면 행 추가가 이전 행에 이어 붙는다.
  `chip_pe.py`는 이 케이스를 처리했는데 등록부 쪽은 빠졌다. 현 등록부는 10행이 다 있어
  행 추가 경로 자체가 닿지 않는다
- 셀에 `\|` 이스케이프가 있으면 행 재조립에서 깨진다. 현 등록부에 그런 셀은 없다
  (`chip_pe.py`는 `|`를 거부하고 등록부는 안 한다)
- 셀프테스트 `batch_id`가 ISO 형식이다 — 수정안 #3 §2.2 는 `YYYYmmddTHHMMSSZ`. 헤더 16열은
  맞고 값 형식만 다르다
- `--prep-only`가 요약 없이 exit 0 · `TimeoutExpired`·`EOFError`(Ctrl-D) 미처리
  — 앞의 둘은 **2026-09-16 [로그 36](36.flash_id_and_sweep_uid_check.md) 개편으로
  없어졌다**: `--mode newchip|sweep` 으로 가면서
  `--prep-only` 자체가 사라졌고, `TimeoutExpired` 는 중요 4 의 `except Exception` 이 요약을
  남기고 재전파한다. `EOFError` 는 그대로 남아 있다
- 등록부 파서는 같은 헤더의 **첫** 표를 잡고, 고친 행의 빈 셀이 `|  |`가 된다
- `#PREP JEDEC`은 `%02x` 소문자, `#PREP UID`는 `%02X` 대문자 — 한 앱 안에서 불일치(파서는 관대)
- `capture_sweep()`에는 데드라인이 없다 — 보드가 스윕 중 죽으면 영원히 기다린다(Ctrl-C 가 출구)
- 재장착 프롬프트에서 칩을 안 빼고 엔터만 쳐도 검출되지 않는다 — 로그 23 부록 A 가 이미 인정

검토 중 사고가 하나 있었다. 첫 래퍼 하네스가 `label_for`·`register`·`capture_sweep`의
**기본 인자가 정의 시 바인딩**된다는 것을 놓쳐 실제 `docs/chip_registry.md`와 `build/data/`
를 건드렸다. `git checkout` + 가짜 CSV 삭제로 원복했다. [U24-7]을 정할 때 이 바인딩을
감안해 `path`를 명시 인자로 넘기는 편이 안전하다.
