# 35. `flash_id` 설계 결정 — sweep 모드가 칩을 확인하지 않는 문제

- **작성일**: 2026-09-16
- **작성**: 한영웅
- **성격**: 설계 결정. 구현은 별도 세션(로그 36)
- **발단**: `run_sweep_chip.py` 를 `--mode` 구조로 바꾸면서(로그 34) `sweep` 모드가
  **아무 확인 없이 측정에 들어간다**는 것이 드러났다
- **관련**: 로그 23 부록 A · 로그 34 · 워크플로 9(역할) · `docs/chip_registry.md`

---

## 1. 산출물 (예정)

| # | 산출물 | 위치 | 성격 |
| - | ------ | ---- | ---- |
| 1 | 공용 부품 (UART·SPI·JEDEC·UID) | `ps/src/flash_io.{c,h}` | 신설. `main()` 없음 |
| 2 | 신원 확인 앱 | `ps/src/flash_id.c` | 신설. 부품의 첫 소비자 |
| 3 | 빌드 스크립트 | `ps/scripts/build_flash_id.py` | 신설. G2 XSA 소비 |
| 4 | sweep 모드 세션1 + UID 대조 | `host/run/run_sweep_chip.py` | 수정 |
| 5 | 빌드 단계 등록 | `reproduce.py` `STEPS` | 수정 (미결 5) |

기존 앱 네 개(`flash_prep` · `flash_jedec` · `core_smoke` · `g0_sweep`)는 **건드리지 않는다**(D2).

## 2. 무엇이 문제인가

`--mode sweep`(등록된 칩 재측정, P/E 불변)은 `flash_prep` 을 돌리지 않는다. 그런데 칩을
확인하는 일이 전부 그 앱 안에 있었다.

| | `--mode newchip` | `--mode sweep` |
| --- | --- | --- |
| 세션1 | `flash_prep` | **없음** |
| JEDEC(접촉·배선) | O | **×** |
| UID(신원) | O — 기계가 4Bh 를 3회 읽음 | **×** — 사람이 `--chip` 으로 선언 |
| P/E | +1 | 0 |

**P/E 를 아낀 대가로 확인을 통째로 잃은 상태**다. 설계 의도가 아니라, "UID 를 읽으려면
반드시 지워야 한다"는 제약에서 나온 부작용이다.

위험이 비대칭이다. 잘못 집은 칩으로 측정하면 **CSV 에 남의 UID 가 박히고**, 사후에
판별할 방법이 없다. 앵커(chip02)를 사이사이 끼우는 W10-M 에서 특히 실현 가능성이 높다 —
책상에 육안 구분이 안 되는 칩이 10개 널려 있다.

**로그 23 부록 A 가 이 상황을 예고했다**: W5-D(책상에 chip01 한 개)에서는 오배치가 물리적으로
불가능해 UID 전용 앱을 만들지 않기로 했고, **"W5-M(10칩 배치)에서는 다르다 … `flash_uid.c` 가
필요하다"** 고 적어 두었다. 과거 판단을 뒤집는 게 아니라 **그 조건이 도래했다.**

## 3. 결정과 근거

### D1. `flash_jedec.c` 를 확장하지 않고 새 앱을 만든다

`flash_jedec` 은 이미 UART 설정·SPI 초기화·JEDEC 읽기를 갖고 있어 **UID 읽기 25줄이면**
끝난다. 그럼에도 새 앱으로 간다.

- 그 파일은 **장세은 소유**다 (헤더: "스펙·검토·게재물 캡처 소유: 장세은", 로그 9 ③).
  게재 2번(성공 캡처 + 모듈 분리 대조군)의 산출 경로다
- **앱 하나 = 목적 하나**가 지금 4개 앱이 지켜온 규칙이다. 진단·게재용 앱이 측정 전
  신원 확인까지 겸하면 둘 중 하나를 바꿀 때 다른 하나가 딸려 온다
- `flash_jedec` 은 1초 주기 무한 루프다. 측정 직전에 쓰기엔 성격이 다르다

25줄을 아끼자고 소유가 갈린 게재물 파일을 건드릴 이유가 없다.

### D2. 공용 부품은 신설하되, **기존 앱은 옮기지 않는다**

중복 실측 (2026-09-16):

| | `core_smoke` | `flash_jedec` | `flash_prep` | `g0_sweep` |
| --- | --- | --- | --- | --- |
| `uart_set_baud()` | ✓ | ✓ | ✓ | ✓ |
| SPI 초기화 | | ✓ | ✓ | |
| `xfer()` | | | ✓ | |
| JEDEC 확인 | | ✓ | ✓ | |

**UART 보 레이트는 네 앱 전부에 같은 코드로 있다.** 9/15 에 115200 → 921600 으로 바꿀 때
네 파일을 다 고친 것이 이미 치른 비용이다(로그 30 §10.3). 통합할 이유는 충분하다.

그런데 **지금은 아니다**:

- `flash_prep` 은 **chip05~10 을 측정할 바로 그 앱**이다. 리팩터하면 chip04 와 다른 빌드가
  되고, 프리스케일러·보 레이트가 미묘하게 달라지면 측정 도중에 알게 된다
- `flash_jedec` 은 장세은 소유다 (D1)
- 마모 엔진(`flash_wear`)이 무엇을 필요로 할지 아직 모른다. 지금 인터페이스를 고정하면
  그때 또 고친다

그래서 **새 코드만 부품으로 만든다.** 늘어나는 중복은 `flash_id` 를 독립 파일로 만들든
부품으로 만들든 같고, 부품으로 두면 **미래 통합 지점이 생긴다**. `flash_wear` 를 만들 때
`flash_prep`·`flash_jedec` 을 여기로 옮긴다 — 그때는 캠페인도 끝나 있고 사용처도 확정된다.

### D3. JEDEC 까지 읽는다 → 이름은 `flash_id`

UID 가 3회 일관되게 읽히면 통신은 이미 증명된다. JEDEC 은 **중복**이다. 그럼에도 넣는다 —
값어치가 **실패했을 때 원인을 가르는 것**에 있기 때문이다.

| UID 만 읽을 때 | JEDEC 도 읽을 때 |
| --- | --- |
| "UID 안 읽힘" | `FF FF FF` → 무칩·오배선 |
| | `00 00 00` → 전원·CS |
| | `EF 40 17` 인데 UID 실패 → SPI 경로 간헐 |

코드 3줄에 이 진단이 붙는다. 밤에 칩을 갈아 끼우다 안 될 때 원인을 바로 짚어준다.

그래서 이 앱은 "UID 를 뽑는 앱"이 아니라 **"신원을 확인하는 앱"**이고, 로그 23·워크플로 9 가
예고한 이름 `flash_uid` 는 절반만 말한다. **`flash_id`** 로 간다 — 앱 이름이 하는 일을 말하는
이 저장소의 규칙(`flash_jedec`·`flash_prep`·`g0_sweep`)과 같은 축이다.

### D4. 출력 접두는 `#G2`, 형식은 기존 파서와 맞춘다

`flash_jedec` 이 `#G2`, `flash_prep` 이 `#PREP` 를 쓴다. 새 앱은 G2 비트스트림 위에서 도는
진단 계열이므로 `#G2 JEDEC …` · `#G2 UID <16hex 대문자>`. 래퍼 파서는 두 접두를 다 받게 한다.

### D5. 대조 실패는 **스윕 전에** 중단한다

읽은 UID 와 `--chip` 의 등록부 UID 가 다르면 즉시 `Abort`. 메시지에 읽은 UID·기대 UID·기대
라벨을 모두 찍고, 읽은 UID 가 등록부에 있으면 그 라벨도 같이 보여준다 — "무슨 칩을 꽂았는지"를
사람이 바로 알아야 한다.

세션1 은 약 10초, **P/E 는 0**이다. 이 비용으로 sweep 모드가 newchip 과 같은 수준의 사전
확인을 갖는다.

## 5. 미결 의사결정

1. **역할 배분.** 워크플로 9 는 `flash_uid.c` 를 **장세은** 담당으로 둔다. 세은이 Windows
   빌드에 묶여 있어 한영웅이 직접 하기로 했는데, **이 변경은 회의에서 확정할 사안**이다.
   확정 전에는 워크플로 9 를 고치지 않는다
2. **`flash_prep`·`flash_jedec` 을 언제 `flash_io` 로 옮길 것인가.** D2 는 "마모 엔진을 만들
   때"로 미뤘다. 그 시점에 `flash_wear` 가 요구하는 인터페이스를 보고 한 번에 정한다
3. **재장착 미검출은 그대로 남는다.** UID 대조는 "다른 칩을 꽂았다"만 잡고 **"재장착을
   안 했다"는 못 잡는다**(로그 23 부록 A 에서 이미 지적된 한계). 재장착 σ 의 신뢰는 여전히
   사람 손에 달려 있고, 이 작업으로 해결되지 않는다
4. **`reproduce.py` 에서 선택 단계인가 기본 단계인가.** `jedec`·`smoke` 처럼 `default=False`
   로 두면 필요한 사람만 굽는다. 그런데 `--mode sweep` 에 이 ELF 가 **반드시** 필요하고
   앵커 측정(chip02 ②③④)이 W10-M 일정에 들어 있어, 측정하는 사람은 전부 필요해진다.
   추가 비용은 약 17초. **FULL 에 넣는 쪽으로 기운다** — "빌드는 통과했는데 측정을 못 하는"
   상태를 만들지 않는 것이 `reproduce.py` 의 목적이다. 다만 구현물을 보고 확정한다
   → **확정: `FULL` 에 넣었다** (2026-09-16, 로그 36 §2-8). 구현은 선택 단계로 왔으나,
   `--mode sweep` 이 ELF 없이는 시작도 못 하는 것을 실제로 확인하고 뒤집었다
5. **`--mode sweep` 의 세션1 을 선택으로 둘 것인가.** 지금은 항상 돌리는 것으로 본다.
   10초·P/E 0 이면 끌 이유가 약하지만, 앵커를 연속으로 여러 번 돌릴 때 불필요하게 느껴질 수
   있다. 실제로 돌려보고 정한다
