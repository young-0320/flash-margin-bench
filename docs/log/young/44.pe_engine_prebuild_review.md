## 근거

### 1. 두 번째 구간을 시작할 수단이 없다 — mock 에서 재현했다

경계는 START(신규) · RESUME(읽기 전용) · REERASE 뿐이다. START 는 tally 에 `0x00` 이 하나라도
있으면 `E_DIRTY` 로 거부한다 — S-4 §4 마지막 줄, 재개를 신규로 착각해 tally 를 지우는 것을 막는
자물쇠다. 그 자물쇠가 정상 진행도 잠근다.

```
wear_start(0,7,0x00,300) → (300, 'checkpoint_due')   tally (300, 300)
wear_start(0,7,0x00,300) → REJECT E_DIRTY
```

지금 harness 는 START 한 번에 100사이클을 돌리고 끝나므로 이 자리를 한 번도 밟지 않았다.
전원 장애 복구도 같다 — RESUME 이 원자료를 주고 호스트가 147 을 채택해도, 그 147 을 엔진에
넘겨 A 행 번호와 tally 눈금(다음 마크는 200)을 잇는 명령이 없다. 지민 회신의 명령표 넷에도 없다.

「N번째 체크포인트까지는 사람이 확인하고 넘어간다」는 옵션(S-1 §11 「자동화 전 수동 판정」)은
**호스트가 사람을 기다리느냐** 의 정책이고 이 문제와 층이 다르다. 사람이 「가라」고 해도 엔진에
그것을 받을 명령이 없다.

후보는 둘이다. ⓐ START 에 `cycle=` 을 더하고 `E_DIRTY` 를 「tally 가 비어 있지 않은데
`cycle=0`」으로 좁힌다. ⓑ `CONTINUE cycle= delta=` 를 신설한다. ⓐ를 권한다 — 명령이 하나이고
범위 검사가 한 곳이며, 받은 `cycle` 과 tally×100 의 관계가 S-1 §8.3 의 `d` 규칙 밖이면
엔진이 거부하는 안전판을 같은 자리에 둘 수 있다. 어느 쪽이든 경계 서명 변경이라 `pe_engine.md`
· S-4 §4 · mock · TB 케이스가 함께 바뀐다 — [U44-1].

### 2. 체크포인트마다 리셋은 어차피 일어난다 — mux 의 전제

지민이 mux 를 고른 이유는 「체크포인트마다 보드 리셋과 재프로그래밍이 개입하지 않게」다.
그런데 스윕은 부팅 1회에 1회다 — `g0_sweep.c:121` 이 그렇게 짜여 있고, `program_g3.tcl` 은
MMCM 위상 잔존(`phase_pos_mismatch`) 때문에 ELF 만 재로드하면 거부되도록 전체 경로
(`rst -system` → 비트스트림 → ELF)를 강제한다. 파일럿 한 점에 스윕이 3회이므로 리셋이 최소
3회다. 무상태 엔진은 어차피 §13 B(전원 차단)가 요구하므로 추가 비용이 아니다.

| | ⓐ 스윕을 부팅 1회 X회로 고치고 mux 로 한 비트스트림 | ⓑ 리셋을 받아들이고 엔진을 무상태로, 파일럿은 mux 없이 |
| - | - | - |
| 새로 만드는 것 | 스윕 앱을 명령 서버로 재작성 · 위상 0 복귀 · 캡처 스크립트 다세션화 · mux RTL · 계약 수정안 · cocotb · 핀 브링업 | flash_prep 파라미터화(B-0) · 호스트가 XSCT 로 ELF 를 갈아 끼우는 절차 |
| 검증된 계측기(스윕)에 손대나 | **댄다** — 게재 곡선과 앵커 기준선의 출처 코드 | 안 댄다 |
| 체크포인트당 JTAG 작업 | 0 | 약 7회 (prep 3 · 스윕 3 · 엔진 1) |
| JTAG 이 실패하면 | — | 엔진은 `checkpoint_due` 에서 멈춰 있어 **마모도 X축 손상도 없다**. 사람이 재시도 |
| 파일럿 전체 절약 시간 | 리셋·로드 약 11점 × 7회 × 10초 ≈ 13분 | — |
| 새 고장 부류 | 두 마스터가 한 버스 — 동시 구동 | 없음 |

파일럿(34~40시간)에서 ⓐ가 되찾는 것은 십수 분이고, 그 값으로 검증된 계측기를 열고 P/E 엔진
일정을 스윕 재작성에 묶는다. **파일럿은 ⓑ** 를 권한다. 본 실험은 점당 스윕이 15회라 JTAG
작업이 점당 20회에 가까워지므로 그때 ⓐ를 다시 본다 — 파일럿에서 JTAG 실패율이 실측되면 그
판단의 분모가 생긴다. 한영웅은 ⓐ 쪽 성향이다 — [U44-2].

### 3. mux 가 살아남으면 계약이 열린다

로그 29 §4 가 PS C 를 고른 근거 하나가 「계약 변경 0」이었는데 mux 는 소유권 선택·readback
레지스터 하나를 요구한다. 계약 §3 에 `0x28` 이 비어 있다. 리셋 시 기본 소유자는 PS 쪽이어야
한다 — 리셋 직후 도는 것이 prep 이나 엔진이기 때문이다. §2 가 ⓑ로 가면 파일럿에는 필요 없다.

### 4. 근접·원격 보호가 거부 코드에 없다

S-4 §4 의 여섯 거부에는 tally 겹침만 있다. `START base=7 n_sectors=7` 은 통과해 근접 대조군을
마모시킨다. `base` 가 인자인 이유(TB 영역 1,000 · 본 실험 그룹)는 타당하므로, 보호 목록을
엔진 상수로 두고 코드 하나를 더한다. 「ELF 재빌드 없이」의 조건은 START 의 네 인자에만 걸린
것이라 배치 상수를 빌드 타임에 두는 것과 어긋나지 않는다. S-4 §4 표와 T3 집행 케이스가 함께 는다.

### 5. 합 불변식은 패턴 `0x00` · 같은 읽기에서만 참이다

S-1 §7 은 「`erase_residual + program_fail = 전량` 이 항상 성립」이라 적었다. 기대 비트가 1인
자리에서는 두 값이 같은 것을 세므로 `0x55` 에서 깨지고, B 행의 두 값은 서로 다른 두 읽기라
B 행에는 애초에 적용되지 않는다 — mock 의 `_emit_b` 도 이미 두 시점 값을 실어 정상 B 행은
0+0 이다. `probe` 의 기대값도 패턴 의존이다 — 소거 직후 `program_fail` 의 정답은 전량이 아니라
`바이트 수 × popcount(~pattern)` 이다.

### 6. 사건 행 하나로 재소거와 정지 사유를 같이 받는다

재소거뿐 아니라 WIP 타임아웃·UID 불일치·프로그램 실패 같은 정지 사유도 S-1 §10 이 「기록」만
요구하고 자리가 없다. 부분 실패의 「어디까지 물리적으로 발행됐나」(지민 프롬프트 §3.3)도 같은
자리다. 종류(`kind=`)로 가르는 한 행이 후보다.

```
#WEAR R kind=reerase sector=3 t_erase_us=51230 ok=1 resid_before=812 resid_after=0 cycle=147 ts=… sum=…
#WEAR R kind=wip_timeout op=erase sector=5 wait_us=2000000 cycle=4211 ts=… sum=…
```

호스트 쪽은 `docs/chip_pe.md` 에 증분 +1 행을 비고 「reerase · ±1」로 남기면 영역별 누적에도
자취가 남는다. B 행의 phase 분리도 같은 성격이다 — 프로그램 실패(전하가 안 들어감)와 소거
잔류(전하가 안 빠짐)는 다른 고장이고 사후 분석의 「재현 횟수」는 phase 별 주소가 있어야 센다.
한 행 안에서 `p_defect_addrs`·`p_worst_page_idx`·`p_worst_page_bits`·`e_…` 여섯 필드로 가르면
A3 「정확히 1행」이 그대로 서고 파서(`key=value`)는 하위 호환이다. 로그 42 §8 이 제안-3 을 다시
열지 않기로 한 것은 우리가 여는 경우였고, 지금은 구현자가 묻는 경우다 — [U44-4]·[U44-5].

### 7. `recovering` 이 없으면 REERASE 의 조건을 엔진이 모른다

지민 §3.3 의 조건 「현재 세션이 전원 장애 복구 상태」·「가장 최근 live blank check 에서 부분
소거 확인」을 엔진이 판정하려면 RESUME 뒤의 상태와 마지막 blank check 결과를 들고 있어야
한다. 다섯 상태(`idle`·`running`·`checkpoint_due`·`halted`·`error`)에는 그 자리가 없다.
전이는 `idle → RESUME → recovering → blank_check → REERASE → blank_check → START(cycle=채택값)`.

### 8. 사람이 멈출 명령이 없다

구간이 ×2.15 로 자라 뒤로 갈수록 십수 시간이다. 중간에 세우려면 전원을 뽑는 수밖에 없고,
그러면 정상 중단이 아니라 복구 경로로 들어가 ±1 불확실을 떠안는다. `halted` 상태는 이미 있다.

### 9. `req` 는 리셋마다 0 으로 돌아간다

§2 대로 체크포인트마다 리셋이면 세션마다 `req` 가 새로 시작한다. 엔진에는 비휘발 카운터가
없으므로 세션 id 는 호스트가 준다. H 행이 그것을 되돌리면 호스트가 여러 세션의 로그를 이을 때
경계가 보인다.

### 10. 시간 예산 — 바닥은 칩이 정하고 SPI 는 웃돈만 깎는다

PS SPI 는 EMIO 경로라 상한이 25 MHz 다 (UG585 §17). 기준 클럭 166.67 MHz 에서 프리스케일러
8 → 20.8 MHz, 16 → 10.4 MHz, 지금은 64 → 2.6 MHz. 페이지 한 장 전송(260 바이트)이 2.6 MHz
에서 0.8 ms 라 tPP 와 같은 크기이고 그것이 112장이다. 추정치이고 실측 대상이다.

| PS SPI | 1사이클 | 300k |
| --- | --- | --- |
| 2.6 MHz (현재) | 약 495 ms | 약 41 h |
| 10.4 MHz | 약 430 ms | 약 36 h |
| 20.8 MHz | 약 415 ms | 약 34.5 h |
| 바닥 (7×tSE + 112×tPP) | 약 360~405 ms | 30~34 h |

다이가 하나라 동작을 겹칠 수 없고, 7섹터는 32KB 블록 소거 경계에 맞지 않아 명령 수도 못 줄인다.
`t_program_us` 는 WIP 지속시간 합이라 측정값은 클럭과 무관하다 — [U44-7].

### 11. TB 가 안 재는 자리

지금 TB 가 증명하는 것은 「START 한 번에 100사이클」이다. 파일럿은 약 11구간이 체크포인트로
이어지고 사이에 복구가 낄 수 있다. 이음매에서만 깨지는 것 — A 행 번호의 연속(300→301),
147 재개 뒤 tally 눈금 정렬, `E_DIRTY` 의 새 뜻, 세션·`req`, HALT 뒤 계속 — 은 지금 케이스에
